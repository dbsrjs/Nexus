## 0. 정한 것

### 16-1 스페이스 수준

| # | 결정 | 이유 |
|---|---|---|
| D1 | **스페이스 만들기를 앱에 둔다** — 스페이스 선택 화면과 레일의 「+」. 기존 `POST /api/spaces` 를 쓴다 | 지금은 시드만 스페이스를 만든다. 초대할 사람이 먼저 스페이스를 가져야 Phase 1 기준이 앱 안에서 닫힌다 |
| D2 | 초대 받기는 **코드 붙여넣기**다(딥링크는 «마지막»). 입력에서 **끝의 영숫자 12자**를 코드로 읽는다 — 앞뒤 공백 · 문장째 붙여넣어도 된다 | 제품 기획 §5.1-c. 코드는 헷갈리는 글자를 뺀 12자(`generateInviteCode`) |
| D3 | 초대 수락 실패는 **두 문구**로만 가른다 — 404 「없는 초대 코드」, 400 「만료됐거나 사용 한도가 찬 초대 코드」 | 서버 문구를 화면에 쓰지 않는다(§3 앱 규칙). 만료와 소진을 가를 필요가 없다 — 사용자가 할 일(새 코드를 받는다)이 같다 |
| D4 | 수락하면 서버가 **본인에게 `rooms:invalidate`, 스페이스에 `member:joined`** 를 보낸다. 앱은 스페이스 목록을 다시 받고 그 스페이스로 들어간다 | 새 스페이스 룸에 붙어야 실시간이 온다. 기존 멤버의 멘션 자동완성에 새 사람이 바로 떠야 한다 |
| D5 | **스페이스 설정 창은 셸 밖 `/s/:spaceId/settings/:section`** — 섹션은 `general`(일반) · `members`(멤버) · `invites`(초대). 틀은 14단계 `SettingsFrame` 을 그대로 쓴다 | 들어갔다 나오는 곳이다(§3-13). 사용자 설정 창과 같은 모양이라 배울 것이 없다 |
| D6 | 진입은 **채널 판 머리 줄의 스페이스 이름**을 누르면 뜨는 메뉴 — 「멤버」(전원) · 「초대하기」 · 「스페이스 설정」(admin+) · 「스페이스 나가기」(owner 아님) | 디스코드와 같은 자리. 볼 수 없는 항목은 감춘다(§3-7) |
| D7 | **멤버 목록은 전원이 본다**(기존 `GET .../members`, 역할 제한 없음). 역할 바꾸기 · 내보내기 동작은 **내가 그 사람보다 높을 때만** 보인다 | 읽기 라우트에 `@MinRole` 을 걸지 않는다(§3-9). 서버의 `outranks` 규칙을 앱이 그대로 비춘다 — 눌러 봐야 실패할 버튼을 만들지 않는다 |
| D8 | 초대 관리 API 를 더한다 — **`GET .../invites`(유효한 것만) · `DELETE .../invites/:inviteId`**, 둘 다 admin+. 취소는 행을 지운다 | 새어 나간 코드를 거둘 방법이 없다. 초대는 사용자가 쓴 글이 아니라 지워도 잃는 것이 없다 |
| D9 | 「유효」는 **만료 전이고 사용 한도가 남은 것**이다. 지난 것은 목록에 싣지 않는다(행은 남는다) | 쓸 수 없는 코드를 보여 줄 이유가 없다 |
| D10 | 초대 만들기 화면은 **역할(guest · member · admin) · 유효 기간(1일 · 7일 · 무기한) · 사용 횟수(1회 · 10회 · 무제한)** 셋을 고른다. 기본은 member · 7일 · 무제한 | 기존 DTO 의 범위 안에서 자주 쓰는 값만 고르게 한다. 숫자 입력칸은 두지 않는다 |
| D11 | **나가기 `POST .../leave`** 를 더한다. owner 는 403(소유권 이전이 없다 — 범위 밖). 채널 멤버십을 같은 트랜잭션에서 지운다 | 기존 `DELETE .../members/:userId` 는 자기 자신을 막는다. 내보내기와 뜻이 달라 경로를 나눈다 |
| D12 | 멤버 변화는 스페이스 룸으로 **`member:joined` · `member:updated`(역할) · `member:left`** 를 보낸다. 앱은 멤버 목록을 다시 받는다 | 모두에게 같은 값이다(§3-6). 멤버 목록은 캐시하지 않으므로 고칠 drift 가 없다 |
| D13 | 내보내지거나 나가면 그 사용자에게 **`space:removed { spaceId }`** + `rooms:invalidate`. 앱은 **그 스페이스의 drift 캐시와 전송 큐를 지우고**, 보고 있었다면 `/spaces` 로 보낸 뒤 토스트로 알린다 | 볼 수 없게 된 대화가 기기에 남지 않게 한다. 큐는 보낼 곳이 사라졌다 — 남겨 두면 다시 초대받았을 때 옛 메시지가 뒤늦게 나간다. 사용자가 한 일(나가기) 또는 알린 일(토스트)이라 「조용히 지우지 않는다」와 어긋나지 않는다 |
| D13a | 내보내기 · 나가기에서는 **서버가 그 사용자의 소켓을 스페이스 룸과 그 스페이스의 채널 룸에서 직접 뺀다**(`socketsLeave`). `rooms:invalidate` 는 그 뒤에 보낸다 | `rooms:invalidate` 는 앱에게 「다시 계산해 달라」는 부탁일 뿐이다. 고친 클라이언트가 `rooms:sync` 를 부르지 않으면 내보내진 뒤에도 그 스페이스의 메시지를 계속 받는다 — 테넌트 격리 구멍이다 |
| D14 | 「일반」 섹션은 **스페이스 이름 바꾸기**만 둔다(기존 `PATCH /api/spaces/:id`, admin+) | 아이콘 올리기는 아바타와 같은 파이프라인이 필요하다 — 범위 밖 |

### 16-2 채널 수준

| # | 결정 | 이유 |
|---|---|---|
| D15 | **채널 만들기를 앱에 둔다**(admin+, 기존 `POST .../channels`) — 이름 · 주제 · 카테고리 · 비공개. 진입은 채널 목록 카테고리 머리의 「+」 | 비공개 채널을 앱에서 만들 수 없으면 비공개 멤버 관리가 쓸 곳이 없다 |
| D16 | **채널 설정 창은 셸 밖 `/s/:spaceId/c/:channelId/settings/:section`** — `overview`(개요) · `members`(멤버, 비공개만) · `permissions`(권한, 공개 채널 · admin+). 진입은 대화 머리 줄의 채널 이름 | D5 와 같은 틀 |
| D17 | **비공개 채널 멤버 추가 `POST .../channels/:channelId/members { userIds }`** — 그 채널을 볼 수 있고(= 이미 멤버) **역할이 member 이상**. 멱등. 스페이스 멤버가 아닌 id 는 **404** | 슬랙과 같다 — 비공개 채널은 안의 사람이 들인다. 손님(guest)은 들이지 못한다(§3-9 — 여럿에게 번지는 것). 없는 id 는 404(§3-4) |
| D18 | **제거 `DELETE .../channels/:channelId/members/:userId`** — 본인이면 누구나(나가기), 남이면 admin+. **마지막 한 명은 나갈 수 없다(409)** | 마지막 사람이 나가면 아무도 볼 수 없는 채널이 된다(admin 도 비공개 채널은 멤버여야 본다 — §3 가시성 표). 남을 빼는 것은 여럿에게 번지는 일이다 |
| D19 | 멤버 추가 · 제거는 **공개 채널에 400** | 공개 채널의 `channel_members` 는 읽음 · 음소거를 담는 행이지 출입 명단이 아니다 |
| D20 | 추가 · 제거된 사람에게 **`rooms:invalidate`**. 제거는 그 전에 **서버가 채널 룸에서 직접 뺀다**(D13a 와 같다) | 역할 변경과 같은 경로다(제품 기획 §5.1-c). 앱은 이미 이 이벤트에 채널 목록을 다시 받는다 |
| D21 | **권한 행은 guest · member 두 역할에만 둔다.** admin · owner 행은 400 | admin 이 자기 역할을 가려 채널에서 스스로 잠기는 길을 없앤다. 행이 없으니 admin+ 는 저절로 기본값(전부 허용)이다 |
| D22 | **`canView=false` 는 공개 채널에서만 뜻이 있다.** 비공개 채널에 `canView=false` 를 쓰면 400. 비공개에서는 명단이 정한다 | 두 규칙이 겹치면 「명단에 있는데 안 보임」이 생긴다. 하나만 정하게 한다 |
| D23 | **공개 채널에서 `canView=false` 는 `channel_members` 행보다 앞선다** — 지금은 행이 있으면 보인다 | 공개 채널은 한 번 읽기만 해도 `markRead` 가 행을 만든다. 지금 규칙이면 「역할 가리기」가 그 채널을 읽어 본 적 없는 사람에게만 듣는다 — 결함이다 |
| D24 | 권한 API 는 **`GET .../channels/:channelId/permissions`** · **`PUT .../permissions/:role { canView, canSend }`** · **`DELETE .../permissions/:role`**(기본값으로) — 전부 admin+ | 기존 스키마(`channel_permissions`)를 그대로 쓴다. 행을 지우는 것이 「기본값」이다 — 예외로만 쓰는 행(§3)이 남지 않는다 |
| D25 | 권한이 바뀌면 스페이스에 **`rooms:invalidate`**. `canView=false` 가 되면 그 전에 **그 역할의 스페이스 멤버를 채널 룸에서 직접 뺀다**(D13a) | 볼 수 있는 채널 · 보낼 수 있는지가 사람마다 달라진다. 앱은 이미 채널 목록을 다시 받는다 |
| D26 | 채널 목록 응답에 **`canSend`** 를 싣는다. drift `cached_channels.can_send` 한 컬럼(`schemaVersion` 18) | 받는 사람마다 다른 값이지만 목록은 원래 사람마다 따로 받는다(브로드캐스트가 아니다 — §3-6 과 어긋나지 않는다) |
| D27 | 보낼 수 없는 채널은 **입력창 자리에 「읽기 전용 채널입니다」** 한 줄. 메시지 메뉴의 고정 · 답글(스레드) · 답장을 감춘다. **리액션은 남긴다** | §3-9(리액션은 열람, 핀은 전송). §3-7(눌러 봐야 실패할 버튼은 만들지 않는다) |
| D28 | **옛 `src/permissions/` 는 지우고** 새 `PermissionsModule` 을 같은 자리에 쓴다. **판정은 `ChannelsService` 에 남긴다**(가시성 규칙은 한 곳) — 새 모듈은 행을 읽고 쓰는 API 만 맡는다. 판정은 순수 함수 `channelAccess()` 로 빼 단위 테스트한다 | 옛 코드는 단일 테넌트 · 전역 역할 · 없는 컬럼(`isReadonlyDefault`)을 참조한다 — 살릴 줄이 없다. 8-1 의 `src/files` 와 같은 처리다 |
| D29 | 채널 개요(이름 · 주제 · 비공개)는 **admin+ 만 고친다**(기존 `PATCH`). 그 밖의 사람에게는 읽기만 보인다 | 채널 구조는 admin(§3-9) |
| D30 | **공개 → 비공개로 바꾸면 그때 `channel_members` 행이 있는 사람이 명단이 된다.** 바꾸기 전에 확인 창에서 명단 인원을 알린다 | 공개 채널의 행은 「읽어 본 사람」이라 명단과 다를 수 있다. 숨기지 않고 알린다 |

## 1. API

### 16-1

```
POST   /api/spaces                                   { name }          → 201 Space        (기존)
PATCH  /api/spaces/:spaceId                          { name }          → 200 Space        (기존, admin+)
GET    /api/spaces/:spaceId/members                                    → 200 Member[]     (기존)
PATCH  /api/spaces/:spaceId/members/:userId          { role }          → 200              (기존, admin+)
DELETE /api/spaces/:spaceId/members/:userId                            → 204              (기존, admin+)
POST   /api/spaces/:spaceId/leave                                      → 204              (새)
POST   /api/spaces/:spaceId/invites                  { role?, expiresInHours?, maxUses? } → 201 Invite (기존, admin+)
GET    /api/spaces/:spaceId/invites                                    → 200 Invite[]     (새, admin+)
DELETE /api/spaces/:spaceId/invites/:inviteId                          → 204              (새, admin+)
POST   /api/invites/:code/accept                                       → 200 Space        (기존)
```

| 조건 | 응답 |
|---|---|
| 나가기: owner | 403 |
| 초대 취소: 다른 스페이스의 초대 · 없는 id | 404 |
| 초대 목록 · 취소 · 만들기: member 이하 | 403(SpaceRoleGuard — 스페이스는 이미 보이므로) |

### 16-2

```
POST   /api/spaces/:spaceId/channels                         { name, topic?, categoryId?, isPrivate? } (기존, admin+)
PATCH  /api/spaces/:spaceId/channels/:channelId              { name?, topic?, isPrivate? }            (기존, admin+)
GET    /api/spaces/:spaceId/channels/:channelId/members                       → 200 ChannelMemberView[] (새, 열람)
POST   /api/spaces/:spaceId/channels/:channelId/members      { userIds }      → 200 ChannelMemberView[] (새)
DELETE /api/spaces/:spaceId/channels/:channelId/members/:userId               → 204                    (새)
GET    /api/spaces/:spaceId/channels/:channelId/permissions                   → 200 RolePermission[]   (새, admin+)
PUT    /api/spaces/:spaceId/channels/:channelId/permissions/:role { canView, canSend } → 200          (새, admin+)
DELETE /api/spaces/:spaceId/channels/:channelId/permissions/:role             → 204                    (새, admin+)
```

`ChannelMemberView` 는 `{ userId, name, avatarUrl, role }` — 멤버 목록과 같은 모양의 사용자 칸.
`RolePermission` 은 `{ role, canView, canSend, explicit }` 를 **guest · member 두 줄** 로 늘 돌려준다
(행이 없으면 기본값 `true, true, explicit: false`).

| 조건 | 응답 |
|---|---|
| 볼 수 없는 채널 | 404 |
| 멤버 추가 · 제거 · 목록: 공개 채널 (목록은 공개 채널도 400) | 400 |
| 멤버 추가: 역할이 guest | 403 |
| 멤버 추가: 스페이스 멤버가 아닌 id 가 하나라도 있음 | 404(아무도 넣지 않는다 — §3-4) |
| 멤버 추가: `userIds` 가 비었음 · 50개 초과 | 400 |
| 남 제거: admin 미만 | 403 |
| 제거: 채널 멤버가 아님 | 404 |
| 제거: 마지막 한 명 | 409 |
| 권한: `:role` 이 admin · owner · 없는 값 | 400 |
| 권한: 비공개 채널에 `canView=false` | 400 |

### 실시간

| 이벤트 | 룸 | 페이로드 | 조각 |
|---|---|---|---|
| `member:joined` | 스페이스 | `{ spaceId, userId }` | 16-1 |
| `member:updated` | 스페이스 | `{ spaceId, userId, role }` | 16-1 |
| `member:left` | 스페이스 | `{ spaceId, userId }` | 16-1 |
| `space:removed` | 그 사용자 | `{ spaceId }` | 16-1 |
| `rooms:invalidate` | 사용자 · 스페이스 | `{ reason }` — `member.joined` · `member.left` · `channel.members` · `channel.permissions` 를 더한다 | 둘 다 |

`member:*` 는 사람 하나를 가리킬 뿐 내용을 싣지 않는다 — 앱은 멤버 목록을 다시 받는다.
`space:updated { spaceId }` 는 16-2 에서 더했다(D34) — 이름 · 스프린트 스위치가 바뀌면 스페이스 룸으로 온다.

## 2. 가시성 판정 — `channelAccess()`

`ChannelsService` 안의 판정을 순수 함수로 뺀다. `canView` · `canSend` · `viewableChannelIds` 가
전부 이것을 부른다(한 곳).

```ts
channelAccess({ isPrivate, isMember, perm }): { view: boolean; send: boolean }
// perm: 그 역할의 행 { canView, canSend } | null — admin · owner 는 늘 null(D21)

view = isPrivate ? isMember : (perm?.canView ?? true)     // D22 · D23
send = view && (perm?.canSend ?? true)
```

지금 코드와 다른 곳은 공개 채널에서 `isMember` 가 `view` 를 열지 않는다는 한 가지다(D23).

## 3. 앱

### 화면

| 화면 | 자리 | 조각 |
|---|---|---|
| 스페이스 만들기 · 초대 코드로 참여 | 스페이스 선택 화면 아래 두 버튼 · 레일 「+」 메뉴. 둘 다 다이얼로그(`NxDialog`) | 16-1 |
| 스페이스 메뉴 | 채널 판 머리 줄 이름 → `NxMenu` | 16-1 |
| 스페이스 설정 창 | `/s/:spaceId/settings/:section` — 일반 · 멤버 · 초대 | 16-1 |
| 초대하기 | 메뉴 「초대하기」는 설정 창 「초대」 섹션을 연다. 만들면 코드를 크게 보이고 복사 버튼 | 16-1 |
| 채널 만들기 | 카테고리 머리 「+」(admin+) → 다이얼로그 | 16-2 |
| 채널 설정 창 | `/s/:spaceId/c/:channelId/settings/:section` — 개요 · 멤버 · 권한 | 16-2 |
| 읽기 전용 입력창 | 대화 화면 입력창 자리 | 16-2 |

설정 창 섹션 목록은 **보일 섹션만** 싣는다 — 멤버(채널)는 비공개 채널에서만, 권한은
공개 채널 · admin+ 에서만, 일반 · 초대(스페이스)는 admin+ 에서만. 없는 섹션 주소로 들어오면
첫 섹션으로 돌린다.

### 반영

| 받은 것 | 앱이 하는 일 |
|---|---|
| `member:*` | `spaceMembersProvider` 무효화 |
| `space:removed` | `spacesProvider` 무효화 · `AppDatabase.purgeSpace(spaceId)`(채널 · 카테고리 · 메시지 · 이슈 · 스프린트 캐시와 그 스페이스의 큐) · 지금 그 스페이스면 `/spaces` + 토스트 |
| `rooms:invalidate` | 기존 그대로(룸 재계산 · 채널 목록 다시 받기) |

내 역할은 `currentSpaceProvider` 의 `role` 에서 읽는다(스페이스 목록 응답에 이미 있다).
역할이 바뀌면(`member:updated` 의 `userId` 가 나) 스페이스 목록도 다시 받는다.

### 실패 문구

| 실패 | 문구 |
|---|---|
| 초대 404 | 없는 초대 코드입니다 |
| 초대 400 | 만료됐거나 사용 한도가 찬 초대 코드입니다 |
| 채널 마지막 멤버 409 | 마지막 멤버는 나갈 수 없습니다 |
| 그 밖 | 기존 공통 문구(네트워크 · 알 수 없는 오류) |

## 5. 검증

### `check:members` (새 계약 검증)

자체 계정 셋(owner · admin · member)과 손님 하나로 스페이스를 만들어 쓴다.

- 16-1: 초대 만들기 · 목록(유효한 것만) · 취소 · 취소한 코드 수락 404 · 만료 · 소진 400 ·
  수락 시 `member:joined` · `rooms:invalidate` · 역할 변경 `member:updated` · 내보내기
  `space:removed` + `member:left` · **내보내진 소켓이 `rooms:sync` 를 부르지 않아도 그 스페이스의
  새 메시지를 받지 않는다**(D13a) · 나가기 · owner 나가기 403 · 다른 스페이스 초대 취소 404
- 16-2: 비공개 채널 멤버 추가(멱등 · 비멤버 id 404 · 손님 403 · 공개 400) · 추가된 사람의
  `rooms:invalidate` 와 채널 목록 등장 · 제거(본인 · 남 admin · 남 member 403 · 마지막 409) ·
  권한 행 쓰기 · admin 행 400 · 비공개 `canView=false` 400 · **읽어 본 공개 채널에서
  `canView=false` 가 채널을 가림**(D23 — 고치기 전 코드로 빨개지는지 본다) ·
  `canSend=false` 에서 전송 403 · 리액션 200 · 채널 목록 `canSend`

### 단위

- `channelAccess()` — 비공개/공개 × 멤버/아님 × 행 없음/가림/읽기 전용
- 초대 코드 읽기(앱) — 공백 · 문장째 · 코드만 · 짧은 문자열

### 앱

- 위젯 테스트: 설정 창 섹션 목록이 역할 · 채널 종류에 따라 줄고 는다 · 읽기 전용 입력창 ·
  메시지 메뉴에서 고정 · 답글이 빠짐 · 멤버 줄의 동작이 `outranks` 를 따른다
- `purgeSpace` 가 그 스페이스만 지운다(다른 스페이스 캐시 · 큐는 남는다)
- `app:flow` 에 스페이스 설정 창(멤버 · 초대 만들기) 을 더한다

### 화면 확인

Windows 에서 두 계정으로 — 하나가 만든 초대 코드로 다른 하나가 들어와 첫 메시지까지.
비공개 채널에 들이고 빼면 상대 화면의 채널 목록이 바로 바뀌는지. 슬라이스 경계에서 Android · 웹.
