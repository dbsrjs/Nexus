# 13 AI — 설계

> 2026-09-20. [12 저장소 인덱싱](2026-09-08-인덱싱-design.md) 이 만든 벡터
> 검색 위에 얹는다. **백엔드-설계 §8.2 의 Redis 큐는 12단계가 이미 뒤집었고**,
> 같은 §8.2 의 「runId + 소켓」은 그대로 따른다.

대화를 요약하고, 대화에서 이슈 초안을 뽑고, 저장소 코드에 질문한다.
**12단계가 앱을 한 줄도 고치지 않았던 것과 반대로, 이 단계는 세 기능 모두
화면까지 간다** — 7단계부터의 규율이다.

구현은 셋으로 자른다. 첫 슬라이스는 **대화 요약**이다 — RAG 가 빠져 있어
파이프라인 전체(큐 · 어댑터 · `runId` · 소켓 · 캐시 · 화면)를 가장 짧은
경로로 증명한다. 12단계 설정(임베딩 · 저장소 연결) 없이도 돌아간다.

| 슬라이스 | 내용 |
|---|---|
| 13-1 | LLM 어댑터 · 큐 · 소켓 · **대화 요약** (서버→화면) |
| 13-2 | **이슈 초안** — 구조화 출력(JSON) |
| 13-3 | **코드 질의** — RAG · 인용 · `search()` 의 모델 불일치 해소 |

## 0. 먼저 정한 것

### 임베딩 모델은 바꾸지 않는다

설계 도중 `Qwen3-Embedding-8B` 로의 교체를 검토했다. 품질 주장은 사실이다 —
네이티브 4096차원, MTEB multilingual 70.58 로 2025-06 기준 공개 모델 1위,
100개 이상 언어, MRL 로 32~4096 사이 임의 차원.

**그럼에도 이 PC 에서는 지금 바꾸지 않는다.** 근거 셋:

1. **4096차원은 pgvector 가 HNSW 로 색인하지 못한다.** 한계가 2000차원이다
   (인덱스 튜플이 8KB 페이지에 들어가야 한다). `halfvec` 로 4000까지 늘려도
   4096은 여전히 초과다. **MRL 로 잘라야만 쓸 수 있고**, 그러면 이 모델의
   강점인 4096차원 공간을 버린다. 768로 자르면 768차원 네이티브로 학습된
   `embeddinggemma` 와의 격차가 상당히 좁혀진다
2. **VRAM 12GB(RTX 5070)를 생성 LLM 과 나눠 쓴다.** `embeddinggemma` 는
   0.6GB 지만 Qwen3-8B 는 Q4_K_M 이 약 5GB 다. 코드 질의는 매 질의마다
   임베딩 → 생성 두 모델을 연속으로 쓰는데, 둘이 동시에 상주하지 못하면
   Ollama 가 질의마다 모델을 내리고 올려 수 초씩 까먹는다
3. **인덱싱 시간이 10~20배가 된다.** 그리고 모델을 바꾸면 전체 재인덱싱이
   강제된다(2026-09-17 빚 정리)

무엇보다 **현재 모델이 실패하고 있지 않다.** 진행 기록 «12 실제 태우기» 의
실측은 `embeddinggemma` 가 한국어 질의 4/4, 정답 0.52~0.62 vs 오답 0.13~0.27
로 간격이 충분히 벌어져 있음을 보여준다.

**13단계가 끝난 뒤 재검토한다.** 순서가 그렇다 — 생성 LLM 을 먼저 골라 GPU 에
올려 본 뒤 남는 VRAM 을 보고 정하는 것이 맞다. 그때의 현실적 후보는
`Qwen3-Embedding-0.6B`(네이티브 1024차원, MRL, VRAM 은 지금과 같다)다.

### 스트리밍을 넣지 않는다

로컬 LLM 은 첫 토큰까지가 빨라 스트리밍의 체감 이득이 크다. 그럼에도 넣지
않는 이유는 앱 규칙이다 — **「화면은 drift 만 구독한다」** 인데 토큰 델타를
매번 로컬 DB 에 쓸 수는 없고, 안 쓰면 화면이 두 공급원을 보게 된다. 그것은
6-1 에서 카테고리로 실제로 겪어 금지한 패턴이다(오프라인 진입 후 서버가
돌아와도 회복되지 않는 틈).

**뒤집을 여지는 남긴다.** 코드 질의의 답변이 길어 견디기 어려워지면 그때
`ai:run:delta` 와 함께 앱의 상태 보관을 다시 판단한다.

## 1. 모듈 구조

```
server/src/llm/                    EmbeddingModule 과 같은 자리
  llm.provider.ts                  LlmProvider 인터페이스 + LLM_PROVIDER 심볼
  llm.config.ts                    resolveLlm() — 설정 해석의 유일한 지점
  local-llm.provider.ts            Ollama /api/chat
  gemini-llm.provider.ts           generateContent
  fake-llm.provider.ts             계약 검증용. 결정적 출력
  llm.module.ts

server/src/ai/                     501 스텁을 지우고 다시 쓴다
  ai.controller.ts                 POST 셋 + GET 하나
  ai.service.ts                    적재 · 조회 · 권한 · 캐시 조회
  ai-queue.service.ts              lease · succeed · fail (12단계 복제)
  ai.worker.ts                     @Cron 30초 + kick()
  ai-runner.service.ts             kind 별 파이프라인 분기
  transcript.ts                    메시지 → 프롬프트 텍스트 (순수 함수)
  prompts/                         요약 · 이슈 초안 · 코드 질의 프롬프트
  dto/
```

`AiModule` 이 import 하는 것: `SpacesModule`(가드) · `MessagesModule`(본문 읽기 —
`MessagesService` 를 이미 export 한다) · `ReposModule`(검색) ·
`RealtimeEmitterModule`(소켓) · `LlmModule`.

**`ReposModule.exports` 에 `IndexingService` 를 더하는 것이 저장소 쪽 유일한
변경이다.** 단방향이라 순환이 없다 — repos 는 ai 를 모른다. 12단계가 이
자리를 미리 만들어 두었다(`IndexingService.search()` 의 주석과 `topK` 방어).

**`LlmModule` 을 `@Global` 로 두지 않는다.** 임베딩은 인덱싱과 AI 둘이 쓰지만
LLM 은 AI 만 쓴다. 전역이면 아무 데서나 부를 수 있게 되어 `ai_runs` 기록을
우회하는 경로가 생긴다.

## 2. 데이터 모델

`ai_runs` 는 이미 있고 `state: queued | running | done | failed` 까지 갖췄다.
**이 테이블이 곧 큐다** — 새 테이블을 만들지 않는다.

넷을 더한다:

| 컬럼 | 왜 |
|---|---|
| `input Json` | 무엇을 요약·질의하는지. `{channelId, messageIds}` · `{repoId, question, channelId?}` |
| `leaseUntil DateTime?` | 리스. 크래시 복구의 유일한 수단 |
| `attempts Int @default(0)` | `MAX_ATTEMPTS` 판정 |
| `startedAt DateTime?` | 진단용. 인덱싱 큐와 같은 모양 |

기존 `error` 를 `lastError` 대신 그대로 쓴다. 인덱스로 `@@index([state, createdAt])`
를 더한다 — `lease()` 가 이것으로 고른다.

### 인덱싱 큐와 다른 점 셋

12단계의 `IndexQueueService` 를 복제하되:

1. **합치지 않는다.** `enqueue` 는 언제나 `INSERT` 다(`ON CONFLICT` 없음).
   인덱싱은 저장소마다 한 행이라 합침이 구조였지만, AI 는 요청마다 한 행이고
   합치면 사용자가 두 번 물은 것이 한 번이 된다. 같은 요청의 재실행은 합침이
   아니라 `promptHash` 캐시가 맡는다
2. **리스가 짧다** — 10분 대신 **3분**. LLM 한 번이 그보다 오래 걸리면 뭔가
   잘못된 것이다. `renew()` 를 두지 않는다(배치 루프가 없어 갱신할 지점이 없다)
3. **`succeed()` 에 「그사이 바뀌었나」 판정이 없다.** 인덱싱은 도는 중에 push 가
   오면 `queued` 로 되돌렸지만, AI 요청의 입력은 적재 시점에 고정된다

### 반드시 가져오는 것

```ts
const UTC_NOW = Prisma.sql`(now() at time zone 'utc')`;
```

이 스키마의 시각 컬럼은 `timestamp without time zone` 이고 Prisma 는 거기에
UTC 를 쓰는데 `now()` 는 DB 로컬(KST)을 준다. 12단계에서 이것 때문에 리스가
한 번도 동작하지 않았다. `check:sql-time` 이 CI 에서 잡는다.

마이그레이션은 **`nexus-migration` 스킬 절차를 따른다** — `prisma migrate dev`
가 이 환경에서 거부되고, 자동 생성 SQL 이 pgvector HNSW 인덱스를 지운 전력이
넷 있다.

## 3. LLM 어댑터

`EmbeddingProvider` 를 그대로 베낀다. 이미 세 벌로 검증된 모양이라 새로 판단할
것이 없다.

```ts
export interface LlmMessage {
  role: 'system' | 'user';
  content: string;
}

export interface LlmResult {
  text: string;
  promptTokens: number | null;
  completionTokens: number | null;
  /** 실제로 응답한 모델. 설정값이 아니다 */
  model: string;
}

export interface LlmOptions {
  maxTokens: number;
  temperature: number;
  /** 구조화 출력. 이슈 초안에서만 쓴다 */
  json?: boolean;
}

export interface LlmProvider {
  /** `provider:model`. promptHash 에 섞는다 */
  readonly modelId: string;
  complete(messages: LlmMessage[], options: LlmOptions): Promise<LlmResult>;
}

export const LLM_PROVIDER = Symbol('LLM_PROVIDER');
```

**토큰 수를 모르면 `0` 이 아니라 `null`** — 판단 #2. `0` 은 "안 썼다"로 읽힌다.

`json: true` 는 Ollama 가 `format: 'json'`, Gemini 가 `responseMimeType:
'application/json'` 으로 각자 번역한다. **어댑터 밖으로 새지 않는다.**

### 설정

`resolveLlm()` 은 `resolveEmbedding()` 과 같은 규칙이다:

- 미설정이면 `null`. **서버는 정상 부팅하고 AI 만 503** 이다
- **모르는 이름은 던져 부팅을 멈춘다** — 없는 것("이 기능을 안 쓴다")과 잘못된
  것(설정 실수)은 다르다
- **빈 문자열을 미설정으로 친다**(`||`, `??` 가 아니다). `.env` 에 자리만 잡아
  둔 경우가 있다
- **기본 provider 를 두지 않는다.** `fake` 가 기본이면 운영에서 아무도 모르게
  가짜 답이 나온다

| 키 | 기본 |
|---|---|
| `LLM_PROVIDER` | 없음(미설정 = AI 꺼짐) |
| `LLM_MODEL` | local → `qwen2.5-coder:7b`, gemini → **구현 시점에 문서를 보고 정한다** |
| `LLM_BASE` | local → `http://127.0.0.1:11434` |
| `LLM_MAX_TOKENS` | 1024 |

API 키는 `GEMINI_API_KEY` 를 임베딩과 공유한다.

**gemini 의 기본 모델 이름을 이 문서에 박지 않는다.** 임베딩 쪽이
`gemini-embedding-001` 을 쓰는 것은 2026-09-10 에 문서를 직접 보고 정한
값이다. 생성 모델은 세대 교체가 잦아, 설계 시점에 적어 두면 구현할 때 이미
틀린 값이 된다 — `llm.config.ts` 를 쓰는 작업에서 문서를 확인해 정한다.

**`local` 의 기본을 `qwen2.5-coder:7b` 로 잡는 근거**는 VRAM 이다. Q4 가 약
4.7GB 라 `embeddinggemma`(0.6GB)와 함께 올려도 5.3GB 로 12GB 안에 둘이
상주한다. 주 용도가 코드 질의이고 한국어도 된다. **실제 태우기에서 뒤집힐 수
있는 값이다** — 요약 품질이 모자라면 `gemma3:12b` 쪽을 재본다.

## 4. `promptHash` 캐시

```
sha256(kind + '\0' + llm.modelId + '\0' + 조립된_프롬프트_전문)
```

**모델 ID 를 반드시 섞는다.** 모델을 바꿨는데 캐시가 옛 답을 주면 오류 없이
결과만 틀린다 — 임베딩에서 이미 겪은 종류의 실패다(2026-09-17 빚 정리).

**`spaceId` 는 해시에 넣지 않고 조회 `WHERE` 에 넣는다.** 테넌트 격리는 해시
충돌이 아니라 쿼리로 지켜야 한다.

적중하면 **새 행을 만들지 않고** 기존 `runId` 를 돌려준다. 응답은
`{ runId, state: 'done' }` 이라 앱은 소켓을 기다리지 않고 곧바로 `GET` 한다.

조회 조건: 같은 `spaceId` + 같은 `promptHash` + `state = 'done'`,
`createdAt` 내림차순 하나.

## 5. 실패 처리

12단계의 구분을 그대로 쓴다 — **네트워크 실패는 시도 횟수로 치지 않는다.**
오프라인은 오류가 아니다.

| 실패 | 시도로 세나 | 결과 |
|---|---|---|
| 네트워크 · Ollama 미기동 | ✗ | `queued` 로 돌려 60초 뒤 재시도 |
| 429 · rate limit | ✗ | `Retry-After` 만큼 미룸 |
| 5xx | ✓ | `MAX_ATTEMPTS`(3)까지 |
| 컨텍스트 초과 · JSON 파싱 실패 | ✓ **fatal** | 곧바로 `failed` |

fatal 을 두는 이유는 12단계의 401·404 와 같다 — **다시 걸어도 같은 실패는 세 번을
기다리지 않는다.** 같은 모델에 같은 프롬프트를 세 번 넣어 봐야 같은 것이 나온다.

**동시 실행은 프로세스당 하나다.** 인덱싱 워커의 `running` 플래그와 같은
모양이다. GPU 에 모델이 하나 올라가 있으므로 병렬로 불러 봐야 서로 기다린다.

**AI 가 실패해도 서버는 떠 있다.** 워커의 `try/catch` 가 12단계와 같다.

## 6. 메시지를 프롬프트에 넣는 법

요약(13-1)과 이슈 초안(13-2)이 같은 전처리를 쓴다. `transcript.ts` 의 순수
함수 하나이고, 서버 단위 테스트가 여기를 덮는다.

- **`<@userId>` 를 표시 이름으로 되돌린다.** 저장 형식 그대로 주면 LLM 이
  UUID 를 읽는다. 멘션된 멤버를 한 번에 조회해 `@이름` 으로 바꾼다.
  멤버가 아닌 id 는 `@(알 수 없음)` 으로 둔다
- **소프트 삭제된 메시지는 본문을 싣지 않는다**(판단 #5) — `(삭제된 메시지)` 로
  자리만 둔다
- **첨부는 파일명만.** 바이트를 LLM 에 보내지 않는다
- 형식은 `[HH:mm] 이름: 본문` 한 줄씩. **마크다운 원문을 그대로 둔다** —
  벗기면 코드블록만 망가진다
- **메시지 200개 상한.** 넘으면 400 이다. 조용히 자르지 않는다(판단 #4).
  화면이 먼저 막는다. 상한값은 9-1 의 컬럼 상한과 같은 200이다

## 7. 세 기능

### 7.1 대화 요약 (`summarize`, 13-1)

입력 `{ channelId, messageIds[] }` → 결과 `{ markdown: string }`.

프롬프트는 한국어로 셋을 뽑게 한다 — **무엇이 정해졌는가 · 누가 무엇을
맡았는가 · 남은 질문.** 결과는 마크다운이고 앱은 이미 가진 `MarkdownBody` 로
그린다.

**범위는 사용자가 고른 구간이다.** 「안 읽은 것부터」가 개인 프로젝트에 더
어울려 보이지만, 사람마다 범위가 달라 `promptHash` 캐시가 거의 안 맞고 공개
채널은 읽음 마커 행이 없을 수 있다(7-4 의 `LEFT JOIN` 이유와 같다). 선택은
9-2b 의 「대화 → 이슈」 가 이미 가진 UI 다.

**「채널에 붙이기」는 별개의 기존 API 다.** 앱이 받은 마크다운을 평범한 메시지
전송으로 보낸다. 서버에 새 경로를 만들지 않는다.

### 7.2 이슈 초안 (`draft_issue`, 13-2)

입력 `{ channelId, messageIds[] }` → 결과 `{ title, description, labelIds[] }`.

- `json: true` 로 구조화 출력을 받는다. **파싱 실패는 fatal**
- 라벨은 **스페이스의 기존 라벨 목록을 프롬프트에 주고 그중에서만 고르게** 한다.
  그래도 없는 id 가 오면 **버린다.** 9-2b 는 "없는 라벨 id 는 404" 였지만
  그것은 사람이 보낸 것이고, 이것은 초안이라 하나 때문에 전체를 잃게 하지
  않는다 — 판단 #4 의 "사람이 쓴 본문" 예외와 같은 성격이다
- **이슈를 만들지 않는다.** 제안만 돌려주고 사람이 9-2b 의 기존 생성 화면에서
  확인·수정한 뒤 만든다(판단 #7)

### 7.3 코드 질의 (`ask`, 13-3)

입력 `{ repoId, question, channelId? }` → 결과 `{ answer, citations[] }`.

```
question → embed(query) → IndexingService.search(topK=8)
        → 「경로:시작줄-끝줄」 머리말과 함께 청크를 프롬프트에 조립
        → LLM → answer
```

**`citations` 는 LLM 이 아니라 검색 결과에서 우리가 채운다** —
`{ path, startLine, endLine, commitSha }`. LLM 이 지어낸 경로가 링크가 되는
일을 원천 차단한다. 답변 본문의 인용 표기는 LLM 에게 맡기되, 화면이 거는
링크는 우리가 아는 청크만이다. 링크는 10-3a 의 파일 보기로 간다.

`channelId` 를 함께 주면 그 채널 최근 메시지도 프롬프트에 넣는다 — 기획서
§6-3 의 "맥락을 아는 AI" 다.

## 8. 「알려진 빚」 해소 — `search()` 의 모델 불일치

CLAUDE.md §5 가 *"13단계에서 AI 가 검색을 부르는 모양을 보고 정한다"* 로 미뤄
둔 것이다. **거절로 정한다.**

| `repo.indexedEmbeddingModel` | `search()` |
|---|---|
| 현재 provider 의 `modelId` 와 같음 | 정상 |
| 다름 | **503** — "임베딩 모델이 바뀌어 다시 인덱싱해야 합니다" |
| `null`(미인덱싱 · 전체 재인덱싱 중) | **503** — "인덱싱 중입니다" |

조용히 틀린 순위를 내놓는 것보다 못 한다고 말하는 쪽이 낫다(판단 #4). 전체
재인덱싱 중에 검색이 막히지만 **그 구간은 원래 답이 없는 구간이다.**

이 변경은 `IndexingService.search()` 안에서 일어나므로 12단계의
`POST .../index/search` 경로도 함께 엄격해진다. 의도한 것이다 — 두 경로가
다른 기준으로 답하면 안 된다.

## 9. API 계약

```
POST /api/spaces/:spaceId/ai/summarize      { channelId, messageIds[] }
POST /api/spaces/:spaceId/ai/draft-issue    { channelId, messageIds[] }
POST /api/spaces/:spaceId/ai/ask            { repoId, question, channelId? }
   → 202 { runId, state: 'queued' | 'done' }

GET  /api/spaces/:spaceId/ai/runs/:runId
   → { runId, kind, state, result, error, model,
       promptTokens, completionTokens, createdAt, finishedAt }
```

`SpaceGuard` 만 건다. **`@MinRole` 을 걸지 않는다**(판단 #9 — 읽기 라우트에
역할을 걸면 코드를 볼 사람과 설정을 바꿀 사람이 같아진다). 대신 서비스가
**채널 가시성을 직접 확인한다**: 비공개 채널이면 `channel_members` 에 있어야
하고, 아니면 **404**(403 이 아니다). `ask` 는 저장소가 그 스페이스 것인지 본다.

**권한의 무게**(판단 #9):

| 행위 | 권한 |
|---|---|
| 요약 · 이슈 초안 · 코드 질의 요청 | 채널·저장소 **열람** 권한. 읽을 수 있으면 요약할 수 있다 |
| 「채널에 붙이기」 | **전송** 권한. 모두에게 보이는 변경이다 |
| 「이 내용으로 이슈 만들기」 | `member`. 9-1 의 이슈 생성과 같다 |

뒤의 둘은 **기존 API 를 그대로 쓰므로 새로 만들 권한 검사가 없다.**

`GET runs/:runId` 는 **요청자 본인 것만** 돌려준다(`userId` 일치, 아니면 404).
같은 스페이스라도 남의 질문과 답을 읽을 이유가 없다.

LLM 미설정이면 POST 셋이 **503** 이다 — 임베딩 미설정 때 인덱싱이 멈추는 것과
같다.

DTO 는 전부 class-validator 다. 전역 파이프가 `forbidNonWhitelisted` 라 DTO 밖
필드는 400 으로 거부된다.

## 10. 소켓

```
ai:run:done  →  user:{userId} 룸에만
payload: { runId, kind, state: 'done' | 'failed' }
```

**결과 본문을 싣지 않는다.** 앱이 이벤트를 받고 `GET runs/:runId` 로 가져온다.
이유 둘: 코드 질의 답변이 길 수 있고, **소켓을 놓친 경우(재접속 · 다른 기기)와
받은 경우가 같은 코드 경로를 탄다.** 소켓 없는 환경의 폴링 경로도 그대로 이
`GET` 이다.

**실패도 같은 이벤트에 `state: 'failed'`** 로 온다. 이벤트를 둘로 나누면 앱이
둘 다 처리해야 한다.

`SocketEvent` 가 `sealed` 라 `features/realtime/socket_controller.dart` 의
`switch` 를 함께 고쳐야 한다. 의도된 동작이다.

## 11. 앱

**AI 실행 상태는 drift 에 넣지 않는다.** 「화면은 drift 만 구독한다」의
예외이고, 근거는 8-2 의 `attachment_draft.dart` 선례다 — 업로드 진행률도 캐시
대상이 아니라 Riverpod 컨트롤러가 들고 있다. AI 결과는 오프라인에서 만들 수
없고 일회성이라 캐시할 것이 없다. **「채널에 붙이기」로 메시지가 된 순간부터**
평범한 메시지로 drift 에 들어간다.

| 기능 | 진입 | 자리 |
|---|---|---|
| 요약 · 이슈 초안 | 채널에서 **메시지 선택 모드** → 「요약」 · 「이슈 초안」 | 9-2b 의 선택 UI 재사용 |
| 코드 질의 | 저장소 화면의 질문 입력줄 | 저장소가 셸 밖(덮어서 여는 곳)이라 그 안에 둔다(판단 #13) |

결과는 패널에 `MarkdownBody` 로 그리고 버튼을 단다 — 요약은 「채널에 붙이기」,
이슈 초안은 「이 내용으로 이슈 만들기」(기존 생성 화면을 채운 채로 연다).

**진행 중에는 스피너와 「취소」** 를 보인다. 취소는 `ai_runs` 를 `failed` 로
표시할 뿐 **LLM 호출을 실제로 끊지는 않는다** — 끊을 수 있는 척하지 않는다
(판단 #7). 화면 문구도 "중단했습니다"가 아니라 "결과를 기다리지 않습니다"다.

**서버 오류 문구를 화면에 그대로 쓰지 않는다.** 실패 종류만 받아 앱이 자기
문구를 쓴다(`ApiFailure` 규칙).

## 12. 검증

### `npm run check:ai` (새 계약 검증)

`fake` LLM provider 로 돈다 — **결정적 출력**이어야 캐시 적중을 검증할 수
있다. 자체 계정·스페이스를 만들어 쓰므로 시드 비밀번호가 필요 없다.

| 갈래 | 케이스 |
|---|---|
| 큐 | 적재 → 완료 · 리스 만료 뒤 복구 · 네트워크 실패는 시도로 안 셈 · 5xx 3회 뒤 `failed` · fatal 은 곧바로 `failed` |
| 캐시 | 같은 입력 재요청이 새 행 없이 같은 `runId` · **모델이 바뀌면 적중하지 않음** |
| 권한 | 비멤버 404 · 비공개 채널 404 · 남의 `runId` 404 · LLM 미설정 503 |
| 소켓 | `ai:run:done` 이 **요청자에게만** 도착 · 실패도 같은 이벤트 |
| 전처리 | `<@id>` → 이름 치환 · 삭제된 메시지는 본문 없음 · 201개 400 |
| 코드 질의 | 모델 불일치 503 · `indexedEmbeddingModel` null 503 · **`citations` 가 검색된 청크 밖으로 안 나감** |

`.env` 는 `check:indexing` 과 같은 것에 **`LLM_PROVIDER=fake` 가 더 필요하다.**
인덱싱 워커가 백그라운드로 도는 스크립트라, 호출 수를 재기 전에
`scripts/lib/indexing.mjs` 의 `settleIndexing()` 으로 조용하게 만든다.

**단언 규율**: 값이 있는지부터 단언한다. `undefined === undefined` 로 통과하는
사고가 10-2b·12 에서 두 번 있었다.

### 그 밖

- **서버 단위 테스트는 순수 로직만** — 프롬프트 조립 · `promptHash` 계산 ·
  `transcript.ts` 전처리 · `resolveLlm()` 분기. 실 DB 동작은 계약 검증이
  담당한다(CLAUDE.md §6 교훈)
- `check:sql-time` · `check:migrations` 가 CI 에서 자동으로 돈다
- 앱은 위젯 테스트 — 선택 모드에서 버튼이 뜨는지, 결과 패널이 마크다운을
  그리는지, 실패 문구가 서버 문구가 아닌지

### 실제 태우기

12단계가 그랬듯 **진짜 Ollama + `qwen2.5-coder:7b`** 로 세 기능을 완주한다.
`fake` 로는 프롬프트가 실제로 쓸모 있는지, GPU 12GB 에 임베딩과 생성이 함께
상주하는지, 한국어 요약 품질이 어떤지를 하나도 알 수 없다.

**확인할 것**: 두 모델 동시 상주 여부(`ollama ps`) · 요약 한 번의 실제 소요
시간 · 코드 질의의 인용이 실제로 맞는 파일을 가리키는지.
