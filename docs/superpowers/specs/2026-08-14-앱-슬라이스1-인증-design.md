## 1. 5단계를 네 조각으로 자른다

[앱-설계.md §11](../../앱-설계.md) 의 12단계를 한 스펙으로 잡으면 너무 크다. 화면이
보이는 지점을 기준으로 자른다.

| 슬라이스 | 내용 | 끝나면 보이는 것 |
|---|---|---|
| **1** ← 이 문서 | 스캐폴드 · 스택 배선 · 테마 · 라우터 · 인증 | **로그인해서 내 계정이 화면에 뜬다** |
| 2 | 스페이스 선택 + 반응형 셸 | 3단 레이아웃 껍데기 |
| 3 | 채널 목록 + 메시지 리스트/전송 (REST) | 대화가 보인다 |
| 4 | 소켓 연결 · 실시간 갱신 · catch-up | 상대가 보낸 메시지가 바로 뜬다 |

drift 캐시는 6단계라 여기 없다. 슬라이스 4까지 끝나면 5단계 완료다.

**자르는 기준은 "화면에 무언가 새로 보이는가"다.** 각 슬라이스는 끝났을 때 사람이
눈으로 확인할 수 있어야 한다. 서버 4단계에서 얻은 교훈 — 화면 없는 구간을 만들지
않는다 — 을 앱 안에서도 지킨다.

## 2. 개발·검증 플랫폼: Windows 데스크톱

> **2026-08-14 개정.** 원안은 6개 플랫폼을 전부 스캐폴드하는 것이었으나 **macOS 와
> Linux 를 뺐다** ([앱-설계.md §0](../../앱-설계.md)). 대상은 android · ios · windows ·
> web 4종이다. 그리고 아래 "Windows 데스크톱으로 검증한다"는 결정은 **실제로는
> 실행되지 못했다** — §2-1 참조.

스캐폴드는 android · ios · windows · web 4개 플랫폼을 만든다. 다만 **개발 중 눈으로
확인하는 루프는 Windows 데스크톱**으로 돌 계획이었다.

| | 이유 |
|---|---|
| 반복 속도 | 에뮬레이터 부팅이 없다 |
| 네트워크 | `127.0.0.1:3000` 이 그대로 붙는다. 네이티브라 CORS 가 무관하다 |
| 목표 화면 | 앱 설계 §4 의 3단 레이아웃이 데스크톱 기준이다 |
| 토큰 저장 | `flutter_secure_storage` 가 Windows 에서 wincred 로 동작한다 |

### 2-1. 실제로는 Chrome 으로 검증했다

**Windows 데스크톱 빌드가 되지 않았다.** 이 PC 에는 Visual Studio 2026(18.x)이 깔려
있는데 Flutter 3.38 이 그 버전을 몰라 CMake 제너레이터를 `Visual Studio 16 2019` 로
잡고 실패한다. `flutter doctor` 는 VS 를 정상 인식했다고 보고하므로 더 헷갈린다.

그래서 검증 루프를 **Chrome(`--web-port=5173`)** 으로 옮겼다. 그 포트를 고른 이유는
서버 `.env` 의 `CORS_ORIGINS` 가 이미 `http://localhost:5173` 을 허용하기 때문이다.

웹의 토큰 저장 전략(refresh 를 `HttpOnly` 쿠키로)은 **이번에도 만들지 않았다.**
앱이 `client: 'native'` 를 보내므로 서버가 두 토큰을 모두 응답 바디로 준다. 웹을
정식 대상으로 삼을 때 그 분기를 설계한다.

## 3. 무엇을 만드는가

폴더는 [앱-설계.md §3](../../앱-설계.md) 구조를 따르되 **이번에 쓰는 것만 만든다.**
빈 디렉터리를 미리 파 두지 않는다.

```
app/lib/
  main.dart                    ProviderScope 부트스트랩
  core/env.dart                --dart-define API_BASE. 기본 http://127.0.0.1:3000
  core/theme.dart              design-system/tokens.css 이식 (다크 · 라이트)
  core/router.dart             go_router + 인증 가드(redirect)
  data/api/dio_client.dart     dio + 401 → refresh 1회 재시도 인터셉터
  data/api/auth_api.dart       login · refresh · me
  data/auth_storage.dart       flutter_secure_storage 래퍼
  domain/models/user.dart      freezed + json_serializable
  domain/models/auth_tokens.dart
  features/auth/               로그인 화면 + Riverpod 컨트롤러
  features/home/               로그인 후 자리표시자 — /me 결과만 표시
```

### 이번에 넣지 않는 것

| 뺀 것 | 이유 |
|---|---|
| 회원가입 화면 | 시드 계정이 있다. 라우트 자리표시자만 둔다 |
| 반응형 셸 · 채널 · 메시지 | 슬라이스 2~3 |
| socket_io_client | 슬라이스 4 |
| drift | 6단계 |
| 웹 전용 토큰 경로 | §2 참조 |

### freezed 를 지금 넣는 이유

모델이 `User` · `AuthTokens` 둘뿐이라 당장은 손해다. 그래도 넣는다 — 앱 설계가 못박은
스택이고, 손으로 쓴 모델을 나중에 전환하는 비용이 지금 도입 비용보다 크다. 무엇보다
**이 슬라이스가 이후 모든 모델의 본보기가 된다.**

## 4. 테마 — 토큰을 그대로 옮긴다

`design-system/tokens.css` 는 이미 "Flutter `core/theme.dart` 는 이 파일의 토큰 이름을
그대로 따른다"고 적어 두었다. 그 약속을 지킨다.

- CSS 변수 이름을 Dart 상수 이름으로 1:1 옮긴다 (`--bg-surface` → `bgSurface`).
  이름이 갈라지면 디자인 시스템 문서와 코드를 대조할 수 없게 된다.
- **다크가 기본**이다. 토큰 파일이 다크를 `:root` 에 두고 라이트를 뒤집는 구조다.
- 폰트는 이번에 번들하지 않는다. `Pretendard` 가 없으면 시스템 폰트로 떨어지게 두고,
  폰트 자산은 화면이 여러 개가 될 때 넣는다.
- 간격·반경·모션 토큰도 함께 옮긴다. 값이 작아 지금 옮기는 비용이 거의 없고,
  나중에 화면을 만들 때마다 매직 넘버를 쓰게 되는 것을 막는다.

## 5. 인증 흐름

```
로그인 화면 ──dio POST /api/auth/login──→ { user, accessToken, refreshToken }
                                              │
                                              ├─→ flutter_secure_storage 에 저장
                                              └─→ authProvider 상태 갱신
                                                      │
                                          go_router redirect 가 /home 으로 보냄

앱 시작 ──secure storage 읽기──→ 토큰 있음? ──→ GET /api/me 로 확인 ──→ /home
                                    │                    │
                                    └─ 없음 → /login      └─ 401 → refresh 1회 → 실패 시 /login
```

### 규칙

- **`client` 필드를 `native` 로 보낸다.** 서버가 `web` 이 아니면 refresh 토큰을 응답
  바디로 준다 ([백엔드-설계.md §6](../../백엔드-설계.md)). 안 보내면 기본이 native 라
  동작은 같지만, 명시해 두면 웹 분기를 붙일 때 대비가 된다.
- **401 재시도는 1회뿐이다.** refresh 도 실패하면 저장된 토큰을 지우고 `/login` 으로
  보낸다. 무한 재시도는 서버의 재사용 탐지에 걸려 계정을 잠글 수 있다 — 서버가
  리프레시 토큰 재사용을 탐지하면 그 family 를 끊는다.
- **토큰은 절대 로그에 남기지 않는다.** dio 로거를 붙일 때 `Authorization` 헤더와
  응답 바디의 토큰 필드를 가린다.
- **API 주소는 `--dart-define`.** `core/env.dart` 의 `String.fromEnvironment` 한 곳에서만
  읽는다. 하드코딩 금지 — 옛 `www/api.js:6` 이 `localhost` 를 박아 실기기에서 연결
  불가였던 것이 이 규칙의 이유다.

### 오류 처리

| 상황 | 화면 |
|---|---|
| 잘못된 자격증명 (401) | 로그인 화면에 "이메일 또는 비밀번호가 올바르지 않습니다" |
| 서버 연결 불가 | 로그인 화면에 "서버에 연결할 수 없습니다" — **앱이 죽지 않는다** |
| 앱 시작 시 토큰 만료 | 조용히 `/login` 으로. 오류를 띄우지 않는다 (정상적인 만료다) |

서버 메시지를 그대로 노출하지 않는다. 서버는 한국어 메시지를 주지만 앱이 그것을
신뢰하면 서버 문구가 바뀔 때마다 앱 UX 가 흔들린다.

## 6. 검증

**Windows 데스크톱에서 실제로 띄워 확인한다.** 4단계에서 얻은 교훈 그대로 — 빌드가
통과한 것과 동작하는 것은 다르다 (CLAUDE.md §6).

| # | 케이스 | 확인하는 것 |
|---|---|---|
| 1 | `flutter analyze` | 정적 오류 0 |
| 2 | 시드 계정으로 로그인 | 이름·이메일이 화면에 뜬다 |
| 3 | 틀린 비밀번호 | 에러 문구가 뜨고 로그인 화면에 머문다 |
| 4 | **앱을 껐다 켠다** | 로그인 화면을 건너뛴다 (토큰 복원) |
| 5 | 서버를 끈 채 실행 | 앱이 죽지 않고 연결 실패를 표시 |
| 6 | 로그아웃 | 저장된 토큰이 지워지고 `/login` 으로 |

**4번이 이 슬라이스의 진짜 시험이다.** 저장 · 복원 · 라우터 가드가 전부 엮여야 통과한다.

자동화된 테스트는 이번에 두지 않는다. 위젯 테스트는 화면이 하나뿐이라 얻는 것이 적고,
`integration_test`(로그인 → 채널 진입 → 전송)는 슬라이스 3 이 끝나야 의미가 있다.
[앱-설계.md §10](../../앱-설계.md) 의 테스트 계획은 그때 착수한다. **이것은 빚이며,
슬라이스 3 에서 갚는다.**
