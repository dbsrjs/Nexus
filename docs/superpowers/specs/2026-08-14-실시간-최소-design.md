# 실시간 최소 (Socket.IO) — 설계

전환 계획 4단계. 2026-08-14.

관련 문서: [백엔드-설계.md §5](../../백엔드-설계.md) · [전환-계획.md](../../전환-계획.md)

---

## 1. 목적과 범위

Flutter 앱(5단계)이 REST 만 전제로 상태 계층을 짜지 않도록, **앱보다 먼저** 소켓
계약을 고정한다. 실시간을 뒤로 미루면 앱의 상태·캐시 계층을 다시 쓰게 된다 —
스레드·리액션처럼 나중에 붙여도 기존 코드를 안 건드리는 기능과 다르다.

**넣는 것**: 핸드셰이크 인증 · 룸 조인 · `rooms:sync` / `rooms:invalidate` ·
`message:new` · `message:edited` · `message:deleted` · 읽음 저장과 `read:synced`.

**빼는 것과 이유**:

| 뺀 것 | 이유 |
|---|---|
| `typing` | 화면이 없어 검증할 방법이 없다. 나중에 붙여도 기존 코드를 안 건드린다 |
| `presence:changed` | Redis 프레즌스가 전제. 위와 같은 이유 |
| `thread:*` 룸 | 스레드 기능(7단계)과 함께 |
| Redis 어댑터 | 단일 인스턴스. §6 참조 |

`message:edited` · `message:deleted` 는 원래 4단계 범위 밖이지만 넣는다. 배선이
`message:new` 와 동일해서 추가 비용이 사실상 없고, 빼면 앱이 수정·삭제를 따라가지
못해 5단계에서 이 파일들을 다시 열어야 한다.

## 2. 모듈 구조

```
src/realtime/
  realtime-emitter.ts          Server 참조를 들고 룸에 쏜다. 다른 의존성 없음
  realtime-emitter.module.ts   RealtimeEmitter 하나만 export
  rooms.service.ts             사용자 → 조인할 룸 목록 계산
  realtime.gateway.ts          핸드셰이크 인증 · 룸 조인 · rooms:sync · read
  realtime.module.ts
  dto/socket-read.dto.ts       소켓 페이로드 검증
```

### 순환 의존을 구조로 없앤다

`message:new` 는 `MessagesService` 가, `read:synced` 는 `ChannelsService` 가 쏴야
한다. 그런데 게이트웨이는 룸을 계산하려고 `ChannelsService.viewableChannelIds()` 를
쓴다. 게이트웨이를 그대로 주입하면 `ChannelsModule` ↔ `RealtimeModule` 순환이 된다.

**쏘는 쪽과 룸을 아는 쪽을 분리한다.** `RealtimeEmitter` 는 `Server` 참조와 룸 이름
헬퍼만 가진 의존성 없는 provider 다. 게이트웨이가 `afterInit` 에서 서버 참조를
넣어 준다.

```
RealtimeEmitterModule  ←── ChannelsModule      read:synced · rooms:invalidate
        ↑              ←── MessagesModule      message:new · edited · deleted
        │
RealtimeModule ────────→   ChannelsModule      viewableChannelIds · markRead
```

의존이 한 방향으로만 흐른다. `forwardRef` 도, `@nestjs/event-emitter` 같은 새
의존성도 필요 없다. 7단계에서 리액션·멘션이 붙을 때도 `RealtimeEmitter` 만
주입하면 된다.

**서버 참조가 아직 없을 때**: `RealtimeEmitter` 의 emit 메서드는 서버가 주입되기
전에 호출되면 조용히 무시한다(경고 로그 1회). 부팅 순서 때문에 요청이 실패하는
것보다 낫고, 실제로는 `afterInit` 이 첫 요청보다 항상 먼저다.

## 3. 인증

### 미들웨어에서 검증한다

`afterInit(server)` 에서 `server.use()` 로 붙인다. `handleConnection` 안에서
`disconnect()` 하면 클라이언트는 **이유 없이 끊긴 것만** 보지만, 미들웨어에서
`next(new Error('unauthorized'))` 를 하면 앱이 `connect_error` 로 이유를 받는다.
5단계 앱은 "토큰이 만료돼 재로그인" 과 "서버가 죽음" 을 구분해야 한다.

### 규칙

- **`handshake.auth.token` 만** 받는다. 옛 게이트웨이의 `Authorization` 헤더 ·
  `?token=` 쿼리스트링 경로는 삭제한다. 쿼리스트링은 액세스 로그·프록시 로그에
  토큰을 남긴다 ([백엔드-설계.md §5](../../백엔드-설계.md)).
- 시크릿은 `resolveJwtSecrets()` 한 곳에서 읽는다. 옛 게이트웨이의
  `config.get('JWT_SECRET') ?? config.get('JWT_ACCESS_SECRET')` 폴백은 제거한다.
- **검증은 핸드셰이크에서 한 번.** 액세스 토큰은 15분이지만 소켓은 그보다 오래
  붙어 있다. 주기적 재검증이나 `auth:refresh` 왕복은 두지 않는다 — 앱·서버 양쪽에
  상태가 늘고, 역할 변경은 `rooms:invalidate` 로 이미 반영된다. 재접속 시에는
  새 토큰이 필요하다.
- 소켓에 담는 것은 `{ userId }` 뿐이다. **역할은 담지 않는다** — 스페이스마다
  다르고, 박아 두면 역할 변경이 재접속 전까지 반영되지 않는다(가드와 같은 이유).

## 4. 룸

| 룸 | 조인 대상 |
|---|---|
| `user:{userId}` | 항상 |
| `space:{spaceId}` | 내가 멤버인 **모든** 스페이스 |
| `channel:{channelId}` | 각 스페이스에서 `viewableChannelIds()` 가 준 채널 전부 |

**연결 하나가 사용자의 전 스페이스를 담당한다.** 앱은 연결을 하나만 관리하고,
스페이스 전환에 재연결이 없으며, 보고 있지 않은 스페이스의 알림도 받는다. 비용은
`rooms:sync` 가 스페이스 수만큼 쿼리하는 것뿐이다.

### RoomsService

```ts
interface RoomSet {
  spaceIds: string[];
  channelIds: string[];
}

// 사용자의 SpaceMember 를 전부 읽고, 스페이스마다 viewableChannelIds(member) 를
// 돌려 합집합을 만든다. 가시성 규칙은 ChannelsService 한 곳에만 있어야 하므로
// 여기서 규칙을 복제하지 않는다.
computeRooms(userId: string): Promise<RoomSet>
```

**재조인은 차집합이 아니라 전체 교체로 한다.** 현재 조인한 방에서 **자기
`socket.id` 룸과 `user:` 룸을 뺀 나머지**를 전부 떠난 뒤 새 목록으로 조인한다.
(Socket.IO 는 연결마다 `socket.id` 와 같은 이름의 룸에 자동으로 넣는다. 이걸
떠나면 그 소켓에 개별 emit 을 할 수 없게 된다.) 차집합 계산은 상태가 어긋날
여지를 만들고, 스페이스 수가 한 자릿수인 개인 프로젝트에서 아낄 것이 없다.

## 5. 이벤트 계약

### 서버 → 클라이언트

| 이벤트 | 룸 | 페이로드 |
|---|---|---|
| `message:new` | `channel:{id}` | `{ spaceId, channelId, message }` |
| `message:edited` | `channel:{id}` | `{ spaceId, channelId, message }` |
| `message:deleted` | `channel:{id}` | `{ spaceId, channelId, messageId }` |
| `read:synced` | `user:{id}` | `{ spaceId, channelId, lastReadMessageId, lastReadAt }` |
| `rooms:invalidate` | `space:{id}` 또는 `user:{id}` | `{ reason }` |

`message` 는 REST 응답과 **같은 모양**이다. 앱이 소켓용 파서를 따로 두지 않게 한다.

### 클라이언트 → 서버

| 이벤트 | 동작 |
|---|---|
| `rooms:sync` | 룸 재계산 후 재조인 |
| `read` | `{ spaceId, channelId, lastReadMessageId }` → `ChannelsService.markRead()` |

**ack 은 두 이벤트 모두 같은 모양이다.** 성공이면 `{ ok: true, ... }`, 실패면
`{ ok: false, error }`. 앱이 분기를 한 번만 짜면 된다.

```
rooms:sync  → { ok: true, spaces: string[], channels: string[] }
read        → { ok: true }
실패         → { ok: false, error: string }
```

`rooms:sync` 가 ack 으로 룸 목록을 돌려주는 이유: 앱이 "지금 어떤 채널을 실시간으로
받고 있는지" 를 알아야 REST 로 다시 물어볼 대상을 정할 수 있다.

### rooms:invalidate 를 쏘는 지점

| 지점 | 대상 룸 | reason |
|---|---|---|
| 채널 생성 | `space:{spaceId}` | `channel.created` |
| 채널 수정 (`isPrivate` 변경 시에만) | `space:{spaceId}` | `channel.visibility` |
| 채널 join | `user:{userId}` | `channel.joined` |
| 멤버 역할 변경 | `user:{userId}` | `member.role` |

채널 수정은 `isPrivate` 가 실제로 바뀐 경우에만 쏜다. 이름·토픽 변경으로 전원이
룸을 다시 계산하게 만들 이유가 없다.

### 권한은 서버가 판단한다

클라이언트가 `read` 로 보낸 `channelId` 를 그대로 믿지 않는다. `markRead()` 가
`assertCanView()` 를 거치므로 볼 수 없는 채널이면 실패한다. 소켓 핸들러에서도
`SpaceMember` 를 DB 에서 읽어 넘긴다 — 소켓에 역할을 담지 않는 이유와 같다.

## 6. 미루는 것 — Redis 어댑터

단일 인스턴스이고 개발 PC 에 Redis 가 없다. `redis-io.adapter.ts` 는 `tsconfig` 의
`exclude` 에 남긴다.

인스턴스가 2개 이상이 될 때 `main.ts` 에서 어댑터만 갈아 끼우면 되고, **앱이 보는
계약은 바뀌지 않는다.** 지금 넣으면 검증할 수 없는 코드가 늘 뿐이다.

## 7. 오류 처리

| 상황 | 동작 |
|---|---|
| `auth.token` 없음 / 검증 실패 | `connect_error` 로 `unauthorized`. 연결 거부 |
| `read` 페이로드가 DTO 위반 | ack 으로 `{ ok: false, error }`. 연결은 유지 |
| `read` 대상이 볼 수 없는 채널 | 위와 같음. 연결을 끊지 않는다 — 룸이 낡았을 뿐일 수 있다 |
| `rooms:sync` 중 DB 오류 | ack 으로 `{ ok: false, error }`. 앱이 재시도 |

**잘못된 페이로드로 연결을 끊지 않는다.** 앱이 룸을 재계산하는 사이의 경합으로도
생길 수 있는 일이고, 끊으면 재연결 폭풍이 된다.

## 8. 검증

스텁이 아니라 **실제 DB + 실제 소켓**으로 확인한다 (CLAUDE.md §6). `socket.io-client`
를 devDependency 로 추가한다.

| # | 케이스 | 확인하는 것 |
|---|---|---|
| 1 | 토큰 없이 연결 | `connect_error` |
| 2 | 잘못된 토큰 | `connect_error` |
| 3 | 정상 연결 | `rooms:sync` ack 에 시드 채널 5개 |
| 4 | A 가 REST 로 전송 | **B 의 소켓에 `message:new` 도착** |
| 5 | B 가 볼 수 없는 비공개 채널에 전송 | B 에게 **안 감** (테넌트 격리) |
| 6 | 다른 스페이스의 사용자 | 그 스페이스 룸에 없다 |
| 7 | 소켓 `read` | `channel_members.last_read_at` 이 실제로 갱신됨 |
| 8 | 같은 사용자의 두 번째 소켓 | `read:synced` 수신 |
| 9 | REST `POST /read` | 소켓에도 `read:synced` 가 감 (두 경로가 같은 코드) |
| 10 | 채널 생성 | `rooms:invalidate` 수신 |
| 11 | 메시지 수정 · 삭제 | `message:edited` · `message:deleted` 도착 |

5번과 6번이 이 단계에서 가장 중요하다. 룸 계산이 틀리면 **다른 사용자의 메시지가
새는** 종류의 버그가 된다.
