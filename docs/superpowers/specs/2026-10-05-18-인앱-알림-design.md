# 18 인앱 알림 — 설계

> **✅ 완료(2026-10-05).** 경과는 [진행 기록](../../진행-기록.md) «18 완료».

> 2026-10-05. 출발점은 [제품 기획 §5.1-c](../../제품-기획.md) «18». 17단계로 DM 이 생겼다 — 이제
> 놓친 멘션 · DM · 내 글에 달린 답글이 한곳(알림함)에 모인다. 푸시 · 데스크톱 알림은 «마지막».

한 조각이다. 서버에서 화면까지 끝나야 완료다(CLAUDE.md §5).

## 0. 정한 것

### 무엇을 알리나

| # | 결정 | 이유 |
|---|---|---|
| N1 | 알림 종류는 넷 — **`mention`**(나를 직접 부름 `<@나>`) · **`broadcast`**(`@channel` · `@everyone`) · **`dm`**(DM 에 온 메시지) · **`reply`**(**내가 쓴 메시지**의 스레드에 달린 답글) | 제품 기획의 셋(멘션 · DM · 스레드 답글)에서 멘션을 둘로 나눴다. `@everyone` 은 가장 흔히 끄고 싶은 소리라 스위치를 따로 둔다(N9) |
| N2 | **메시지 하나는 받는 사람마다 알림 하나**다. 여러 이유가 겹치면 **`mention` > `dm` > `reply` > `broadcast`** 로 하나를 고른다. 고른 종류가 꺼져 있으면 다음 것으로 내려간다 | DM 에서 나를 부르고 내 글의 답글이기까지 하면 세 줄이 뜨는 것은 소음이다. 순서는 「나만 겨냥했는가」의 순서다 |
| N3 | **자기 글은 알리지 않는다.** 받는 사람은 **그 채널을 지금 볼 수 있는 사람**과의 교집합이다(판정은 `ChannelsService` — §3-판단 · 16단계 검토) | 비공개 채널 밖의 사람을 멘션해도 그 사람의 알림함으로 본문이 새면 안 된다. 멘션 행(7-4)은 지금처럼 만들어지지만 뱃지는 볼 수 있는 채널만 센다 — 알림도 같은 규칙 |
| N4 | `reply` 의 받는 사람은 **부모 메시지 작성자 한 명**이다. 스레드에 참여한 다른 사람은 받지 않는다 | 제품 기획 «내 메시지의 스레드 답글». 참여자 전원에게 보내는 것(구독)은 따로 끄고 켜는 장치가 있어야 소음이 아니다 — 범위 밖(§5) |
| N5 | 알림은 **메시지 생성 때만** 만든다. 수정으로 멘션이 더해져도 만들지 않는다 | 멘션 행(7-4)도 수정 때 다시 만들지 않는다. 같은 규칙을 둔다 |
| N6 | 알림 행은 **메시지 · 멘션과 같은 트랜잭션**에서 만든다. 소켓은 커밋 뒤에 쏜다 | §3-11. 메시지만 남고 알림이 빠지면 재시도로도 낫지 않는다 |

### 음소거 · 스위치

| # | 결정 | 이유 |
|---|---|---|
| N7 | **음소거한 채널은 `mention`(직접 멘션)만 알린다.** `broadcast` · `dm` · `reply` 는 만들지 않는다 | 14단계 D17 이 「나를 부른 멘션은 음소거해도 남긴다」로 정했다(디스코드와 같다). 음소거한 DM 은 DM 알림이 오지 않는다 — 사람이 고른 것이다 |
| N8 | 막는 것은 **만들 때**다. 나중에 음소거하거나 스위치를 꺼도 이미 온 알림은 남는다 | 알림함은 「그때 일어난 일」의 기록이다. 끈 뒤에 지난 것까지 사라지면 놓친 것을 다시 찾을 길이 없다 |
| N9 | 스위치는 **종류마다 하나씩 넷**이고 **사용자 단위**다(스페이스마다가 아니다). `users` 에 `notify_mentions` · `notify_broadcast` · `notify_dms` · `notify_replies` 네 컬럼(기본 켜짐) | 설정 창(14단계)은 사용자 설정이다. 스페이스마다 다르게 고르는 것은 «알림 세분화 설정»(제품 기획 §5.2) 몫 |
| N10 | `GET /api/me/notification-settings` · `PATCH /api/me/notification-settings` — 부분 갱신, 응답은 넷 다 | 스위치 하나를 누를 때 나머지를 몰라도 된다. 저장은 멱등 |

### 읽음

| # | 결정 | 이유 |
|---|---|---|
| N11 | 알림은 **자기 `read` 를 갖는다.** 멘션 뱃지(7-4)는 **그대로 집계로 둔다** — 알림함이 대체하지 않는다 | 뱃지는 「이 채널에 안 읽은 멘션」(읽음 위치 기준)이고 알림함은 「내가 볼 일」이다. 뱃지를 알림 테이블로 옮기면 음소거 · 스위치가 뱃지까지 끄게 된다 — 14단계 D17 과 어긋난다 |
| N12 | **채널을 읽으면 그 채널의 알림이 따라 읽힌다** — 읽음 위치(`markRead`)가 움직이면 그 채널의 **최상위 메시지** 알림 중 그 시각까지의 것을 읽음으로. 스레드 답글의 알림은 ~~알림함에서 누르거나 「모두 읽음」으로만 읽힌다~~ → **스레드를 열면 읽힌다**(2026-10-11 뒤집음 — 읽고 답까지 했는데 배지가 남았다. [진행 기록](../../진행-기록.md) «메시지 수정 · 삭제 · 스레드 알림 읽음») | DM 을 열어 다 읽었는데 알림함에 「안 읽음」이 남으면 거짓말이다. 스레드는 읽음 위치가 없다(7-2) — 채널을 읽었다고 답글을 읽은 것은 아니다 |
| N13 | `POST .../notifications/:id/read` · `POST .../notifications/read-all` — 둘 다 멱등. 남의 알림 · 없는 id 는 404 | 알림 하나를 누르면 그것만, 「모두 읽음」은 그 스페이스 전부 |
| N14 | 읽음이 바뀌면 **내 기기 전부**에 `notification:read { spaceId, ids }` (`ids: null` = 그 스페이스 전부) | 휴대폰에서 읽은 것이 데스크톱 뱃지에 남지 않게. `read:synced` 와 같은 자리(사용자 룸) |

### 보이기

| # | 결정 | 이유 |
|---|---|---|
| N15 | `GET /api/spaces/:spaceId/notifications?cursor&limit` — 최신순 커서 페이지 · **지금 볼 수 없는 채널의 알림은 빼고** 준다. `unread-count` 도 같은 규칙 | 비공개 명단에서 빠지면 그 채널의 알림 본문도 더는 보이면 안 된다. 행은 지우지 않는다 — 다시 들어오면 다시 보인다 |
| N16 | 알림 한 줄은 **본문을 저장하지 않고 읽을 때 메시지에서 꺼낸다** — `{ id, type, read, createdAt, channelId, messageId, threadId, actor, channel, body, deleted }`. 소프트 삭제된 메시지는 `body: ''` · `deleted: true` | 사본을 두면 수정 · 삭제를 따라가야 한다(§3-1). 삭제된 본문을 알림함이 흘리면 소프트 삭제의 뜻이 없다(§3-5) |
| N17 | 그래서 `notifications` 에 **`channel_id` · `message_id` · `actor_id` 컬럼**을 더한다(`payload` 는 쓰지 않는다). 인덱스 `(user_id, space_id, created_at)` · `(channel_id)`(기존 `(user_id, read)` 는 둔다) | 볼 수 있는 채널로 거르고(N15) 채널을 읽을 때 따라 읽히려면(N12) JSON 안이 아니라 컬럼이어야 한다. 메시지는 소프트 삭제라 FK 가 끊기지 않는다 |
| N18 | 새 알림은 **받는 사람의 사용자 룸**에 `notification:new { spaceId, notification }` — 목록 응답과 같은 모양 | 받는 사람마다 따로 쏜다. 내용은 같지만 받는 사람이 다르다 — 스페이스 룸에 실으면 남의 알림이 보인다(§3-6) |

### 앱

| # | 결정 | 이유 |
|---|---|---|
| N19 | 알림함은 **셸 안 `/s/:spaceId/notifications`**. 채널 판의 「작업」 맨 위 **「알림」 + 안 읽은 수 뱃지**, 모바일은 아래 탭에 「알림」(수) | 자주 들르는 곳이다 — 파일 · 이슈 보드와 같은 자리(§3-13). 모바일에서 판 안에만 두면 수가 안 보인다 |
| N20 | **캐시하지 않는다**(drift 에 넣지 않는다). 목록은 REST, 수는 REST 처음 값 + 소켓 | 파일 목록(8)과 같은 판단 — 읽기 전용 색인이고 진실(볼 수 있는지 · 읽음)이 서버에 있다. 오프라인이면 알림함은 「연결되면 보입니다」, 대화는 캐시로 그대로 읽힌다 |
| N21 | 한 줄을 누르면 **읽음으로 바꾸고 그 자리로 간다** — 최상위 메시지면 채널, 답글이면 스레드 | 「보러 간다」가 곧 「읽었다」다 |
| N22 | 줄 모양: 작성자 아바타 · 「가나 님이 #개발 에서 멘션했습니다」 같은 한 줄 · 본문 두 줄(평문화, 멘션은 이름으로) · 시각. 안 읽은 줄은 앞에 점 | 자체 UI 규칙(15단계) — 줄 앞 장식 아이콘 없이, 뜻이 있는 표시(안 읽음 점)만 |
| N23 | 설정 창 «알림» 맨 위에 **스위치 넷**(N9), 그 아래 기존 채널 음소거. 음소거 설명을 지금 효과로 고친다 — 「…안 읽음 표시와 알림이 꺼집니다. 나를 부른 멘션은 그대로 알립니다」 | 14단계 D17 이 「알림을 막는 효과는 18단계가 더한다」고 남겨 둔 자리 |

## 1. API

```
GET   /api/spaces/:spaceId/notifications?cursor=&limit=   → { items: NotificationItem[], nextCursor }
GET   /api/spaces/:spaceId/notifications/unread-count     → { count }
POST  /api/spaces/:spaceId/notifications/:id/read          → 200 NotificationItem   (멱등)
POST  /api/spaces/:spaceId/notifications/read-all          → 200 { count }          (이번에 읽음으로 바뀐 수)
GET   /api/me/notification-settings                        → { mentions, broadcast, dms, replies }
PATCH /api/me/notification-settings   { mentions?, broadcast?, dms?, replies? } → 같은 모양
```

```ts
NotificationItem = {
  id, type: 'mention' | 'broadcast' | 'dm' | 'reply', read, createdAt,
  channelId, messageId,
  threadId: string | null,              // 답글이면 부모 id — 앱이 스레드로 연다
  actor: { id, name, avatarUrl },       // 메시지 작성자
  channel: { name, kind: 'text' | 'dm' },
  body: string,                          // 지금 본문. 삭제됐으면 ''
  deleted: boolean,
}
```

| 조건 | 응답 |
|---|---|
| 읽음: 남의 알림 · 다른 스페이스의 id · 없는 id | 404 |
| 읽음: 지금 볼 수 없는 채널의 알림 | 404(목록에도 없다) |
| 설정: 불리언이 아닌 값 · 모르는 필드 | 400 |

### 실시간

| 이벤트 | 룸 | 페이로드 |
|---|---|---|
| `notification:new` | 받는 사람 | `{ spaceId, notification: NotificationItem }` |
| `notification:read` | 본인(모든 기기) | `{ spaceId, ids: string[] \| null }` — `null` 은 그 스페이스 전부 |

## 2. 고르기 — 순수 함수 하나

```ts
pickNotificationType(reasons, prefs, muted): NotificationType | null
  // reasons: { mention, broadcast, dm, reply } — 이 사람이 이 메시지를 받을 이유
  // 순서 mention > dm > reply > broadcast, 꺼진 종류는 건너뛴다(N2),
  // 음소거면 mention 만(N7)
```

받는 사람 후보 = 직접 멘션 ∪ (`@channel`·`@everyone` 이면 그 채널을 볼 수 있는 사람 전원) ∪ (DM 이면 상대)
∪ (답글이면 부모 작성자) − 작성자, 그리고 **볼 수 있는 사람과 교집합**(N3).

## 4. 검증

- **`npm run check:notifications`** — 멘션 · `@everyone` · DM · 답글이 각각 알림이 됨 · 자기 글은 없음 · 겹치면 하나(우선순위) ·
  비공개 채널 밖 사람을 멘션해도 없음 · 음소거면 직접 멘션만 · 스위치 끄면 그 종류 없음(다음 종류로 내려감) ·
  소켓 `notification:new` 는 받는 사람에게만 · 목록 · 수 · 읽음 · 모두 읽음 · 남의 알림 404 · 채널을 읽으면 따라 읽힘(답글은 아님) ·
  명단에서 빠지면 목록 · 수에서 빠짐 · 삭제된 메시지는 본문 없음 · `notification:read` 가 내 다른 소켓에
- 서버 단위: `pickNotificationType`
- 앱: 위젯 테스트(줄 문구 · 안 읽음 점 · 누르면 읽음 · 빈 화면) · 설정 스위치
- 새 ★ 케이스는 코드를 되돌려 빨개지는지 본다(CLAUDE.md §5 빚)

## 5. 범위에서 뺀 것

| 뺀 것 | 이유 |
|---|---|
| 푸시 · 데스크톱(OS) 알림 | «마지막» 단계 |
| 스레드 구독(참여자 전원에게 답글 알림) | N4 |
| 스페이스마다 · 채널마다 다른 스위치 | 제품 기획 §5.2 «알림 세분화 설정» |
| 다른 스페이스의 안 읽은 알림 표시(레일의 점) | 지금 스페이스의 수만 보인다. 여러 스페이스를 오가는 사람이 늘면 |
| 이슈 배정 · 이슈 댓글 알림 | 제품 기획 «18» 범위 밖. 종류는 문자열이라 더하기 쉽다 |
| 오래된 알림 지우기(보관 기간) | 무기한 보관이 제품 특성이다. 쌓여 느려지면 그때 |
| 알림 하나 지우기 · 안 읽음으로 되돌리기 | 읽음으로 충분하다 |
