# 10-2 — GitHub OAuth 설계

> 2026-08-20. 10단계 전체의 자르기는 [저장소 연동 설계](2026-08-20-저장소-연동-design.md),
> 계약은 [백엔드 설계 §7.1 · §4](../../백엔드-설계.md).
> 이 문서는 **계약이 정하지 않은 것**과 **거기서 갈라진 것**만 적는다.

---

## 0. 자르기 — 한 조각이 끝나면 화면에 뭔가 보인다

| 조각 | 끝나면 보이는 것 |
|---|---|
| **10-2a** | 저장소 화면 상단에 **"GitHub 연결됨 @계정"**(아바타 · 해제) |
| **10-2b** | 내 저장소를 **골라 채널에 붙이면 웹훅이 저절로 걸린다** |

계층(서버 전부 → 앱 전부)이 아니라 **기능 축**으로 잘랐다. 9-3 에서 서버 API 를
다 만들어 놓고 화면을 빠뜨린 채 완료로 보고한 일이 있었고, 계층으로 자르면
그 구멍이 구조적으로 다시 생긴다.

**10-1 의 수동 등록 경로는 지우지 않는다.** 설계 §7.1 이 말하는 "웹훅을 등록할
수 없는 환경"의 대비책이고, `PUBLIC_BASE_URL` 이 없을 때의 유일한 길이다.

## 1. OAuth App 인가 GitHub App 인가

**OAuth App 을 쓴다.**

| | OAuth App (택함) | GitHub App |
|---|---|---|
| 웹훅 | 저장소마다 **우리가** 건다 → URL·시크릿이 repo 별로 갈리는 **10-1 구조 그대로** | 앱 하나에 URL·시크릿 하나 → 10-1 의 `repoId` 별 경로를 뜯어야 한다 |
| 토큰 | 만료되지 않는다 → **갱신 경로가 없다** | 설치 토큰 1시간 · 사용자 토큰 8시간 → 갱신 경로가 필요하다 |
| 권한 | `repo` 하나. **거칠다** | 저장소 단위 · 세밀하다 |

보안은 GitHub App 이 낫다. 그런데 그 이점을 얻는 대가가 **이미 만들어 검증까지
끝낸 10-1 을 뜯는 것**이라, 지금 단계에서는 값이 맞지 않는다. 저장소별 시크릿
모델을 유지하는 쪽을 골랐다.

**scope 는 `repo` 하나다.** 비공개 저장소 조회와 웹훅 관리(`admin:repo_hook`)가
여기 포함된다. 좁히려면 공개 저장소만 다루는 `public_repo` 로 갈 수 있지만,
그러면 비공개 저장소를 붙일 수 없다.

## 2. 콜백을 앱으로 되돌리는 법

**서버가 끝내고 소켓으로 알린다.** 앱은 브라우저를 열기만 한다.

```
앱     ──POST /api/me/connections/github/start──▶ 서버   { authorizeUrl }
앱     ──authorizeUrl 을 시스템 브라우저로 열기──▶ GitHub
GitHub ──GET /api/auth/github/callback?code=&state=──▶ 서버
           서버: state 검증 → 토큰 교환 → GET /user → oauth_accounts upsert
           서버 ──oauth:connected──▶ room.user(userId) ──▶ 앱
           서버 ──"닫아도 됩니다" HTML──▶ 브라우저
```

딥링크(`nexus://`)를 쓰지 않은 이유는 **플랫폼마다 설정이 다르기 때문**이다 —
Android 는 intent-filter, Windows 는 레지스트리 프로토콜 등록, Web 은 아예 다른
경로(팝업 + `postMessage`)다. 검증 플랫폼이 셋이라 같은 것을 세 번 만들게 된다.
이 방식은 **플랫폼별 설정이 0** 이고, `room.user(userId)` 개인 룸이
`realtime.gateway.ts:97` 에 **이미 있어서** 새로 만들 것도 없다.

**콜백 실패는 HTML 로만 말한다.** `state` 가 틀렸거나 토큰 교환이 실패하면
브라우저에 오류 페이지를 그리고 소켓으로는 아무것도 보내지 않는다. 앱은 연결
전 상태 그대로 남고, 사람이 다시 시도하면 된다. 실패를 앱까지 밀어 넣으려면
"실패했다"를 누구에게 보낼지 정해야 하는데, `state` 가 깨진 경우에는 그 누구가
누구인지조차 알 수 없다.

**HTML 은 서버가 문자열로 그린다.** 템플릿 엔진을 들이지 않는다 — 페이지가
둘(성공 · 실패)뿐이다.

---

## 3. `state` — 저장하지 않고 서명한다

CSRF 방어용 `state` 에 **`userId` · 용도 · nonce 를 담아 5분짜리 JWT 로 서명**한다.
DB 에도 메모리에도 두지 않는다.

- Redis 가 없다. DB 에 5분짜리 행을 만들면 **청소가 숙제로 남는다**
- 서명 인프라는 이미 있다(`src/config/jwt.config.ts`)
- 콜백은 `@Public()` 이라 요청자가 누구인지 알 방법이 `state` 밖에 없다

`nonce` 는 같은 사용자가 연달아 시작해도 `state` 문자열이 겹치지 않게 하는
값일 뿐이다 — **저장하지 않으므로 일회용을 강제하지는 않는다.**

**대가: 같은 `state` 로 두 번 올 수 있다.** 무상태라 일회용을 강제하지 못한다.
다만 `state` 는 `code` 와 함께 와야 하고 **GitHub 이 `code` 재사용을 거부**하므로,
두 번째 요청은 토큰 교환에서 실패한다. 실질 피해가 없어 감수한다.

**용도(`purpose`)를 반드시 넣는다.** 안 넣으면 액세스 토큰을 `state` 자리에
그대로 넣는 공격이 성립한다 — 같은 시크릿으로 서명된 유효한 JWT 이기 때문이다.

## 4. 토큰 보관

`oauth_accounts.access_token` 은 **AES-256-GCM 으로 암호화**해 넣는다. 스키마
주석이 이미 그렇게 약속하고 있다.

- 키는 **전용 env `OAUTH_TOKEN_KEY`**(32바이트, base64url). `JWT_SECRET` 에서
  파생하지 않는다 — 시크릿 하나가 두 용도를 겸하면 **JWT 를 회전하는 순간
  저장된 GitHub 토큰이 전부 못 읽히게 된다**
- **키가 없으면 부팅은 되고 연결 시도만 503.** `JWT_SECRET` 과 다르게 다루는
  이유는 범위다 — JWT 가 없으면 시스템 전체가 성립하지 않지만, OAuth 가 없어도
  대화 · 이슈 · 첨부는 전부 돈다. 저장소를 안 쓰는 사람까지 부팅을 막을 이유가 없다
- **복호화 실패는 "연결 없음"으로 취급한다.** 키를 바꾸면 옛 토큰을 못 읽는데,
  그때 500 을 내면 사용자가 할 수 있는 일이 없다. "다시 연결해 주세요"로 떨어뜨린다

**토큰은 어떤 응답에도 실리지 않는다.** 연결 목록은 `provider · login ·
avatarUrl · connectedAt` 만 준다(설계 §7.3 — 클라이언트에 provider 토큰을 절대
내려보내지 않는다).

---

## 5. 연결 해제의 뜻

`DELETE /api/me/connections/github` 는 **내 토큰을 지우는 일이지 연동을 끝내는
일이 아니다.** 이미 걸린 웹훅은 그대로 둔다.

훅은 GitHub 쪽 저장소에 걸려 있고 시크릿도 우리 것이라, 지우면 **이벤트가
끊긴다** — 채널에 커밋이 안 뜨는 것이 "계정 연결을 해제했다"의 결과여서는
안 된다. 연동을 끝내려면 저장소를 지우면 된다(§7).

해제 후에 안 되는 것: 저장소 목록 조회 · 훅 재등록 · 훅 삭제. 다시 연결하면
곧바로 된다.

## 6. 저장소 목록

```
GET /api/me/github/repos?page=
```

**DB 에 두지 않고 프록시한다**(설계 §7.3). 내가 가진 저장소 목록은 GitHub 이
원본이고, 사본을 두면 동기화가 곧바로 숙제가 된다.

`GET /user/repos?sort=updated&affiliation=owner,collaborator,organization_member`
를 감싼다. 페이지는 GitHub 의 page 번호를 그대로 노출한다 — 커서를 새로 만들
이유가 없다.

**서버에 검색을 두지 않는다.** `/user/repos` 에는 검색 파라미터가 없고, 검색은
`/search/repositories` 라는 **다른 API** 다. 그쪽은 rate limit 이 따로 걸리고
(인증 상태에서 분당 30회) **`permissions` 를 주지 않아 `canWebhook` 을 채울 수
없다** — 즉 검색 결과와 목록 결과의 모양이 달라진다. 앱이 받아 온 페이지 안에서
이름으로 거르는 것으로 충분하다(`per_page=100`).

저장소가 100개를 넘겨 이 방식이 답답해지면 그때 `/search/repositories` 를 붙인다.
그 시점에는 `canWebhook` 을 모르는 항목을 어떻게 그릴지 함께 정해야 한다.

응답은 필요한 것만 준다.

```
{ id, fullName, private, defaultBranch, pushedAt, canWebhook }
```

**`canWebhook` 을 함께 준다.** GitHub 저장소에 admin 권한이 없으면 훅을 걸 수
없는데(`permissions.admin`), 그걸 모르고 고르면 **눌러 봐야 403** 이다. 앱이
회색으로 그려 고를 수 없게 한다 — 눌러 봐야 실패하는 버튼은 없느니만 못하다
(7-5 에서 답글 고정을 시트에서 감춘 것과 같은 판단).

**429 는 그대로 전달하되 `Retry-After` 를 붙인다**(설계 §7.3).

## 7. 웹훅 자동 등록

```
POST   /api/spaces/:spaceId/repos/connect          @MinRole('admin')
POST   /api/spaces/:spaceId/repos/:repoId/webhook  재등록 · 주소 갱신
DELETE /api/spaces/:spaceId/repos/:repoId          (기존) + GitHub 훅 삭제
```

**`connect` 를 기존 `POST /repos`(수동 등록)와 합치지 않는다.** 한 자원의 두
생성 방법이지만 요청 필드도(숫자 id vs `소유자/이름`), 응답도, 실패 조건도
다르다. 특히 **수동은 `webhookSecret` 을 돌려줘야 하고**(사람이 GitHub 설정에
붙여야 하니) **자동은 돌려줄 이유가 없다** — 한 엔드포인트에 넣으면 "언제
시크릿이 실리는가"가 요청 모양에 따라 달라진다. 10-1 코드를 건드리지 않는 것도
이점이다.

쓰기 권한은 10-1 과 같은 `admin` 이다. 저장소를 채널에 붙이는 것은 **그 채널에
남의 서비스가 글을 쓰게 하는 일**이라 스페이스의 뼈대를 바꾸는 쪽에 가깝다.

### 순서 — DB 가 먼저, GitHub 이 나중

훅 URL 에 `repoId` 가 들어가므로 DB 행이 먼저 있어야 하고, 외부 호출을
트랜잭션 안에 넣을 수도 없다(느리고, 롤백해도 GitHub 쪽은 안 돌아온다).

1. `PUBLIC_BASE_URL` 이 비어 있으면 **400** — 자동 등록만 거부하고 수동 경로를 안내한다
2. 트랜잭션: `repos` 행 생성 + `webhookSecret` 발급
3. `POST /repos/{owner}/{repo}/hooks` — `url = {PUBLIC_BASE_URL}/api/webhooks/github/{repoId}`,
   `content_type: json`, `secret`, `events: [push, pull_request]`
4. 성공하면 `webhook_external_id` 저장

**3이 실패해도 행을 지우지 않는다.** `webhookExternalId = null` 로 남기고 화면에
"웹훅 등록 실패 · 다시 걸기"를 띄운다. 지우면 사용자가 재시도할 대상이 사라지고
수동으로 붙일 길도 막힌다.

> 8-1 은 "스토리지에 먼저 쓰고 DB 를 나중에 쓴다"였다. 방향이 반대인데 **이유는
> 같다 — 되돌릴 수 없는 쪽이 나중이어야 한다.** 8-1 에서 되돌릴 수 없는 쪽은
> 파일 바이트였고, 여기서는 남의 서비스에 남긴 훅이다.

`content_type` 을 `json` 으로 박는 것이 중요하다. GitHub 기본값은 `form` 이고,
그러면 **서명이 맞지 않는다**(10-1 에서 실제로 겪었다).

### 수동으로 붙인 저장소와 겹칠 때 — 승격한다

`@@unique([spaceId, provider, externalProjectId])` 인데 **수동은 거기에
`소유자/이름` 을, 자동은 GitHub 숫자 id 를 넣는다.** 같은 저장소를 양쪽으로
붙여도 유니크가 걸리지 않아 **행이 둘 생긴다.**

그래서 `connect` 는 `fullPath` 로도 한 번 찾아본다. 이미 있으면 새로 만들지
않고 그 행을 **승격**한다 — `externalProjectId` 를 숫자 id 로 바꾸고 훅을 건다.
쌓인 `repo_events` 가 그대로 이어지고, 채널에 올라간 옛 메시지도 살아 있다.

승격하면 `externalProjectId` 가 **이름 변경에 견디는 값**이 된다. 수동 등록이
경로를 식별자로 쓸 수밖에 없던 제약(10-1)이 여기서 풀린다.

### 누구의 토큰을 쓰나

**그 순간 요청한 사람의 토큰.** 저장소는 스페이스에 붙는데 토큰은 사람에게
붙어 있어 어긋난다. 등록한 사람을 따로 기록해 두는 방법도 있지만, 그러면 그
사람이 연결을 해제한 순간 아무도 훅을 손볼 수 없게 된다. admin 이면 누구나
할 수 있는 편이 낫다.

**토큰이 없으면 GitHub 호출을 건너뛰고 우리 행만 지운다.** 남은 고아 훅은 우리
서버로 오지만 `repoId` 가 없어 404 로 떨어지고, GitHub 이 연속 실패한 훅을
스스로 비활성화한다.

### 주소가 바뀔 때

무료 cloudflared quick tunnel 은 띄울 때마다 도메인이 바뀐다. `PUBLIC_BASE_URL`
을 고치고 `POST /repos/:repoId/webhook` 을 부르면 **저장된 훅 id 로 GitHub 쪽
URL 을 갱신**한다. GitHub 설정 화면을 열 필요가 없다.

- 훅 id 가 없으면(등록에 실패했던 행) 새로 만든다
- 훅 id 가 있는데 GitHub 이 404 를 주면(사람이 지웠다) 새로 만든다
- 시크릿은 **그대로 둔다.** 주소가 바뀐 것과 시크릿을 새로 파는 것은 다른 일이다

## 8. 스키마 · 환경 변수

**마이그레이션 1개** — `repos.webhook_external_id String?` 하나뿐이다.

> 자동 생성된 SQL 에 pgvector HNSW `DROP INDEX` 가 섞여 들어오는 일을 **네 번**
> 겪었다. `npm run check:migrations` 가 CI 에서 잡지만, 생성된 SQL 은 읽고 커밋한다.

| env | 상태 | 설명 |
|---|---|---|
| `GITHUB_CLIENT_ID` · `GITHUB_CLIENT_SECRET` | 자리 있음 | OAuth App 등록 후 채운다 |
| `GITHUB_CALLBACK_URL` | 자리 있음 | **브라우저가 오는 주소.** localhost 로 둬도 된다 |
| `OAUTH_TOKEN_KEY` | 신규 | 토큰 암호화 키. 없으면 연결만 503 |
| `PUBLIC_BASE_URL` | 신규 | **GitHub 서버가 오는 주소.** 터널이어야 한다 |
| `GITHUB_API_BASE` · `GITHUB_OAUTH_BASE` | 신규 | 기본값은 진짜 GitHub. 검증에서만 바꾼다(§10) |

**`GITHUB_CALLBACK_URL` 과 `PUBLIC_BASE_URL` 을 합치지 않는다.** 둘은 다른
주소다 — 콜백은 **사람의 브라우저**가 오므로 개발 PC 의 `localhost` 로 충분하고
(GitHub OAuth 는 localhost 콜백을 허용한다), 웹훅은 **GitHub 서버**가 오므로
반드시 밖에서 닿는 주소여야 한다. 합치면 OAuth 를 시험하는 데도 터널이 필요해진다.

## 9. 앱

새 화면 하나 — `/s/:spaceId/repos`. 앱에 설정 화면이 아직 없어서 저장소 화면이
연결 상태까지 함께 보여 준다.

**10-2a 에서 만드는 것** — 화면 자체와 상단 연결 영역.

- **연결 안 됨**: "GitHub 연결" 버튼 → `start` → `url_launcher` 로 브라우저를 연다
  → "브라우저에서 계속하세요" 상태로 대기 → `oauth:connected` 를 받으면 바뀐다
- **연결됨**: 아바타 · `@계정` · 해제 버튼

**10-2b 에서 채우는 것** — 목록과 붙이기.

- **저장소 추가**: 시트에 내 GitHub 저장소(페이지 넘김 + 받아 온 목록 안에서
  이름 거르기). `canWebhook=false` 는 회색으로 고를 수 없게 한다 → 고르고
  채널 선택 → `connect`
- **붙은 목록**: 경로 · 연결된 채널 · 웹훅 상태. 실패한 것에 "다시 걸기"

**저장소 목록도 붙은 목록도 drift 에 캐시하지 않는다.** 파일 목록 · 이슈 댓글과
같은 판단이다 — 오프라인에서 볼 이유가 약하고, 캐시하면 GitHub 쪽 변화와
어긋난 채로 굳는다. 화면이 drift 만 구독한다는 규칙은 **대화 경로의 규칙**이고,
이미 그 예외가 둘 있다.

새 의존성은 `url_launcher` 하나다.

**대기 상태에 타임아웃을 두지 않는다.** 사람이 브라우저에서 GitHub 로그인부터
해야 할 수도 있어 얼마가 걸릴지 알 수 없다. 대신 "다시 확인" 버튼을 둬서
소켓을 놓쳤을 때도 목록을 다시 부를 수 있게 한다.

## 10. 검증 — 가짜 GitHub 을 띄운다

10-1 의 `check:repos` 30개는 **GitHub 없이** 돌았다. 서명을 우리가 만들어 보내면
그만이었다. 10-2 는 토큰 교환 · 저장소 목록 · 훅 등록이 **전부 밖으로 나가는
호출**이라 그대로는 돌지 않는다.

**`GITHUB_API_BASE` · `GITHUB_OAUTH_BASE` 를 env 로 뺀다.** 검증 스크립트가
로컬 가짜 GitHub 을 띄우고 그 주소를 물려 돌린다. 억지 추상화가 아니라 GitHub
자신이 GHE 를 위해 가진 개념이라, 이 갈래는 나중에도 값을 한다.

`npm run check:repos` 에 더할 것:

| 갈래 | 케이스 |
|---|---|
| `state` | 위조 거부 · 만료 거부 · 용도가 다른 JWT 거부 |
| 토큰 | 암호화 왕복 · **연결 목록 응답에 토큰이 없음** · 복호화 실패는 "연결 없음" |
| 연결 | 연결 · 재연결(upsert) · 해제 · 해제 후에도 훅은 살아 있음 |
| 목록 | 프록시 · 페이지 · `canWebhook=false` 인 저장소로 connect 하면 거부 |
| 자동 등록 | `PUBLIC_BASE_URL` 없으면 400 · 성공 시 훅 id 저장 · **실패해도 행이 남고 상태가 실패** |
| 승격 | 수동으로 붙인 저장소를 connect 하면 행이 늘지 않고 승격되며 이벤트 이력이 남는다 |
| 재등록 | 주소 갱신 · 훅 id 없을 때 새로 만듦 · GitHub 404 일 때 새로 만듦 |
| 삭제 | GitHub 훅도 지운다 · 토큰이 없으면 우리 행만 지운다 |
| 격리 | 남의 스페이스 저장소에 connect · webhook · delete 는 전부 404 |

**앱은 위젯 테스트로 분기를 고정한다** — 연결 안 됨/됨, 웹훅 실패 표시,
`canWebhook=false` 가 고를 수 없는 것. 9-3 에서 화면을 빠뜨린 채 완료로 보고한
일이 있었고, 그런 구멍은 사람이 눈으로 볼 때만 드러났다.

**마지막에 실제 GitHub 으로 한 번 종단 확인한다.** 그때 필요한 것이 OAuth App
등록(Client ID · Secret · 콜백 URL)이고 **이것만 사람이 직접 해야 한다.**
설계 · 구현 · 계약 검증은 그것 없이 끝까지 간다.
