# 10-3b 커밋 열람 — 설계

> 2026-08-21. [10-3a 저장소 열람](2026-08-21-저장소-열람-design.md) §0 이 미뤄 둔
> 조각이다. 그 문서가 "커밋 단건의 변경 파일 계약이 백엔드-설계에 없어 그때
> 정한다"고 적은 것을 여기서 정한다.

10-1 이 커밋을 채널로 흘려보냈고, 10-3a 가 저장소 안을 열었다. 여기서 **채널의
그 한 줄과 코드가 이어진다** — "커밋 9개를 올렸습니다"를 누르면 그 아홉 개가
보이고, 하나를 누르면 무엇이 바뀌었는지 보인다.

---

## 0. 실측이 설계를 바꾼 지점

작업 전에 `repo_events.payload` 를 실제로 열어 보고 둘을 확인했다.

**하나. 커밋이 잘리지 않았다.** GitHub push payload 는 커밋을 최대 20개만
싣는다고 알려져 있는데, 27개를 push 한 이벤트에 **27개가 그대로** 있었다.

**둘. 각 커밋이 `added` · `removed` · `modified` 배열을 이미 들고 있다.**

그래서 **"그 push 에 들어온 커밋들"은 GitHub 을 한 번도 부르지 않는다.** 커밋
목록도 각 커밋의 변경 파일 목록도 우리 DB 에 이미 있다. rate limit 을 쓰지 않고,
GitHub 이 느려도 즉시 열리며, 저장소 접근 권한이 나중에 사라져도 지난 기록은 남는다.

**20개 상한에 대비하는 코드를 지금 넣지 않는다.** 실측에서 걸리지 않았고, 걸리는
것을 보지 못한 채 방어를 넣으면 **확인할 수 없는 가정 위에 코드를 쌓게 된다.**
실제로 잘린 것을 보면 그때 `GET /repos/{o}/{r}/compare/{before}...{after}` 를
붙인다 — `before` · `after` 도 payload 에 이미 있다.

---

## 1. 메시지에서 이벤트로 — `repoEventId`

채널에 뜨는 시스템 메시지는 **한 줄 텍스트일 뿐 커밋 sha 를 들고 있지 않다**
(10-1 이 그렇게 정했다 — 커밋 목록을 다 펼치면 대화가 로그가 된다). 원본은
`repo_events.payload` 에 있고 그 행이 `messageId` 로 메시지를 가리킨다.

**메시지 응답에 `repoEventId` 를 싣는다.** 있으면 파고들 수 있고 없으면 못 한다.

대안이었던 것 둘을 쓰지 않는 이유:

- **작성자에 `isBot`** — 더 일반적이지만, 봇 메시지라고 다 커밋이 있는 것은
  아니다(PR · 이슈 · 릴리스도 봇이 쓴다). 눌러 봐야 빈 화면인 경우가 생긴다
- **이름으로 판별** — 사람이 이름을 "GitHub"으로 지으면 깨진다

대가는 파급이다. 서버 응답 · 앱 모델 · drift 캐시(`schemaVersion` +1) · 소켓
페이로드가 함께 바뀐다. **리액션 · 인용 · 멘션을 붙일 때와 같은 종류의 작업**이고,
이 저장소는 그 길을 세 번 지나왔다.

**N+1 을 만들지 않는다.** 메시지 목록은 이미 리액션 · 인용 · 멘션 · 첨부를
`summarizeMany` 로 한 번에 모은다([messages.service.ts:81](../../../server/src/messages/messages.service.ts)).
`repo_events` 도 같은 방식으로 `messageId in (…)` 한 번에 읽는다.

## 2. API 계약

```
GET /spaces/:spaceId/repo-events/:eventId                  ← payload 에서. GitHub 호출 0
GET /spaces/:spaceId/repos/:repoId/commits?ref=&cursor=    ← GitHub
GET /spaces/:spaceId/repos/:repoId/commits/:sha            ← GitHub
```

셋 다 `SpaceGuard` 아래이고 **읽기라 `@MinRole` 을 걸지 않는다**(10-3a §2 와 같다).

**`repo-events` 만 저장소 밑이 아니다.** 앱이 메시지에서 얻는 것은 `eventId`
하나이고, 그것으로 `repoId` 를 찾는 것은 서버의 일이다. 앱에게 저장소 id 를 먼저
알아 오라고 요구하면 왕복이 하나 는다.

### 응답

```jsonc
// repo-events/:eventId — push 이벤트
{
  "type": "push",
  "repoId": "…", "repoFullPath": "octocat/hello-world",
  "ref": "main",
  "commits": [
    { "sha": "a1b2c3d", "message": "fix: …", "authorName": "dbsrjs",
      "committedAt": "2026-08-21T…", "changedCount": 3 }
  ]
}

// repo-events/:eventId — push 가 아닌 이벤트(PR · 이슈 · 릴리스)
{ "type": "pr", "repoId": "…", "repoFullPath": "…", "ref": null, "commits": [] }

// commits?ref=&cursor= — 브랜치 이력
{ "ref": "main", "commits": [ … ], "nextCursor": "3" }

// commits/:sha — 한 커밋
{
  "sha": "a1b2c3d…", "message": "fix: …", "authorName": "dbsrjs",
  "committedAt": "…",
  "files": [ { "path": "server/src/main.ts", "status": "modified" } ]
}
```

**커밋 요약의 모양을 세 곳에서 같게 쓴다**(`sha` · `message` · `authorName` ·
`committedAt`). 화면이 같은 위젯으로 그리기 위해서다 — payload 에서 온 것과
GitHub 에서 온 것이 다르게 보이면 사용자가 두 목록을 다른 것으로 읽는다.

**`changedCount` 는 payload 에서만 채운다**(`added` + `removed` + `modified`).
GitHub 커밋 목록 API 는 파일 수를 주지 않아 `null` 이다 — 없는 값을 만들려고
커밋마다 상세를 부르면 스무 번 왕복이 된다.

**`message` 는 제목 줄만 자르지 않고 전문을 준다.** 목록은 화면이 한 줄로
자르지만, 상세에서는 본문까지 읽혀야 한다.

### `status` — 파일이 어떻게 바뀌었나

`added` · `removed` · `modified` 셋으로 준다. payload 는 세 배열로 오고,
GitHub 커밋 상세는 `status` 필드로 온다(`renamed` 등 다른 값은 `modified` 로
접는다 — 화면이 할 일이 같다).

### 커서

GitHub `commits` API 는 page 번호를 쓴다. 10-2b 의 저장소 목록과 같이 **그 번호를
그대로 노출한다** — `nextCursor` 는 다음 page 번호의 문자열이고, 없으면 `null` 이다.

### 실패

10-3a §2 와 같다 — 토큰 없으면 400, 429 는 `Retry-After` **헤더**로, GitHub
404 는 404, 그 밖은 502. **`repo-events` 는 GitHub 을 부르지 않아 이 갈래가
없다** — 없는 이벤트는 404 뿐이다.

## 3. 앱

**화면 둘을 더하고 하나를 고친다.**

| 라우트 | 무엇 |
|---|---|
| `/s/:spaceId/repo-events/:eventId` | 그 push 의 커밋 목록 |
| `/s/:spaceId/repos/:repoId/commits/:sha` | 커밋 상세 — 변경 파일 목록 |
| `/s/:spaceId/repos/:repoId/browse` | **고친다** — '커밋' 탭 |

**진입점 둘.**

- **채널 메시지** — `repoEventId` 가 있는 메시지를 누르면 커밋 목록이 열린다.
  없는 메시지는 지금처럼 아무 일도 없다
- **탐색 화면의 '커밋' 탭** — 브랜치 이력. 커서로 더 불러온다

**커밋 상세에서 파일을 누르면 10-3a 의 파일 보기를 그 sha 로 연다.** diff 를
그리지 않는 이유는 렌더러를 새로 써야 하기 때문이다(hunk 파싱 · 줄 번호 두 개 ·
색). 10-3a 에서 신택스 하이라이팅을 미뤄 둔 것과 결이 같다. **그 시점의 전문을
보는 것으로 "무엇이 바뀌었더라"의 대부분이 풀린다** — 바뀐 파일이 무엇인지는
목록이 이미 말해 준다.

**캐시하지 않는다.** 10-3a 와 같다. 다만 **메시지의 `repoEventId` 는 캐시된다** —
메시지 캐시의 한 칸이라 따로 정할 것이 없다(`schemaVersion` +1).

## 4. 검증

`npm run check:browse` 에 더한다. 10-3a 와 같은 주제(열람)이고 같은 가짜 GitHub 을
쓴다.

| 갈래 | 케이스 |
|---|---|
| 메시지 | 저장소 이벤트 메시지에 `repoEventId` 가 실린다 · 사람이 쓴 메시지에는 없다 |
| 이벤트 | push 의 커밋 목록 · `changedCount` · **GitHub 을 부르지 않는다** · PR 이벤트는 `commits: []` |
| 브랜치 이력 | 목록 · 커서 · 마지막 장에서 `nextCursor: null` |
| 커밋 상세 | 파일 목록 · `status` 세 값 · `renamed` 는 `modified` 로 접힘 |
| 격리 | 남의 스페이스 이벤트 · 커밋은 404 |

**"GitHub 을 부르지 않는다"를 어떻게 확인하나** — 가짜 GitHub 이 받은 요청 수를
세어 두고, `repo-events` 호출 전후로 그 수가 그대로인지 본다. 이 조각의 핵심
판단이라 말로만 두지 않는다.

**앱은 위젯 테스트로 고정한다** — 커밋 목록 · 변경 파일의 세 `status` · 메시지에
`repoEventId` 가 없을 때 눌리지 않는 것.

## 5. 범위에서 뺀 것

| 뺀 것 | 이유 |
|---|---|
| diff 본문 | 렌더러를 새로 써야 한다(§3). 파일 전문으로 대부분 풀린다 |
| `compare` API 로 20개 상한 보완 | 실측에서 걸리지 않았다(§0). 걸리는 것을 보면 붙인다 |
| PR diff · 리뷰 | 11단계 |
| 커밋 검색 | 저장소 검색과 같이 다른 API 이고 rate limit 도 따로다 |
| 이벤트 목록(채널의 저장소 활동) | 메시지가 이미 그 목록이다 |
