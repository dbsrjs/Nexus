## 0. 문서에 적힌 판단 둘을 뒤집는다

### 하나. 재귀 트리를 쓴다 — 10-3a 는 일부러 쓰지 않았다

10-3a 는 이렇게 적어 두었다 — *"`git/trees` + `git/blobs` 를 쓰지 않은 이유는
경로를 sha 로 바꾸는 호출이 매번 하나 더 필요하고, 재귀 트리는 큰 저장소에서
수만 항목이 오기 때문이다."*

**그 근거는 「사람이 폴더 하나를 여는」 상황의 것이다.** 한 번에 한 디렉터리만
보면 contents API 가 트리와 파일을 한 엔드포인트로 풀어 주고, 재귀 트리는
쓰지도 않을 수만 항목을 받는 낭비다.

**인덱싱은 정의상 전수 순회라 그 계산이 뒤집힌다.**

- contents API 로 순회하면 **디렉터리마다 한 번씩** 부른다. 트리는 **한 번**이다
- 재귀 트리는 항목마다 `size` 와 `sha` 를 함께 준다. 그래서 **요청을 쓰기 전에**
  크기로 거를 수 있다 — contents API 는 본문을 받아 봐야 크기를 안다
- 10-3a 가 피하려던 "수만 항목"은 우리가 실제로 **원하는 것**이다

그래서 `GET /repos/{o}/{r}/git/trees/{sha}?recursive=1` 한 번으로 목록을 받고,
살아남은 blob 만 `GET /repos/{o}/{r}/git/blobs/{sha}` 로 받는다.

**열람(10-3a)의 코드는 그대로 둔다.** 뒤집는 것은 이 단계의 순회 방식이지
사람이 폴더를 여는 경로가 아니다. 두 경로가 다른 API 를 쓰는 것이 정상이다 —
목적이 다르다.

### 둘. 큐를 Redis 로 하지 않는다

백엔드-설계 §8.2 는 *"호출은 Redis 큐를 거쳐 비동기 처리한다"* 고 적었다.

**이 프로젝트는 Redis 를 두 번 거절했다.** 10-3a 가 열람 캐시에서
*"Redis 가 이 프로젝트에 없고, 들이면 새 PC 셋업이 하나 더 는다"* 로 뺐고,
`docker-compose.yml` 의 `redis` 는 `--profile redis` 뒤에 숨어 있다.

그리고 **부담이 배포 비용이 아니라 로컬 개발 셋업 비용**이라는 점이 판단을
굳힌다. [인프라-설계 §4](../../인프라-설계.md) 는 배포를 *"VM 한 대에 Docker
로 다 올리는"* 형태로 잡고 **Redis 를 Phase 0 의 선택 사항**으로 명시했다 —
*"인스턴스를 늘려야 할 때 켠다."*

같은 문단이 단서를 달았다 — *"다만 코드는 처음부터 Redis 가 있다는 전제로
짠다."* **그 문장이 지키려는 것은 의존성이 아니라 목적이다: 인스턴스가 늘어도
안 깨질 것.** 그 목적은 `FOR UPDATE SKIP LOCKED` 리스로 **지금 당장** 만족된다
(§2). Redis 를 나중에 들이더라도 워커 인터페이스는 그대로다.

## 1. 이미 있는 것으로 끝나는 부분

**스키마를 거의 늘리지 않는다.** 2단계 init 마이그레이션이 다 넣어 두었다.

| 있는 것 | 확인 |
|---|---|
| `repo_index_chunks` | `spaceId` · `repoId` · `path` · `lang` · `startLine` · `endLine` · `content` · `embedding vector(768)` · `commitSha`. **`spaceId` 가 이미 있다** — §3 규칙 1 을 위반하지 않는다 |
| `repos.indexedAt` · `indexedCommitSha` | 증분 판정의 기준(§4). **이 둘로 충분해 새 컬럼이 필요 없다** |
| HNSW 인덱스 | `repo_index_chunks_embedding_hnsw_idx`, `vector_cosine_ops` |
| `@nestjs/schedule` | 이미 의존성이고 `app.module.ts` 에 등록돼 있다 |

**코드도 그렇다.** `RepoAccessService`(토큰 · 접근 제어) · `resolveBlobBody`
(바이너리 판별) · `toGithubHttpError`(429 `Retry-After` 포함) 를 그대로 쓴다.

**늘리는 것은 테이블 하나뿐이다** — `repo_index_jobs`(§2).

## 2. 큐 — DB 테이블 한 장, 저장소마다 한 행

### 왜 DB 인가

| 후보 | 대가 |
|---|---|
| Redis + BullMQ | 새 PC 셋업이 하나 늘고 패키지가 는다. §0 의 이유로 뺀다 |
| **DB 테이블** | 테이블 하나 + 마이그레이션 하나. 폴링이라 지연이 생긴다 |
| 인메모리 | 셋업 비용 0. **인덱싱은 분 단위 작업이라 재시작 한 번에 조용히 사라진다** |

**선례가 이미 돌고 있다.** [`OrphanCleanupService`](../../../server/src/attachments/orphan-cleanup.service.ts)
가 정확히 이 모양이다 — 부팅 때 한 번 + `@Cron`, 실패해도 서버는 떠 있고 다음
회차에 다시 시도한다. 새로 들이는 것이 **없다.**

인메모리를 뺀 이유는 수명이다. 첨부 고아 정리는 놓쳐도 다음 시간에 다시 돌지만,
**인덱싱 작업을 잃으면 그 저장소는 영영 낡은 채로 남는다** — 다시 태울 계기가
push 밖에 없다.

### 왜 `repos` 컬럼이 아니라 별도 테이블인가

의뢰서 §4 가 *"스키마를 늘리기 전에 기존 컬럼으로 되는지 먼저 확인"* 하라 했다.
`repos` 에 `indexState` · `indexError` · `indexAttempts` 를 얹는 안을 검토했고
물렸다.

**워커의 리스가 `repos` 행을 두고 경합한다.** 그 행은 웹훅 수신 · 열람 ·
훅 재등록이 모두 읽고 쓴다. 인덱싱 상태는 그것들과 **수명이 다르다** — 6-2 가
전송 큐를 캐시와 다른 테이블에 둔 것과 같은 이유다.

### 한 저장소에 한 행 — `repoId` 가 기본 키다

```
repo_index_jobs
  repoId      String  @id            ← 저장소마다 한 행. 이것이 합침(coalescing)이다
  spaceId     String                 ← §3 규칙 1. 예외 없다
  state       queued | running | done | failed
  reason      connect | push | manual
  headSha     String?                ← 인덱싱 목표 커밋. null 이면 워커가 정한다(아래)
  baseSha     String?                ← 증분 기준. null 이면 전체(§4)
  attempts    Int
  lastError   String?
  truncated   Boolean                ← 재귀 트리가 잘렸다(§3). 조용히 숨기지 않는다
  leaseUntil  DateTime?
  createdAt / startedAt / finishedAt
```

**행을 하나로 두면 합침이 구조가 된다.** push 가 열 번 와도 인덱싱은 한 번이다 —
목표 커밋만 최신으로 덮어쓴다. 부분 유니크 인덱스(`WHERE state = 'queued'`)로
같은 것을 할 수도 있지만, **그건 Prisma 가 표현하지 못하는 손 관리 객체를 하나
더 만드는 일**이다. HNSW 인덱스로 네 번 데인 자리에 다섯 번째를 만들 이유가 없다.

**`headSha` 가 null 인 경우가 정상이다.** 저장소 연결 시점에는 목표 커밋을 모른다 —
웹훅과 달리 payload 가 없다. 그때는 워커가 default 브랜치의 head 를 먼저 조회해
정한다(요청 하나가 는다). 웹훅에서 온 작업은 `payload.after` 가 있으므로 채워진다.

**돌고 있는 중에 새 push 가 오면** `headSha` 만 바뀐다. 워커는 리스를 잡을 때
`headSha` 를 손에 들고, 끝낼 때 그 값이 그대로인지 본다 — 달라졌으면 `done` 이
아니라 `queued` 로 되돌린다. 추가 컬럼 없이 "돌리는 중에 들어온 것"이 처리된다.

### 리스 — `FOR UPDATE SKIP LOCKED`

```sql
SELECT repo_id FROM repo_index_jobs
 WHERE state IN ('queued','running')
   AND (lease_until IS NULL OR lease_until < now())
 ORDER BY created_at
 LIMIT 1
 FOR UPDATE SKIP LOCKED
```

- 잡으면 `state='running'`, `leaseUntil = now() + 10분`. 파일 배치마다 갱신한다
- **리스가 만료된 `running` 은 다시 잡힌다.** 이것이 크래시 복구다 —
  프로세스가 죽으면 리스만 만료되고 작업은 살아 있다
- **트랜잭션을 작업 내내 붙들지 않는다.** 리스를 쓰고 곧바로 커밋한다.
  분 단위로 행을 잠그면 다른 인스턴스가 아니라 우리 자신이 막힌다

### 언제 깨우나

| 계기 | 자리 |
|---|---|
| 저장소 연결 직후 | `RepoConnectService` 의 연결 성공 뒤. `baseSha = null`(전체) |
| default 브랜치 push | `WebhooksService` — `ref === refs/heads/{repo.defaultBranch}` 일 때만 |
| 사람이 다시 태움 | `POST /spaces/:spaceId/repos/:repoId/index` (`admin`) |

**웹훅의 적재 트랜잭션 밖에 둔다.** 안에 넣으면 큐 쓰기 실패가 웹훅 전체를
넘어뜨리는데, GitHub 은 실패에 재시도하고 저장소 설정 화면이 빨개진다(10-1).

밖에 두어도 **스스로 낫는다** — 적재를 놓친 push 는 다음 push 때
`compare(indexedCommitSha → 새 head)` 안에 통째로 들어온다. 그 사이가 길어질
뿐 빠지지 않는다.

**폴링 지연은 적재 직후 인프로세스로 한 번 깨워 없앤다.** 크론(30초)은 그것이
실패했을 때의 백스톱이다. 이 깨우기는 최적화가 아니라 **검증이 성립하는 조건**
이기도 하다 — 계약 검증이 30초를 기다릴 수는 없다.

### 실패를 어떻게 세나

6-2 의 전송 큐 규칙을 그대로 쓴다. **네트워크 실패는 시도 횟수로 치지 않는다.**

| 실패 | 처리 |
|---|---|
| 429 · 네트워크 · 타임아웃 | 횟수에 안 넣고 `leaseUntil` 을 미뤄 재시도. `Retry-After` 를 존중한다 |
| 401 (토큰 만료) · 404 (저장소 사라짐) | **즉시 `failed`.** 다시 걸어도 같다 |
| 그 밖 | 3회까지. 넘으면 `failed` 로 두고 `lastError` 를 남긴다 |

**`failed` 를 조용히 지우지 않는다.** 화면은 없지만 상태 조회(§6)가 그것을
말한다 — 7-5 · 6-2 가 실패를 남긴 것과 같은 이유다.

## 3. 순회와 파일 선별

### 요청 예산 — 이 저장소로 실측했다

`dbsrjs/Nexus` 기준: 추적 파일 **535개**, 바이너리·생성물을 뺀 텍스트 **474개**,
**3.7MB**, **99,330줄**.

| | 요청 수 | 시간당 5,000 중 |
|---|---|---|
| 최초 전체 인덱싱 | 트리 1 + blob ~474 = **약 475** | **9.5%** |
| push 후 증분 | `compare` 1 + 바뀐 파일 N = **보통 10 미만** | 0.2% |

부차 한도는 **REST GET 1점 · 분당 900점**이므로 동시성을 4 로 두어도 분당
240 요청 수준이라 여유가 크다. 동시성을 그 이상 올리지 않는 이유는 얻을 것이
없어서다 — 전체 인덱싱은 어차피 저장소당 한 번이다.

> 근거: [GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
> (2026-09-08 확인) — 인증 사용자 토큰 5,000/시간, 동시 요청 100,
> REST 분당 900점, GET 은 1점.

### 재귀 트리가 잘리면

재귀 트리는 **10만 항목 / 7MB 에서 잘리고 `truncated: true` 를 준다**
([Git trees](https://docs.github.com/en/rest/git/trees), 2026-09-08 확인).
이 규모에서는 닿지 않는다.

**닿지 않는 것을 알면서 방어를 짓지 않는다** — 10-3b 가 커밋 20개 상한에서
*"걸리는 것을 보지 못한 채 방어를 넣으면 확인할 수 없는 가정 위에 코드를 쌓게
된다"* 고 한 그 규칙이다. 대신 **받은 것까지 인덱싱하고 `truncated` 를 작업에
기록한다** — 9-1 이 컬럼 상한에서 정한 *"조용히 자르지 않는 것이 상한을 둘 수
있는 조건"* 이다. 실제로 잘리는 것을 보면 그때 디렉터리 단위 폴백을 붙인다.

### 무엇을 거르나

**두 가지만 본다.**

1. **크기** — `size > 256KB` 면 건너뛴다. 열람의 512KB(`MAX_BLOB_BYTES`)보다
   낮은 이유는 목적이 달라서다. 열람은 사람이 한 번 보고 마는 것이지만,
   512KB 짜리 한 파일은 **약 260개 청크**가 되어 임베딩 비용이 파일 하나에
   몰린다. 트리가 크기를 먼저 주므로 **요청을 쓰지 않고 걸러진다**
2. **바이너리** — 받은 뒤 `resolveBlobBody()` 가 판별한다. NUL 바이트와
   UTF-8 디코딩 실패로 본다. **확장자 목록을 만들지 않는다**(10-3a 규칙)

**경로 목록(deny-list)을 두지 않는다.** 목록은 유지 비용이 끝없이 늘고, 목록에
없는 것이 나올 때마다 고쳐야 한다 — `blob-content.ts` 가 바이너리 판별에서
같은 판단을 했다.

**다만 예외 하나** — 첫 두 줄에 `GENERATED CODE` 또는 `@generated` 가 있으면
건너뛴다. 경로가 아니라 **내용**으로 보므로 위 규칙과 어긋나지 않는다. 이
저장소의 `.freezed.dart` · `.g.dart` 가 실제로 그 줄로 시작하고, **18,182줄
(전체의 18%)** 이 여기서 빠진다. 사람이 쓰지 않은 코드는 AI 근거로도 값이 없다.

### `lang`

확장자에서 뽑는다. 모르면 `null`. 지금은 표시용이고, 나중에 언어로 좁힌 검색이
필요해지면 그때 쓴다.

## 4. 재인덱싱 — `compare` 한 번으로 바뀐 파일만

§7.4 가 정한 *"`commit_sha` 를 함께 기록해 변경된 파일만 재인덱싱한다"* 를
**기존 컬럼만으로** 구현한다.

```
baseSha = repos.indexedCommitSha
GET /repos/{o}/{r}/compare/{baseSha}...{headSha}    ← 한 번
 → files[] { filename, status, previous_filename? }
```

| status | 처리 |
|---|---|
| `added` · `modified` · `changed` | 그 경로의 청크를 지우고 다시 만든다 |
| `removed` | 청크만 지운다 |
| `renamed` | `previous_filename` 의 청크를 지우고 새 경로로 만든다 |

**전체로 떨어지는 조건 셋.**

- `baseSha` 가 없다 (연결 직후 · 첫 인덱싱)
- `compare` 가 404 다 (force-push 로 base 가 사라졌다)
- `compare` 가 파일 목록을 잘라서 줬다

**전체 재인덱싱은 조용히 하지 않는다** — 작업의 `reason` 과 로그에 남긴다.
왜 갑자기 500 요청을 썼는지 나중에 설명할 수 있어야 한다.

### `commitSha` 컬럼이 뜻하는 것

증분으로 돌면 **바뀌지 않은 파일의 청크는 옛 `commitSha` 를 그대로 들고 있다.**
그것이 맞다 — 이 컬럼은 "저장소의 현재 커밋"이 아니라 **"이 청크의 내용을 뜬
시점"** 이다. 저장소 전체의 기준은 `repos.indexedCommitSha` 하나다.

### 쓰기는 파일 단위 트랜잭션이다

경로 하나당 `delete(repoId, path)` → `insert(청크들)` 를 한 트랜잭션으로 묶는다.

**저장소 전체를 한 트랜잭션으로 묶지 않는다.** 2,300개 행을 한 번에 쓰는
트랜잭션은 몇 분을 잡고 있고, 중간에 끊기면 처음부터다. 파일 단위면 멱등이고
이어서 할 수 있다 — 다시 돌면 이미 한 파일은 같은 결과로 덮인다.

## 5. 청킹 — 고정 60줄 / 10줄 겹침

### 왜 경계 인식을 넣지 않나

§7.4 는 *"함수·클래스 경계 우선, 실패 시 고정 라인 수"* 라 적었다. **경계 인식은
언어별 파서를 뜻한다.**

이 프로젝트는 마크다운 파서와 코드 하이라이터를 직접 만들어 패키지를 거절해
왔지만, **그 둘은 규모가 다르다** — 마크다운은 문법 하나짜리이고, 하이라이터는
**줄 단위로 넷만 칠하는** 얕은 규칙이다(*"여러 줄에 걸친 블록 주석은 추적하지
않는다"*). TS · Dart · SQL · YAML · C++ 의 함수 경계를 제대로 잡는 것은 그것들과
같은 종류의 일이 아니다.

**붙이는 신호는 검색 결과가 함수 중간에서 잘려 근거로 못 쓰이는 것을 실제로
보는 것이다.** 그때 언어 하나씩 붙인다 — 청크 경계는 다시 인덱싱하면 바뀌므로
나중에 바꾸는 비용이 낮다. 저장 형식이 아니다.

### 왜 60 / 10 인가

- **60줄** — 이 코드베이스에서 함수 하나에 앞뒤 맥락이 붙는 크기다. 그리고
  긴 줄을 감안해도 **`gemini-embedding-001` 의 2,048 토큰 한도 아래**로 들어온다
  (60줄 × 약 40자 ≈ 2,400자 ≈ 700~900 토큰). 약한 쪽에 맞춰야 provider 를
  갈아탈 때 청크 크기를 다시 정하지 않는다
- **10줄 겹침(≈17%)** — 경계에서 잘린 함수가 **한쪽 청크에는 온전히** 들어가게
  하는 최소값이다. 겹침이 없으면 경계에 걸친 코드는 어느 청크에서도 완결되지 않는다
- **문자 상한 4,000자를 따로 둔다** — 압축된 파일은 200KB 짜리 한 줄이 나온다.
  줄 수만으로 자르면 그런 파일이 토큰 한도를 통째로 넘긴다. **상한에 걸리면 그
  자리에서 청크를 끊고 다음 청크가 이어받는다 — 내용을 버리지 않는다.** 한 줄이
  혼자 상한을 넘으면 그 줄 안에서 자른다(그런 줄은 사람이 쓴 코드가 아니다)
- **빈 줄에서 끊을 수 있으면 그쪽을 고른다**(경계 앞뒤 5줄 안에서만 찾는다).
  파서가 아니라 한 줄짜리 보정이다

추산: 99,330줄 ÷ 스트라이드 50 ≈ **약 2,300 청크**, 벡터 저장 약 7MB,
전체 인덱싱 1회에 **약 1.2M 토큰**.

## 6. 임베딩 provider — 인터페이스 뒤에 셋

### 768 이 선택을 제약한다

`vector(768)` 이 스키마와 HNSW 인덱스에 박혀 있다. 차원을 바꾸는 것은
**인덱스 재생성**을 뜻한다.

**2026-09-08 에 공식 문서로 확인한 것.**

| provider | 768 | 확인 내용 |
|---|---|---|
| **Gemini** `gemini-embedding-001` · `-2` | ✅ | `output_dimensionality` 로 지정. 기본 3,072 이고 **권장값이 768 · 1,536 · 3,072**. 입력 한도 2,048(001) · 8,192(2) 토큰 |
| **nomic-embed-text** (Ollama) | ✅ | 정확히 768, 8,192 컨텍스트, 무료·무제한. **Ollama 데몬이 새 런타임 의존** |
| **voyage-code-3** (코드 특화) | ❌ | 256 · 512 · 1,024 · 2,048 뿐. **768 이 없어 차원 마이그레이션을 강요한다 — 그래서 뺀다** |

> [Gemini Embeddings](https://ai.google.dev/gemini-api/docs/embeddings) ·
> [voyage-code-3](https://blog.voyageai.com/2024/12/04/voyage-code-3/) ·
> [Ollama nomic-embed-text](https://ollama.com/library/nomic-embed-text:latest/blobs/970aa74c0a90)

**확인하지 못한 것 — 무료 티어 수치.** Gemini 의 rate-limits 문서는 이제
RPM/TPM 을 싣지 않고 *"AI Studio 에서 확인하라"* 고만 한다. **숫자를 인용할 수
없어 적지 않는다.** 실제 한도에 부딪히면 429 재시도 경로(§2)가 받는다.

### 인터페이스

```ts
interface EmbeddingProvider {
  readonly dimensions: number;   // 반드시 768
  embed(texts: string[]): Promise<number[][]>;
}
```

| 구현 | 언제 |
|---|---|
| `gemini` | **기본.** 운영 · 실제 확인 |
| `local` | Ollama 를 쓰는 PC. 키가 필요 없다 |
| `fake` | **검증 전용.** 텍스트를 해시해 결정적 768 벡터를 만든다 |

**`fake` 는 편의가 아니라 요구 조건이다.** 없으면 CI 가 외부 API 키에 묶인다.
그리고 결정적이라 **"이 청크가 1위로 나온다"를 단언으로 고정할 수 있다** —
확률적인 값으로는 검증 케이스를 쓸 수 없다.

### 규칙

- **차원을 어댑터가 검사한다.** 768 이 아닌 벡터가 오면 그 자리에서 실패시킨다.
  그냥 넣으면 pgvector 가 알아보기 어려운 메시지로 던진다
- **정규화해서 넣는다.** `vector_cosine_ops` 는 크기에 영향받지 않아 없어도
  되지만, `gemini-embedding-001` 은 768 로 자르면 단위 벡터가 아니게 되고
  (문서가 직접 정규화를 요구한다), 넣어 두면 나중에 내적 연산으로 바꿀 여지가 남는다
- **배치 크기는 보수적으로 32.** 배치 한도는 문서에 명시돼 있지 않다 —
  모르는 값에 붙어 있지 않도록 낮게 잡고 설정으로 뺀다
- **키가 없으면 부팅은 되고 인덱싱만 멈춘다.** 10-2a 의 `OAUTH_TOKEN_KEY` 규칙
  그대로다 — **없는 것과 잘못된 것은 다르다.** 없으면 작업이 `failed` 로
  남고 상태 조회가 이유를 말한다. 차원이 안 맞는 등 **설정이 틀린 것**은 부팅을 멈춘다
- **API 키는 서버에만 둔다.** 클라이언트가 provider 를 직접 부르는 경로는 만들지 않는다

### `.env`

```
EMBEDDING_PROVIDER=                           # gemini | local | fake. 기본값을 두지 않는다
EMBEDDING_MODEL=gemini-embedding-001
GEMINI_API_KEY=
EMBEDDING_BASE=                               # 비우면 실제 provider
```

**기본값을 두지 않는다.** `fake` 를 기본으로 하면 운영에서 아무도 모르게 해시
벡터가 들어가고, **검색이 돌긴 도는데 결과가 틀린다** — 가장 나쁜 실패다.
비어 있으면 인덱싱만 멈추고 이유를 남긴다.

`EMBEDDING_BASE` 는 **gemini 어댑터를 가짜 서버로 돌려 HTTP 갈래(429 · 5xx)를
태우는 데 쓴다.** `fake` 는 인프로세스라 그 경로를 지나지 않는다.

## 7. API 계약

**세 개뿐이고 앱은 쓰지 않는다.** 13단계 AI 가 그대로 쓸 자리다.

```
GET  /api/spaces/:spaceId/repos/:repoId/index          상태
POST /api/spaces/:spaceId/repos/:repoId/index          다시 태우기      @MinRole('admin')
POST /api/spaces/:spaceId/repos/:repoId/index/search   벡터 검색
```

전부 `SpaceGuard` 를 지난다. **저장소가 이 스페이스 것이 아니면 404 다** —
403 은 그 저장소가 존재한다는 것을 알려 준다.

### 검색에 `@MinRole` 을 걸지 않는다

10-3a 와 같은 이유다 — 걸면 **코드를 볼 수 있는 사람과 저장소 설정을 바꿀 수
있는 사람이 같아진다.** 다시 태우기만 `admin` 인 이유는 그것이 GitHub 할당량과
임베딩 할당량을 쓰는 일이어서다(저장소를 붙이는 것이 `admin` 인 것과 같은 무게).

### 상태

```json
{ "state": "done", "reason": "push", "indexedAt": "...", "indexedCommitSha": "abc123",
  "chunkCount": 2317, "truncated": false, "attempts": 0, "lastError": null }
```

한 번도 인덱싱하지 않았으면 `state: "none"`. **`null` 을 돌려 앱이 「없음」과
「모름」을 헷갈리게 하지 않는다**(10-3b · 11 의 규칙).

### 검색

```
POST … /index/search   { "query": "소켓 재연결은 어디서 하나", "topK": 8 }
→ { "chunks": [ { "path", "lang", "startLine", "endLine", "content", "commitSha", "score" } ] }
```

`topK` 는 기본 8 · 최대 20. `class-validator` DTO 로 받는다 — 전역 파이프가
`forbidNonWhitelisted` 라 DTO 밖 필드는 400 이다.

```sql
SELECT id, path, lang, start_line, end_line, content, commit_sha,
       1 - (embedding <=> $1::vector) AS score
  FROM repo_index_chunks
 WHERE space_id = $2 AND repo_id = $3 AND embedding IS NOT NULL
 ORDER BY embedding <=> $1::vector
 LIMIT $4
```

**`$2` · `$3` 를 `::uuid` 로 캐스팅하지 않는다.** Prisma 는 `String @id` 를
`text` 컬럼으로 만든다 — 캐스팅하면 `operator does not exist: text = uuid` 다
(§3 규칙 6). `$1::vector` 는 **id 가 아니라 벡터 리터럴**의 캐스팅이라 다르다.

**`space_id` 가 `WHERE` 에 있다.** 벡터 검색도 예외가 아니다 — `repo_id` 만으로
좁혀지지만, 규칙 1 은 "부모를 타고 유추할 수 있어도" 넣으라고 되어 있다.

**임베딩 컬럼은 Prisma 클라이언트로 읽고 쓸 수 없다.** 스키마가
`Unsupported("vector(768)")` 이라 클라이언트가 필드를 아예 만들지 않는다 —
삽입도 조회도 raw SQL 이다. 이것은 제약이 아니라 사실이고, 그래서 §8 의
검증이 실제 DB 를 요구한다.

**HNSW 는 필터를 나중에 적용한다.** 선택도가 높은 `WHERE` 를 걸면 상위 K 를
못 채울 수 있다 — 수천 행 규모에서는 문제가 되지 않지만, 실제로 덜 나오는 것을
보면 `hnsw.ef_search` 를 올리는 것이 손잡이다. **지금 손대지 않는다**(§3 의
방어를 미리 짓지 않는 규칙).

## 8. 검증

**벡터 검색은 스텁으로 증명할 수 없는 것의 전형이다.** CLAUDE.md §6 이 기록한
사고(스텁으로 22개를 통과시킨 코드에서 실제 DB 를 붙이자마자 버그 둘)가 정확히
이 종류다 — 스텁은 `$queryRaw` 를 빈 배열로 가짜 대체한다.

| 층 | 무엇 |
|---|---|
| `npm run check:indexing` | **실서버 · 실DB.** 가짜 GitHub(4599)을 스스로 띄운다 — `check:browse` 와 같은 방식이라 진짜 GitHub 없이 돈다 |
| `EMBEDDING_PROVIDER=fake` | CI 가 외부 키에 묶이지 않는다. 결정적이라 순위를 단언할 수 있다 |
| Jest | 청킹 · 파일 선별 · 증분 판정 · 벡터 직렬화처럼 **순수 로직** |
| 실제 GitHub | 마지막에 `dbsrjs/Nexus` 를 진짜로 한 번 태운다 |

### 가짜 GitHub 이 새로 답해야 하는 것

`/git/trees/{sha}?recursive=1` · `/git/blobs/{sha}` · `/compare/{base}...{head}`.
**받은 요청 수를 세어 예산 단언에 쓴다** — 10-3b 가 "GitHub 을 부르지 않는다"를
케이스로 고정한 것과 같은 장치다.

### 덮어야 할 갈래

- 연결하면 작업이 쌓이고 **워커가 청크를 만든다**
- push 웹훅이 **default 브랜치일 때만** 쌓는다. 다른 브랜치는 아무 일도 없다
- **바이너리 · 256KB 초과 · 생성 파일**이 빠진다
- 검색이 그 내용을 담은 청크를 **1위로** 준다 (`fake` 가 결정적이라 가능하다)
- **다른 스페이스의 저장소는 404**, 검색 결과에 남의 스페이스 청크가 없다
- 증분이 **바뀐 파일만** 다시 만든다 — 안 바뀐 청크의 `commitSha` 가 그대로다
- 지워진 파일 · 이름이 바뀐 파일의 옛 청크가 사라진다
- `compare` 404 면 전체로 떨어진다
- 429 는 시도 횟수로 세지 않고 다시 시도한다. 401 · 404 는 즉시 `failed`
- 돌고 있는 중에 push 가 오면 끝나고 다시 `queued` 가 된다
- provider 미설정이면 서버는 뜨고 작업만 `failed` 로 이유를 남긴다

### 마이그레이션

**새 테이블 하나뿐이다.** 그래도 자동 생성 SQL 은 읽고 커밋한다 —
`DROP INDEX "repo_index_chunks_embedding_hnsw_idx"` 가 섞이는 것을 **네 번**
겪었고, **하필 이번이 그 인덱스를 실제로 쓰는 첫 작업이다.** 지운 채로 가면
벡터 검색이 조용히 순차 스캔으로 떨어진다. `npm run check:migrations` 가 CI 에서
잡지만 그것은 그물이지 절차가 아니다. `prisma migrate dev` 는 이 환경에서
거부되므로 `migrate diff` 로 만들어 손질한다(프로젝트 스킬 `nexus-migration`).

**확인함(2026-09-09)**: `EXPLAIN` 이 `repo_index_chunks_embedding_hnsw_idx` 를
쓰는 것을 실제 DB 로 보았다. 인덱스가 조용히 사라지지 않았다.

## 10. 조각내기

**조각마다 끝나면 확인할 수 있는 것이 있다.** 9단계를 넷으로 자른 선례를 따른다.

| 조각 | 내용 | 끝나면 확인되는 것 |
|---|---|---|
