# 11 PR 열람 — 설계

> 2026-08-30. [10-3a 저장소 열람](2026-08-21-저장소-열람-design.md) ·
> [10-3b 커밋 열람](2026-08-21-커밋-열람-design.md) 을 잇는다.
> **백엔드-설계 §3 · §API 의 두 줄을 뒤집는다** — §0 에 적었다.

10-1 이 PR 이벤트를 채널 한 줄로 흘려보냈다. 여기서 **그 한 줄을 누르면 PR 이
열린다** — 무엇이 바뀌었고, 누가 리뷰했고, 파일 하나를 누르면 그 브랜치 시점의
전문이 보인다.

읽기만 한다. 머지 · 리뷰 · 코멘트 같은 쓰기는 넣지 않는다 — 단계 이름이
"PR 확인"이고, 답글을 못 다는 읽기 전용 대화는 결국 GitHub 으로 가게 된다.

---

## 0. 문서에 적힌 판단 둘을 뒤집는다

### 하나. `pull_requests` 테이블을 쓰지 않는다

백엔드-설계 §3 은 이렇게 적어 두었다 — *"`repo_events`만으로는 PR 목록을 만들 수
없다. 웹훅 수신 시 `repo_events` 적재와 별도로 이 테이블을 upsert한다."*

**진단은 맞지만 처방이 이 프로젝트에 맞지 않는다.** 사본을 두면 셋이 따라온다.

- **연결 전에 열린 PR 이 안 보인다.** 웹훅은 등록 이후부터 온다. 채우려면
  연결 시점에 GitHub 을 한 번 긁는 백필이 필요하고, 그 백필은 실패할 수 있으며,
  실패했을 때 "PR 이 없는 것"과 구분되지 않는다
- **웹훅을 놓치면 행이 영영 어긋난다.** 터널이 죽어 있는 동안 머지된 PR 은
  `open` 인 채로 남는다. 이 프로젝트의 터널은 띄울 때마다 주소가 바뀐다
- **10-2b 가 저장소 목록에서 이미 반대쪽을 골랐다** — *"원본이 GitHub 이라 사본을
  두면 동기화가 곧바로 숙제가 된다."* 같은 성격의 자원을 다르게 다룰 이유가 없다

그래서 **목록도 상세도 GitHub 프록시**다. `pull_requests` 테이블은 스키마에
남지만 이번 단계가 쓰지 않는다. 지우지 않는 이유는 인덱싱 · AI 가 PR 본문을
청킹할 때 다시 볼 값이어서다 — **다만 그때 쓰는 것이지 지금 쓰는 것이 아니다.**

대가는 **오프라인에서 PR 을 볼 수 없다는 것**이다. 파일 목록 · 이슈 댓글 ·
저장소 열람과 같은 취급이라 새로운 종류의 손해는 아니다.

### 둘. `/diff` 가 아니라 `/files`, `/reviews` 는 접어 넣는다

백엔드-설계 §API 는 `/pulls/:number/diff` 와 `/pulls/:number/reviews` 를 적어
두었다. 둘 다 고친다.

- **`/diff` → `/files`.** 10-3b 가 *"diff 를 그리지 않는다 — 파일을 누르면 그
  시점의 전문을 보여준다"* 고 정했고 그 판단을 잇는다. 줄 단위 +/- 렌더러는
  통합 diff 파싱 · 헝크 · 긴 줄 · 접기를 전부 새로 만드는 일이고, **"무엇이
  바뀌었더라"의 대부분은 바뀐 파일 목록이 이미 답한다**
- **`/reviews` 를 따로 두지 않는다.** 상세 응답에 접어 넣는다 — 7-1 이 리액션
  원본 행 대신 요약을 준 것과 같다. 화면이 언제나 둘을 함께 쓰는데 왕복을 둘로
  나눌 이유가 없다

## 1. 목록에는 변경량이 없다

GitHub 의 `GET /repos/{o}/{r}/pulls` 는 **`additions` · `deletions` ·
`changed_files` 를 주지 않는다.** 그 셋은 단건(`/pulls/{n}`)에만 있다.

채우려면 목록의 PR 마다 한 번씩 더 불러야 한다 — 열린 PR 이 스물이면 스물한 번
왕복이다. **하지 않는다.** 10-3b 의 `changedCount` 와 같은 규칙을 쓴다:

> **모르는 것은 0 이 아니라 `null` 이고, 모르면 화면이 아예 말하지 않는다.**

0 으로 채우면 "안 바뀐 PR"로 읽힌다. 변경량은 상세를 열면 보인다.

## 2. API 계약

새 파일 둘 — `repos/pulls.controller.ts` · `repos/pulls.service.ts`.
`repos.controller.ts`(168줄)에 붙이지 않는 이유는 그 파일이 이미 **등록·관리
(POST)와 열람(GET)을 함께** 들고 있어서다. 늘리는 대신 PR 은 자기 파일로 시작한다.

```
GET /api/spaces/:spaceId/repos/:repoId/pulls?state=open&page=1
GET /api/spaces/:spaceId/repos/:repoId/pulls/:number
GET /api/spaces/:spaceId/repos/:repoId/pulls/:number/files
```

**`state` 는 `open` · `closed` 만 받고 기본은 `open` 이다.** 응답의 `state` 는
셋(`open` · `merged` · `closed`)인데 질의 파라미터는 둘이라 헷갈리기 쉽다 —
**머지된 PR 은 `state=closed` 로 조회된다.** GitHub 이 그렇게 나누고, 목록을
부를 때 머지 여부로 거를 방법이 없기 때문이다. 화면의 필터도 «열림 · 닫힘»
둘이고, 닫힘 안에서 머지된 것은 칩으로 구분된다.

`SpaceGuard` 만 건다. **`@MinRole` 을 걸지 않는 것은 10-3a 의 판단**이다 —
걸면 코드를 볼 수 있는 사람과 저장소 설정을 바꿀 수 있는 사람이 같아진다.

토큰은 **그 순간 요청한 사람의 것**을 쓴다(10-2b). 등록자를 따로 기록해 두면
그 사람이 연결을 해제한 순간 아무도 PR 을 못 보게 된다.

### 응답 — GitHub 원본을 그대로 흘리지 않는다

`_links` · `diff_url` · `patch_url` 은 뺀다. **`html_url` 은 싣는다** —
10-3a 가 `download_url` 을 뺀 이유는 그것이 토큰이 있어야 열리는 주소여서지,
공개 주소인 `html_url` 은 "GitHub 에서 열기"에 필요하다.

목록 한 건:

```jsonc
{
  "number": 12,
  "title": "…",
  "state": "open",          // open · merged · closed
  "draft": false,
  "authorLogin": "dbsrjs",
  "authorAvatarUrl": "https://…",
  "sourceBranch": "feat/x",  // head.ref
  "targetBranch": "main",    // base.ref
  "htmlUrl": "https://github.com/…/pull/12",
  "openedAt": "…", "mergedAt": null, "closedAt": null
}
```

**`state` 는 GitHub 의 `state` 를 그대로 쓰지 않는다.** GitHub 은 `open` ·
`closed` 둘뿐이고 머지 여부는 `merged_at` 에 있다. 머지와 그냥 닫힘은 사람에게
전혀 다른 일이라 **셋으로 갈라 준다**(스키마의 `PullRequestState` 와 같은 어휘).

상세는 여기에 `body` · `additions` · `deletions` · `changedFiles` · `review` 가
붙는다.

### `review` — 리뷰어마다 마지막 것만 센다

`/pulls/{n}/reviews` 는 리뷰를 **시간순으로 전부** 준다. 같은 사람이 변경을
요청했다가 나중에 승인하면 두 행이 다 남는다. 그대로 세면 승인과 변경 요청이
동시에 뜬다.

**리뷰어마다 마지막 것만 남기고, `COMMENTED` · `DISMISSED` 는 둘 중 어느 쪽도
아니므로 버린다.** 그렇게 접은 뒤:

| 남은 것 | `review` |
|---|---|
| 하나라도 `CHANGES_REQUESTED` | `changes_requested` |
| 그 외에 `APPROVED` 가 있음 | `approved` |
| 아무것도 없음 | `null` |

**`null` 은 `pending` 이 아니라 "그릴 것이 없음"이다.** 혼자 쓰는 저장소에서는
늘 이 값이고, 화면은 그때 **리뷰 칸을 아예 만들지 않는다**(10-3b 의 "모르면
말하지 않는다"와 같은 규칙).

### `files` — `patch` 를 보내지 않는다

GitHub 은 파일마다 `patch`(통합 diff 원문)를 함께 준다. **앱에 보내지 않는다.**
diff 를 그리지 않으므로 쓸 곳이 없고, 응답만 몇 배로 커진다.

```jsonc
{ "path": "app/lib/…/x.dart", "status": "modified",
  "additions": 12, "deletions": 3, "previousPath": null }
```

**필드 이름을 10-3b 의 `ChangedFile` 에 맞춘다**(`filename` 이 아니라 `path`).
커밋 상세가 이미 그 모양이라, 같게 두면 앱이 파일 목록 위젯을 한 벌로 쓴다 —
다르게 두면 보이는 것이 같은데 코드가 둘이 된다.

`status` 는 `added` · `modified` · `removed` · `renamed`. **`removed` 는 앱에서
누를 수 없다** — head 시점에 없어 열어도 404 다(10-3b 와 같은 규칙).

**상한 300개, 넘으면 `truncated: true`.** GitHub 자체가 3000개에서 끊고
페이지당 100개다. 커서를 새로 만드는 대신 상한을 두되 **조용히 자르지 않는
것**이 9-1 에서 정한 조건이다.

### 페이지네이션 · 실패

목록은 **GitHub 의 페이지 번호를 그대로 노출한다**(10-2b 와 같다). 커서를 새로
만들 이유가 없다.

- 연결 없음 · 토큰 없음 → **503**(10-2b 와 같은 분기). 화면은 "GitHub 을
  연결하세요"로 떨어진다
- GitHub 404 → **404**. 없는 PR 번호와 볼 수 없는 저장소를 구분하지 않는다
- 429 → **`Retry-After` 를 HTTP 헤더로** 내보낸다. 본문에 실으면 전역 예외
  필터가 봉투를 다시 빚으며 버린다 — 10-3a 에서 실제로 겪었다

## 3. `GET /repo-events/:eventId` 의 모양을 바꾼다

지금은 이벤트 종류와 무관하게 **커밋을 돌려준다.** 10-3b 가 *"PR · 이슈 이벤트
메시지를 눌렀을 때는 화면으로 보지 않았다"* 고 남긴 자리다.

이벤트 종류로 갈라 준다.

```jsonc
{ "kind": "push", "repoId": "…", "commits": [ … ] }
{ "kind": "pr",   "repoId": "…", "number": 12 }
{ "kind": "other", "repoId": "…" }          // 이슈 · 릴리스
```

앱은 `kind` 로 커밋 화면과 PR 화면 중 하나를 연다. **`other` 는 누를 수 없다** —
눌러 봐야 빈 화면인 버튼은 없느니만 못하다(7-5 에서 답글 고정을 시트에서 감춘
것과 같다).

**PR number 는 `repo_events.payload` 에 이미 있다.** 그래서 이 진입 자체는
GitHub 을 부르지 않는다 — 10-3b 가 커밋에서 세운 규칙이 그대로 이어진다.

## 4. 앱

`browse_screen` 앱바에 아이콘을 하나 더 둔다 — 커밋 아이콘 바로 옆이다.

**`TabBar` 로 묶지 않는다.** `browse_screen` 은 경로와 브랜치라는 자기 상태를
들고 있어, 탭으로 묶으면 그 상태가 전환마다 흔들린다. 커밋이 이미 아이콘 →
별도 라우트로 되어 있어 모양도 그쪽에 맞춘다.

```
/s/:spaceId/repos/:repoId/pulls            목록 (열림 · 닫힘 필터)
/s/:spaceId/repos/:repoId/pulls/:number    상세 + 바뀐 파일
```

- **캐시하지 않는다.** 저장소 열람 · 이슈 댓글과 같은 취급이라
  `schemaVersion` 을 올리지 않는다
- 본문은 `MarkdownBody` 로 그린다 — PR 본문은 마크다운으로 쓰인다
- 파일을 누르면 **10-3a 의 파일 보기가 head 브랜치로 열린다.** 새 화면이 없다
- 목록에 변경량을 그리지 않는다(§1)

## 5. 검증

`npm run check:pulls` 를 새로 만들고 **가짜 GitHub(4599)** 을 띄운다 —
`check:browse` 와 같은 방식이라 진짜 GitHub 없이 돈다.

덮을 것:

- 테넌트 격리 — 타 스페이스의 저장소는 404
- 미연결 503 · 없는 번호 404 · 429 의 `Retry-After` **헤더**
- **응답에 `patch` 가 없다** · `_links` · `diff_url` 이 없다 · `htmlUrl` 은 있다
- `state` 셋으로 갈림 — 특히 **머지된 것이 `closed` 가 아니라 `merged`**
- 리뷰 접기 — 같은 사람이 변경 요청 후 승인하면 `approved`, `COMMENTED` 만
  있으면 `null`
- 파일 상한 초과 시 `truncated`
- **PR 이벤트를 조회하면 커밋이 아니라 `kind: "pr"` 과 number 가 온다**

앱은 모델 파싱과 화면 위젯 테스트. 9-3 에서 서버만 만들고 화면을 빠뜨린 채
완료로 보고한 일이 있어, **화면이 없으면 실패하는 테스트**를 함께 둔다.

## 6. 범위에서 뺀 것

| 뺀 것 | 이유 |
|---|---|
| 쓰기 — 머지 · 리뷰 · 코멘트 | 단계 이름이 "PR 확인"이다. 쓰기는 권한 · 실패 처리 · 낙관적 갱신을 통째로 끌고 온다 |
| 줄 단위 diff 렌더 | §0 |
| PR 의 커밋 목록 | 채널의 push 메시지 → 10-3b 로 가는 **중복 경로**가 이미 있다. 위젯이 있으니 나중에 붙이는 비용도 싸다 |
| 대화(코멘트) 읽기 | 답글을 못 달면 결국 GitHub 으로 간다 |
| 스페이스 전체 PR 대시보드 | 저장소가 여럿일 때 값이 생긴다. 지금은 저장소마다 GitHub 을 한 번씩 부르는 비용만 남는다 |
| `pull_requests` upsert | §0 |
