# 13-3 AI 멀티턴 — 설계

> 2026-09-23. [13-2 AI 패널 설계](2026-09-23-13-2-ai-패널-design.md) 의 D9(「멀티턴은
> 다음 단계. `input` 이 자기완결이라 `parentRunId` 하나를 더하면 된다」)를 연다.
> 13-2 의 API · 컨텍스트 조립 · 캐시 · 인용은 그대로이고 이 문서는 그 위에 얹는다.

---

## 0. 무엇이 바뀌나

| | 13-2 | 13-3 |
|---|---|---|
| 한 번의 문답 | 질문 하나 → 답 하나로 끝 | 답 아래에서 **이어서 묻는다** |
| 「다시 묻기」 | 같은 칩으로 입력창만 돌아온다 | 그대로 둔다 — **새 대화**를 시작하는 버튼이 된다 |
| LLM 에 가는 것 | system + user 하나 | system + user(자료 + 첫 질문) + assistant + user + … |

### 정한 것

| # | 결정 | 이유 |
|---|---|---|
| D1 | **`POST /ai/ask` 에 `parentRunId` 를 더한다.** 새 엔드포인트를 만들지 않는다 | 후속 질문도 「지시문 하나를 묻는 것」이다. 13-2 D1(경로를 늘리지 않는다)과 같다 |
| D2 | 후속 질문은 **`instruction` 만** 받는다. `preset` · `context` 와 함께 오면 400 | 근거(컨텍스트)는 사슬의 첫 문답에서 **물려받는다.** 두 곳에서 받으면 어느 쪽이 진짜인지 규칙이 생긴다 |
| D3 | LLM 에 **역할을 나눈 진짜 멀티턴**으로 보낸다(`assistant` 역할 추가) | 앞 답을 문자열로 붙이면 모델이 「앞 답」과 「자료」를 섞는다. 역할 번역은 어댑터 안에서 끝난다(Gemini `model` · Ollama `assistant`) |
| D4 | **자료(대화 · 코드)는 첫 문답의 것을 그대로 쓴다.** 후속 질문마다 저장소를 다시 검색하지 않는다 | ① `[n]` 인용 번호가 사슬 전체에서 같은 코드를 가리킨다 ② 캐시 키가 재현된다 ③ 임베딩 호출이 늘지 않는다. 다른 코드를 보고 싶으면 「다시 묻기」로 새로 묻는다 |
| D5 | 사슬 길이 상한 **10 문답**(첫 문답 + 후속 9). 넘으면 400 | 조용히 앞을 잘라 내지 않는다(판단 #4). 무료 한도(하루 20회)에서 10 이면 넉넉하다. 앱이 먼저 입력을 막는다 |
| D6 | 후속 질문을 달 수 있는 부모는 **`done` 이고 `kind` 가 `summarize` · `ask`** 인 것 | 이슈 초안(JSON)에 이어 물으면 답이 마크다운이 되어 「이슈 만들기」로 이어지지 않는다. 이슈 초안은 「다시 묻기」로 |
| D7 | 부모는 **같은 스페이스 · 같은 사용자**의 것만. 아니면 404 | 13-2 의 getRun 규칙(본인 것만) 그대로. 남의 문답에 이어 묻는 길은 남의 문답을 읽는 길이다 |
| D8 | 후속 답의 `kind` 는 `ask`, `citations` 는 **첫 문답의 인용 그대로** | D4 의 결과. 후속 답의 `[n]` 이 같은 링크로 풀린다 |
| D9 | 캐시는 **그대로 `promptHash`** 다 | 해시가 앞 문답 전체를 포함한 메시지를 보므로, 같은 부모에 같은 질문이면 적중하고 부모가 다르면 갈린다. 규칙을 새로 만들지 않는다 |
| D10 | 사슬은 **앱 패널의 상태로만** 들고 있다. 닫으면 사라진다 | 서버에는 행이 남지만 「지난 대화 목록」 은 범위 밖이다(§6). 13-2 의 「drift 에 넣지 않는다」와 같다 |
| D11 | 「채널에 붙이기」 · 「복사」는 **마지막 답만** | 문답 전체를 채널에 붙이면 시끄럽다. 필요한 답에서 다시 누르면 된다 — 각 답마다 버튼을 두지 않고 마지막에만 둔다 |

## 1. API

```
POST /api/spaces/:spaceId/ai/ask
{
  instruction: string,        // 1~2000자
  parentRunId: string,        // 이어 물을 문답
}
→ 201 { runId, state: 'queued' | 'done' }
```

첫 질문은 13-2 그대로(`instruction` | `preset` + `context`).

### 검증

| 조건 | 응답 |
|---|---|
| `parentRunId` 와 `preset` 이 함께 | 400 |
| `parentRunId` 와 `context` 가 함께 | 400 |
| `parentRunId` 가 없는데 `context` 도 없음 | 400(13-2 그대로) |
| 부모가 없음 · 다른 스페이스 · 다른 사용자 | 404 |
| 부모가 `done` 이 아님 | 400 「앞 답이 아직 끝나지 않았습니다」 |
| 부모 `kind` 가 `draft_issue` | 400 |
| 사슬이 이미 10 문답 | 400 |

DTO 의 `context` 는 `@IsOptional` 로 바뀐다. 조합 규칙은 13-2 처럼 `validateAskRequest` 가 본다.

## 2. 저장

`ai_runs.parent_run_id` — 같은 테이블을 가리키는 nullable FK, `onDelete: Cascade`
(부모 없는 후속 문답은 프롬프트를 다시 만들 수 없다). 인덱스를 둔다.

후속 문답의 `input`:

```ts
{ instruction: string, parentRunId: string }
```

**자료는 복사하지 않는다.** 워커가 사슬을 거슬러 올라가 첫 문답의 `input` 에서
자료를 다시 읽는다 — 13-2 의 「적재 시점에 확정된 것만」 원칙은 그대로다. 앞
문답들의 `result` 는 `done` 이 된 뒤 바뀌지 않으므로 사슬도 확정돼 있다.

## 3. 프롬프트

사슬 `[첫 문답, …, 부모]` + 새 질문 → 메시지:

```
system  : 첫 문답 종류의 system (요약이면 summarize, 아니면 ask)
user    : 첫 문답의 user (자료 + 첫 요청)       ← 13-2 의 buildAskPrompt 그대로
assistant: 첫 문답의 답(markdown)
user    : 두 번째 질문
assistant: 두 번째 답
…
user    : 새 질문
```

- 첫 문답이 프리셋 요약이어도 그대로 이어진다. 요약 system 은 「세 항목 양식」을
  강제하므로 **후속 질문에는 `ask` 의 system 을 쓴다** — system 은 하나뿐이라
  첫 문답의 것을 쓰면 후속 답이 모두 세 항목 양식으로 굳는다. 요약의 user 는
  「다음 대화를 요약해 줘」 요청과 대화를 함께 담고 있어(`summarize.ts`) system 을
  바꿔도 첫 문답이 그대로 읽힌다 — 세 항목 양식은 이미 assistant 의 답에 들어 있다
- 조립은 **순수 함수** `buildFollowUpPrompt(chain, instruction)` 하나다. 적재(해시)와
  워커(실행)가 같은 것을 부른다 — 13-2 의 `buildAskPrompt` 와 같은 규칙
- 앞 답이 전환 모델(`fallback`)의 것이어도 그대로 싣는다

## 4. 어댑터

`LlmMessage.role` 에 `'assistant'` 를 더한다.

| 어댑터 | 번역 |
|---|---|
| Gemini | `contents` 를 **메시지마다 하나씩**, `assistant` → `role: 'model'`. 지금처럼 user 를 한 덩어리로 합치지 않는다 |
| Ollama | 이미 `role` 을 그대로 넘긴다 — 바꿀 것 없음 |
| fake | 모든 메시지를 해시하므로 그대로 결정적이다 |

## 5. 앱

패널의 결과 화면이 **문답 목록**이 된다.

```
┌ AI ────────────────────────────────┐
│ [💬 메시지 12개] [📦 nexus]             │  ← 칩(읽기 전용)
│                                      │
│ 요약                                  │  ← 첫 요청(프리셋 이름 또는 지시문)
│ ### 정해진 것 …                        │
│                                      │
│ 담당자별로 다시 정리해 줘                  │  ← 후속 질문
│ …                                    │
│ ┌──────────────────────────────┐   │
│ │ 이어서 묻기                        │   │  ← 사슬이 10 이면 안내로 바뀐다
│ └──────────────────────────────┘   │
│ [다시 묻기] [복사] [채널에 붙이기] [보내기] │
└──────────────────────────────────────┘
```

- 패널이 `List<AiTurn>`(질문 문구 · `AiRun`)을 든다. 답이 오면 덧붙인다
- 후속 질문을 보내는 동안에는 지난 문답을 그대로 보이고 아래에 스피너를 둔다
- 실패하면 그 질문만 실패로 보이고 **지난 문답은 남는다.** 다시 보내면 같은 부모로 간다
- 이슈 초안이 첫 답이면 「이어서 묻기」 입력을 두지 않는다(D6)
- 「다시 묻기」는 사슬을 비우고 같은 칩으로 첫 입력 화면에 돌아간다(13-2 그대로)

## 7. 검증

### `check:ai`

| 갈래 | 케이스 |
|---|---|
| 완주 | 자유 질문 → 후속 질문 → `done` · `kind: ask` · `parentRunId` 기록 |
| 요약에 이어 묻기 | 프리셋 요약 부모에 후속 질문 완주 |
| 캐시 | 같은 부모 + 같은 질문 → 같은 `runId` · 부모가 다르면 다른 `runId` |
| 검증 400 | `parentRunId` + `preset` · `parentRunId` + `context` · 이슈 초안 부모 · 끝나지 않은 부모 · 사슬 11번째 |
| 권한 404 | 다른 사용자의 부모 · 없는 부모 |

### `check:indexing`

저장소 컨텍스트 첫 질문에 후속 질문 → 후속 답의 `citations` 가 **첫 답과 같다**.

### 단위

`buildFollowUpPrompt`(역할 순서 · system 선택 · 자료가 첫 user 에만) · 사슬
길이 판정 · Gemini 의 역할 번역(`assistant` → `model`, 메시지마다 한 content).

### 앱

위젯 — 첫 답 아래 「이어서 묻기」 · 보내면 문답이 두 개 · 후속 실패 시 지난 답이
남음 · 이슈 초안이면 입력 없음 · 사슬 10 이면 안내.

### 실제 태우기

실제 Gemini 로 「요약 → 담당자별로 다시」 · 「코드 질문 → 그 함수를 부르는 곳」
두 사슬. **2026-09-23 현재 Gemini 키가 402(선불 크레딧 소진)라 막혀 있다** — 풀리면 태운다.
