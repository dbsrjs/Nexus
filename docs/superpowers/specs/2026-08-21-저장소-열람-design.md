# 10-3 저장소 열람 — 설계

> 2026-08-21. [백엔드-설계.md](../../백엔드-설계.md) §7.3 과 §4 의 API 계약을 구현한다.
> **그 문서와 갈라지는 지점이 하나 있다(캐시) — §3 에서 그 문서를 고칠 근거를 적었다.**

저장소를 붙여 두면 커밋이 채널로 들어온다(10-1 · 10-2). 이제 **그 저장소 안을
들여다본다** — 브랜치를 고르고, 폴더를 타고, 파일을 연다.

---

## 0. 자르기 — 한 조각이 끝나면 화면에 뭔가 보인다

| 조각 | 내용 | 진입점 |
|---|---|---|
| **10-3a** | `branches` · `tree` · `blob` + 앱 탐색 화면 | 저장소 목록의 행 |
| 10-3b | `commits` + 커밋 상세 | 채널의 커밋 메시지 |

**이 문서는 10-3a 를 정한다.** 10-3b 는 커밋 단건의 변경 파일 목록이 필요한데
그 계약이 백엔드-설계에 없어(있는 것은 `pulls/:number/diff` 뿐이다) 그때 따로 정한다.

둘로 자른 이유는 쓰임이 다르기 때문이다. **탐색은 "그 파일 어떻게 생겼더라"이고,
커밋은 "무엇이 바뀌었더라"다.** 전자는 저장소에서 들어가고 후자는 대화에서
들어간다 — 화면은 파일 보기를 공유하지만 그리로 가는 길이 다르다.

---

## 1. GitHub API 를 어떻게 쓰나 — contents 하나로

`GET /repos/{owner}/{repo}/contents/{path}?ref=` 는 **경로가 디렉터리면 항목
배열을, 파일이면 base64 본문을 준다.** 우리 `tree` 와 `blob` 이 같은 호출을
쓰고 응답만 다르게 빚는다.

대안이었던 `git/trees` + `git/blobs` 를 쓰지 않는 이유는 둘이다.

- **경로를 sha 로 바꾸는 호출이 매번 하나 더 필요하다.** 사람은 경로로
  탐색하는데 그 API 는 sha 로 말한다
- **재귀 트리는 큰 저장소에서 수만 항목이 온다.** 한 단계씩 들어가는 화면에
  필요한 것은 그 폴더의 목록뿐이다

**contents API 는 1MB 를 넘는 파일의 본문을 주지 않는다.** 이것이 제약처럼
보이지만, 우리는 이미 "임계값을 넘으면 본문 대신 메타데이터만"(백엔드-설계
§7.3)이라고 정해 두었다 — **두 규칙이 같은 자리에서 만난다.** 큰 파일을 실제로
열어 볼 이유가 생기면 그때 `git/blobs` 폴백을 더한다.

브랜치 목록은 `GET /repos/{owner}/{repo}/branches?per_page=100` 이다.

## 2. API 계약

```
GET /api/spaces/:spaceId/repos/:repoId/branches
GET /api/spaces/:spaceId/repos/:repoId/tree?ref=&path=
GET /api/spaces/:spaceId/repos/:repoId/blob?ref=&path=
```

셋 다 `SpaceGuard` 아래다. **볼 수 없으면 403 이 아니라 404.**

**`ref` 를 비우면 저장소의 기본 브랜치**다. 앱이 첫 화면을 그릴 때 브랜치
목록을 먼저 받지 않아도 되도록 — 두 번 왕복하면 화면이 두 번 튄다. `repos`
행의 `defaultBranch` 를 쓰고, 그것도 비어 있으면 GitHub 이 주는 값을 쓴다.

**`path` 를 비우면 저장소 루트**다. `blob` 에서 `path` 는 필수다 — 루트는
파일이 아니다(400).

### 응답

```jsonc
// branches
{ "branches": [{ "name": "main", "protected": false }], "defaultBranch": "main" }

// tree — 디렉터리 하나의 목록. 폴더가 먼저, 그 안에서 이름순.
{ "ref": "main", "path": "server/src", "entries": [
  { "name": "oauth", "path": "server/src/oauth", "type": "dir", "size": null },
  { "name": "main.ts", "path": "server/src/main.ts", "type": "file", "size": 1820 }
]}

// blob — 본문이 있을 때
{ "path": "server/src/main.ts", "size": 1820, "content": "…", "omitted": null }

// blob — 본문이 없을 때
{ "path": "assets/logo.png", "size": 20480, "content": null, "omitted": "binary" }
```

**GitHub 원본을 그대로 흘리지 않는다.** 필요한 것만 빚어 내려보낸다 — 원본에는
`_links` · `git_url` · `download_url` 처럼 **토큰이 있어야 열리는 주소**가 섞여
있고, 그것을 앱에 흘리면 "서버를 통해서만 나간다"는 전제가 새는 자리가 된다.

### `omitted` — 본문이 없는 세 경우를 구분한다

| 값 | 뜻 | 화면 문구 |
|---|---|---|
| `binary` | 텍스트가 아니다 | "미리 볼 수 없는 파일입니다" |
| `too_large` | 우리 임계값(**512KB**)을 넘었다 | "파일이 큽니다 (1.2MB)" |
| `unavailable` | 임계값 안인데 GitHub 이 본문을 주지 않았다 | "GitHub 이 본문을 주지 않았습니다" |

**`too_large` 가 `unavailable` 보다 먼저다.** 우리가 자른 것을 GitHub 탓으로
돌리지 않는다. 그래서 **GitHub 이 본문을 주지 않는 1MB 초과는 `unavailable` 이
아니라 `too_large` 로 온다** — 512KB 에서 이미 걸리기 때문이다.

그러면 `unavailable` 은 언제 나오나. **GitHub 이 작은 파일의 본문을 생략하는
예상 밖의 경우**뿐이다. 드물지만 없애지 않는 이유는, 그때 `content: null` 을
그대로 내려보내면 앱이 **빈 파일로 오해**하기 때문이다. 도달 빈도가 낮은 것과
필요 없는 것은 다르다.

**하나로 뭉치지 않는 이유는 사용자가 할 수 있는 일이 다르기 때문이다.**
바이너리는 영영 못 보고, 큰 파일은 GitHub 에서 열면 되고, `unavailable` 은
우리가 나중에 폴백을 붙이면 풀린다. 셋을 "볼 수 없습니다" 하나로 합치면 그
차이가 사라진다.

**바이너리 판별은 내용으로 한다** — 디코딩한 바이트에 NUL 이 있거나 UTF-8 로
읽히지 않으면 바이너리다. 확장자 목록은 유지 비용이 끝없이 늘고(`.ts` 가
TypeScript 인지 MPEG 스트림인지 확장자는 모른다), 목록에 없는 것이 나올 때마다
고쳐야 한다.

**512KB 임계값을 GitHub 의 1MB 보다 낮게 잡는 이유**는 그만한 텍스트를 앱이
받아 그리는 것이 이미 무의미하기 때문이다 — 등폭으로 그리면 만 줄이 넘는다.

### 권한 — 읽기는 스페이스 멤버면 된다

저장소를 **붙이는 것**은 `admin` 이다(10-1 · 10-2b). 그 채널에 남의 서비스가
글을 쓰게 하는 일이라 스페이스의 뼈대를 바꾸는 쪽이기 때문이다.

**보는 것은 다르다.** 이슈를 열람하는 것과 같은 무게라 `SpaceGuard` 만 지나면
된다. 여기에 `@MinRole('admin')` 을 걸면 팀에서 코드를 볼 수 있는 사람과 저장소
설정을 바꿀 수 있는 사람이 같아진다.

### 실패

- **토큰이 없으면 400** — "GitHub 계정을 먼저 연결해야 합니다"(10-2b 의 목록과 같다)
- **429 는 `Retry-After` 를 붙여 그대로 전달한다**
- GitHub 404(브랜치·경로 없음)는 **404 로 전달한다**. 저장소 자체가 없는 것과
  구분되지 않지만, 앱이 할 일은 어느 쪽이든 "찾을 수 없습니다"다
- 그 밖(네트워크 실패 · 5xx)은 **502**

## 3. 캐시 — 두지 않는다 (백엔드-설계 §7.3 을 고친다)

백엔드-설계 §7.3 은 "응답은 Redis 에 짧게 캐싱한다(트리·블롭 5분, 커밋·브랜치
60초)"라고 적혀 있다. **10-3a 는 캐시를 두지 않는다.** 그 문장을 이 결정으로
고친다.

이유 셋.

- **Redis 가 이 프로젝트에 없다.** `ioredis` 가 package.json 에 있고
  `redis-io.adapter.ts` 도 있지만 tsconfig 에서 제외돼 있다(다중 인스턴스가 될
  때 되살린다). 캐시를 위해 Redis 를 들이면 `db:up` 처럼 **새 PC 셋업 절차가
  하나 더 늘고**, 그것이 안 떠 있을 때 열람이 통째로 죽는 실패 모드가 생긴다
- **rate limit 이 문제가 아니다.** 인증 상태 GitHub API 는 시간당 5000회다.
  폴더를 한 번 열 때 1회이므로 개인 프로젝트 사용량에서 닿지 않는다
- **캐시는 새 문제를 만든다.** "코드를 고쳤는데 옛 것이 보인다"는 열람 기능에서
  가장 나쁜 종류의 오해다. 5분이면 짧아 보이지만, 방금 push 한 것을 확인하려고
  여는 순간이 정확히 그 5분이다

인메모리 캐시도 두지 않는다. 다중 인스턴스가 되면 **인스턴스마다 다른 것을
보이게** 되어, 지금 아끼는 것보다 나중에 걷어내는 비용이 크다.

캐시가 필요해지는 신호는 **rate limit 을 실제로 만나는 것**이다. 그때는
Redis 를 들이고 §7.3 의 원안으로 돌아간다.

## 4. 앱 — 탐색 화면 하나

저장소 목록(10-2b)의 행을 누르면 열린다. 라우트는
`/s/:spaceId/repos/:repoId/browse`.

**세 층이 한 화면 안에서 바뀐다.**

1. **브랜치** — 상단 드롭다운. 기본값은 `defaultBranch`
2. **경로** — 빵부스러기(`server / src / oauth`). 폴더를 누르면 들어가고,
   빵부스러기를 누르면 그 위로 나온다
3. **목록 또는 파일** — 경로가 디렉터리면 목록, 파일이면 본문

**뒤로 가기는 라우트가 아니라 경로 상태를 되돌린다.** 폴더를 열 때마다 라우트를
쌓으면 다섯 단계 들어간 뒤 저장소로 나오는 데 다섯 번을 눌러야 한다.

- **캐시하지 않는다.** 저장소 목록 · 파일 목록 · 이슈 댓글과 같은 판단이다
  (앱-설계 §9). drift 를 건드리지 않으므로 `schemaVersion` 도 그대로다
- **파일은 등폭 폰트 + 줄 번호로 그린다.** ~~신택스 하이라이팅은 넣지 않는다~~
  → **2026-08-21 에 뒤집었다.** 실제로 써 보니 흑백이 읽기 어려웠다.
  다만 **패키지를 들이지는 않았다** — `features/repo/code_highlight.dart` 에
  주석 · 문자열 · 숫자 · 키워드 넷만 칠하는 **언어 공통 규칙**을 직접 뒀다.
  그 넷은 Dart · TypeScript · Python · Java 가 거의 같아서 언어를 몰라도
  흑백보다 훨씬 읽히고, 언어별 정확도를 쫓으면 규칙 표를 계속 들고 있어야
  한다. 색은 테마 토큰에서 파생시킨다(하이라이터가 자기 팔레트를 들면
  라이트/다크 전환에서 혼자 어긋난다). 9-3 에서 차트 라이브러리 대신
  `CustomPainter` 를 쓴 것과 같은 판단이다
- **긴 줄은 접지 않고 가로로 스크롤한다.** 접으면 줄 번호와 내용이 어긋나 코드를
  읽을 수 없다
- **본문이 없으면 `omitted` 를 그대로 문구로 옮긴다**(§2 의 표)

## 5. 검증

**계약 검증은 `check:oauth` 에 더하지 않고 새로 만든다** — `npm run check:browse`.
그 스크립트는 이미 76개로 커졌고 연결 · 등록이 주제다. 열람은 읽기 전용이라
섞을 이유가 없다.

가짜 GitHub 은 10-2b 와 같은 방식으로 띄운다(`GITHUB_API_BASE`).

| 갈래 | 케이스 |
|---|---|
| 브랜치 | 목록 · `defaultBranch` · 토큰 없으면 400 |
| 트리 | 디렉터리 목록 · **폴더가 먼저** · 없는 경로 404 · 없는 ref 404 |
| 파일 | 본문 · **원본의 `download_url` 이 응답에 없다** |
| 생략 | 바이너리(NUL) · 512KB 초과 · GitHub 이 본문을 안 준 경우 — **셋이 다른 `omitted`** |
| 실패 | 429 에 `Retry-After` · 5xx 는 502 |
| 격리 | 남의 스페이스 저장소는 셋 다 404 |

**앱은 위젯 테스트로 분기를 고정한다** — 디렉터리 목록 · 파일 본문 · `omitted`
세 종류의 문구. 9-3 에서 화면을 빠뜨린 채 완료로 보고한 일이 있었다.

## 6. 범위에서 뺀 것

| 뺀 것 | 이유 |
|---|---|
| 커밋 목록 · 커밋 상세 | **10-3b** |
| PR diff · 리뷰 | 11단계 |
| 파일 검색 | GitHub 코드 검색은 또 다른 API 이고 rate limit 도 따로다 |
| 편집 · 커밋 | 열람이다. 쓰기는 이 제품의 방향이 아니다 |
| 큰 파일 `git/blobs` 폴백 | 실제로 열어 볼 이유가 생기면(§1) |
| 캐시 | rate limit 을 실제로 만나면(§3) |
| GitLab | 두 번째 provider 가 필요해질 때 그 모양이 정해진다(10-2 와 같은 판단) |
