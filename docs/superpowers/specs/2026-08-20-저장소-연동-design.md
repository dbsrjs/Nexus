# 10단계 — 저장소 연동 설계

> 2026-08-20. 계약은 [백엔드 설계 §7](../../백엔드-설계.md), 데이터 모델은 §3.
> 이 문서는 **계약이 정하지 않은 것**과 **거기서 갈라진 것**만 적는다.

---

## 0. 자르기 — 외부 의존이 없는 것부터

10단계는 지금까지와 성격이 다르다. **GitHub 이라는 남의 서비스**가 걸려 있어,
사람이 계정에 무언가를 등록해 주어야 하는 구간이 있다. 그 구간이 전체를
막지 않도록 **외부 의존이 없는 것을 앞으로 당긴다.**

| 조각 | 밖에서 필요한 것 | 내용 |
|---|---|---|
| **10-1** | **없음** | 웹훅 수신 · 서명 검증 · `repo_events` 적재 · **채널에 이벤트 메시지** |
| 10-2 | GitHub OAuth 앱 | OAuth 연결 · 저장소 목록 · 웹훅 자동 등록 |
| 10-3 | OAuth 토큰 | 브랜치 · 트리 · 파일 열람 프록시 |

**10-1 은 저장소를 수동으로 등록한다.** GitHub 저장소 설정에서 웹훅 URL 과
시크릿을 사람이 직접 붙이는 방식이다. 이 길은 10-2 이후에도 남긴다 —
설계 §7.1 이 말하는 "웹훅을 등록할 수 없는 환경"의 대비책이 곧 이것이다.

**마이그레이션이 없다.** `repos` · `repo_events` · `pull_requests` 는 2단계에
이미 만들어 뒀다.

---

## 1. 시스템 메시지의 작성자

`Message.authorId` 는 **필수**다. 저장소 이벤트는 사람이 쓴 것이 아닌데
작성자가 있어야 한다. 셋 중에서 골랐다.

| | 방법 | 대가 |
|---|---|---|
| **택함** | **시스템 사용자 한 명**이 작성자가 된다 | 사용자 테이블에 봇 행 하나 |
| | `authorId` 를 nullable 로 + `kind` 컬럼 | 가장 정직하지만 **가장 뜨거운 테이블**을 건드리고 앱 모델 · 캐시 · 큐 · 멘션 렌더까지 파급된다 |
| | 스페이스마다 봇 | 스페이스가 늘 때마다 봇이 는다 |

**봇은 스페이스 멤버가 아니다.** 멤버 목록도 멘션 자동완성도 `space_members`
를 보므로 거기 끼지 않는다 — 사용자 행이 있다는 것과 그 스페이스의 사람이라는
것은 다르다. 메시지 작성자 FK 는 `users` 를 가리키므로 그것만으로 충분하다.

봇은 **provider 마다 하나**다(`GitHub` · 나중에 `GitLab`). 이벤트 메시지의
작성자 이름이 곧 어디서 왔는지를 말해 준다.

봇 계정은 **로그인할 수 없다.** 비밀번호 해시 자리에 로그인으로는 만들 수 없는
값을 넣는다 — 봇이 사람처럼 로그인되면 그 계정으로 아무 데나 들어갈 수 있다.

## 2. 웹훅 수신

```
POST /api/webhooks/:provider/:repoId      @Public — 서명이 곧 인증이다
```

**`@Public()` 이지만 아무나 부를 수 있는 것은 아니다.** GitHub 이 보내는
`X-Hub-Signature-256` 을 저장소마다 다른 시크릿으로 검증한다. JWT 를 요구할 수
없는 이유는 부르는 쪽이 GitHub 이기 때문이다.

- **원문 바이트로 검증한다.** 파싱된 객체를 다시 직렬화해 HMAC 을 계산하면
  키 순서 · 공백 · 유니코드 이스케이프가 달라져 **멀쩡한 요청이 위조로 판정된다.**
  Nest 의 body parser 를 이 라우트에서만 우회해 원문을 들고 있어야 한다
- **타이밍 안전 비교**를 쓴다(`crypto.timingSafeEqual`). 문자열 `===` 는 앞에서
  몇 글자가 맞았는지가 시간으로 새 나간다
- **서명이 틀리면 401**, 저장소를 못 찾으면 404. 둘을 같은 코드로 뭉개지 않는다 —
  붙이는 사람이 무엇이 틀렸는지 알아야 한다
- **모르는 이벤트 타입은 200 으로 조용히 넘긴다.** GitHub 은 실패를 재시도하고,
  우리가 안 쓰는 이벤트에 계속 실패를 돌려주면 저장소 설정 화면이 빨갛게 된다.
  적재도 하지 않는다 — 쓰지 않을 payload 로 테이블을 불릴 이유가 없다

### 한 트랜잭션으로 묶는 것

설계 §7.2 는 셋을 한 트랜잭션에서 처리하라고 한다. **적재와 메시지 게시까지
둘을 묶는다.** 사이에서 끊기면 "이벤트는 왔는데 채널에는 없는" 상태가 되고,
그건 재시도로도 낫지 않는다(GitHub 은 200 을 받았으므로 다시 보내지 않는다).

`pull_requests` upsert 는 **11단계**다 — 이 조각은 이벤트를 채널로 흘려보내는
데까지다.

### 중복 배달

GitHub 은 같은 이벤트를 **두 번 보낼 수 있다**(응답이 늦으면 재시도한다).
`X-GitHub-Delivery` 가 배달마다 유일하므로 그것으로 거른다.

`repo_events` 에 그 컬럼이 없다. 새 컬럼을 더하는 대신 **`payload` 안에 넣어
두고 최근 것만 조회해 확인한다** — 재시도는 몇 초 안에 오므로 짧은 창이면 충분하고,
마이그레이션 없이 끝난다. 창을 넘긴 중복은 이벤트가 두 번 보이는 정도의 문제라
채널이 깨지지 않는다.

## 3. 채널에 어떻게 보이나

**본문은 한 줄이다.** 커밋 목록을 다 펼치면 대화가 로그로 덮인다 — 대화 안에
개발이 흘러 들어오는 것이 목적이지 대화를 개발 로그로 바꾸는 것이 아니다.

| 이벤트 | 본문 |
|---|---|
| `push` | `아무개 님이 main 에 커밋 3개를 올렸습니다 — 첫 커밋 제목` |
| `pr` | `아무개 님이 PR #12 를 열었습니다 — 제목` |
| `issue` | `아무개 님이 이슈 #3 을 열었습니다 — 제목` |
| `release` | `v1.2.0 이 릴리스됐습니다` |

- **링크는 본문에 넣지 않는다.** 앱이 아직 링크를 특별히 그리지 않아 URL 이
  그대로 보이면 한 줄이 두 줄이 된다. `repo_events.payload` 에 원문이 있으므로
  카드 UI 를 붙일 때 거기서 꺼낸다
- **연결된 채널이 없으면 적재만 하고 메시지는 만들지 않는다.** 저장소를 채널에
  붙이지 않은 채로도 이벤트를 모을 수 있어야 나중에 붙일 때 이력이 남는다

**`repo:event` 소켓 이벤트는 만들지 않는다.** 메시지를 만들면 기존 경로가
`message:new` 를 쏘고, 채널을 보고 있는 사람에게는 그것으로 충분하다. 설계에
있는 `repo:event` 는 **저장소 전용 화면이 생길 때** 필요해진다 — 받는 쪽이
없는 이벤트를 미리 쏘면 계약만 늘고 검증할 방법이 없다.

## 4. 시크릿

**등록 응답에서 딱 한 번만 보여 준다.** 그 뒤로는 목록에도 상세에도 나오지
않는다 — 서버가 검증에만 쓰는 값이고, 다시 볼 수 있게 두면 그것을 볼 수 있는
모든 경로가 새는 자리가 된다. 잃어버리면 **새로 발급**한다.

`webhook_secret` 은 이 조각에서 평문으로 둔다. OAuth 액세스 토큰(`oauth_accounts`)
은 스키마 주석대로 **암호화해야 하지만 그것은 10-2 의 일**이고, 여기서 암호화
계층을 미리 만들면 쓰이지 않는 코드가 된다.

---

## 5. 검증

`npm run check:repos` 를 새로 만든다. **GitHub 없이 전부 돈다** — 서명을 우리가
직접 만들어 보내면 되기 때문이다.

1. 서명이 맞으면 200, **틀리면 401**, 없으면 401
2. 다른 저장소의 시크릿으로 서명하면 401 (저장소마다 다른 시크릿을 쓴다)
3. 없는 `repoId` 는 404
4. `push` 이벤트가 `repo_events` 에 쌓이고 **연결된 채널에 메시지가 뜬다**
5. 메시지 작성자가 **봇이고, 스페이스 멤버 목록에는 없다**
6. 같은 `X-GitHub-Delivery` 를 두 번 보내면 **메시지가 하나만 생긴다**
7. 모르는 이벤트 타입은 200 이고 아무것도 안 쌓인다
8. 채널을 붙이지 않은 저장소는 **적재만 되고 메시지는 없다**
9. 시크릿은 **등록 응답에만** 있고 목록에는 없다
10. 타 스페이스의 저장소는 404
