# 9단계 — 이슈 · 스프린트 설계

> 2026-08-20. 대상은 [전환 계획 §6](../../전환-계획.md) 의 9단계.
> API 계약은 [백엔드 설계 §4](../../백엔드-설계.md), 데이터 모델은 §3 을 따른다.
> 이 문서는 **계약이 정하지 않은 것**과 **거기서 갈라진 것**만 적는다.

---

## 0. 자르기

7·8단계와 같은 기준이다 — **한 조각이 끝나면 화면에 뭔가 새로 보이고, 서버에서
화면까지 끝나야 완료로 친다.**

| 조각 | 내용 | 끝나면 보이는 것 |
|---|---|---|
| **9-1** | 이슈 CRUD · 칸반 보드 · 상태 이동 · 실시간 | **보드가 처음 보인다** |
| **9-2** | 이슈 상세 · 댓글 · 라벨 · 대화 → 이슈 · 삭제 | 카드를 열면 내용이 있다 |
| **9-3** | 스프린트 · 번다운 | 스프린트로 묶여 보인다 |

**드래그 앤 드롭은 9-1 에 넣지 않는다.** 서버는 `PUT /issues/:id/position` 까지
드래그를 전제로 완성하되, 화면은 카드 메뉴로 상태를 옮긴다. 좁은 폭에서
가로 스크롤과 드래그 제스처가 겹치는 문제를 푸느라 **보드를 보는 일 자체가
밀리는 것**을 피한다. 드래그는 계약이 이미 서 있으므로 나중에 화면만 바꾸면 된다.

## 1. 기존 `src/issues` 는 다시 쓴다

`attachments` 때와 같은 판단이다. 옛 소스 414줄에서 살아남는 것은 DTO 골격뿐이다.

- `spaceId` 가 없다 — 모든 쿼리와 시그니처가 바뀐다
- 지금은 없는 `label` 문자열 컬럼을 쓴다(`issue_labels` 로 대체됐다)
- 키 채번이 `count() + 1` 이라 **동시 생성이 같은 키를 받고, 삭제하면 번호가 되돌아간다**
- `IssueProvider` 추상화는 **Redmine 프로바이더**를 위한 것인데 지금 계획에 그런 것이 없다.
  `source` 컬럼은 저장소 연동이 밀어 넣는 이슈를 구분하는 값이지 보드를 갈아 끼우는
  스위치가 아니다 — 남겨 두면 되살리는 사람이 그 오해를 함께 되살린다

옛 소스는 지운다. 필요하면 git 이력에 있다.

**모듈 경계**: `issues/` 한 모듈에 이슈 · 라벨 · 댓글을 두고(`messages/` 가
`reactions.service.ts` · `mentions.service.ts` 를 품은 선례), **스프린트는 9-3 에
`sprints/` 로 따로 만든다.** 라벨 · 댓글은 이슈 없이는 뜻이 없지만 스프린트는
자기 수명주기와 번다운을 갖는 독립된 것이라, 이슈에 종속시키면 `issues/` 가 부푼다.

## 2. 데이터 — 마이그레이션 1건

스키마에 테이블은 이미 다 있다(2단계 재작성 때 만들어 뒀다). 컬럼 둘만 더한다.

```prisma
model Space {
  /// 이슈 키(NEXUS-138)의 연번. 생성 트랜잭션에서 원자적으로 올린다.
  issueSeq Int @default(0) @map("issue_seq")
}

model Issue {
  /// 이슈를 만든 사람. 담당자(assigneeId)와 다르다.
  reporterId String? @map("reporter_id")
}
```

### 채번 — 세는 것이 아니라 발급하는 것

```sql
UPDATE spaces SET issue_seq = issue_seq + 1 WHERE id = $1 RETURNING issue_seq
```

이 한 줄이 스페이스 행을 잠가 동시 생성을 직렬화한다. 생성 트랜잭션 안에서 돈다.

**접두사는 `slug` 에서 만든다** — 첫 마디를 대문자로, 영숫자만 남기고 6자로 자른다
(`nexus` → `NEXUS`). 빈 결과면 `ISSUE`. `UpdateSpaceDto` 에 `slug` 가 없어
**스페이스 slug 는 불변**이므로 한 스페이스 안에서 접두사가 섞이지 않는다.
한글 이름 스페이스는 slug 자체가 `space-a1b2c3d4` 폴백이라 `SPACE-1` 이 되는데,
읽을 수 있고 유일하므로 그대로 둔다. 접두사를 고르는 UI 는 필요해질 때
`issueKeyPrefix` 컬럼으로 승격한다.

### `reporterId` 를 지금 넣는 이유

설계 문서에 없던 것이다. 하지만 **이슈를 누가 만들었는지 기록할 자리가 없으면**
삭제·수정 권한을 정할 근거가 없고, "내가 만든 이슈"를 고를 수도 없다.
나중에 넣으면 **그때까지 만들어진 모든 이슈의 작성자가 영영 null 이다** —
데이터를 잃는 종류라 지금이 가장 싸다. 이미 마이그레이션을 한 번 하는 김에 넣는다.

`null` 을 허용하는 이유는 저장소 연동(9단계 이후)이 밀어 넣는 이슈에는
이 스페이스의 작성자가 없기 때문이다.

### `position` — 사이 삽입이 기본 동작이다

새 이슈는 backlog **맨 위**(`min - 1000`). 두 카드 사이로 옮기면 **중간값**을 준다.
그래야 재정렬 쓰기가 1건으로 끝난다(설계 §3).

`Decimal` 은 Postgres `DECIMAL(65,30)` 이라 중간값을 100번 넘게 반복해도 정밀도가
남지만, **간격이 소진되면 그 컬럼만 1000 간격으로 재채번**하는 경로를 함께 둔다.
카테고리가 쓰는 `Int` + "맨 뒤에 붙이기"와 다른 이유는 칸반이 사이 삽입을
기본으로 하기 때문이다.

## 3. 서버 API (9-1)

전부 `/api/spaces/:spaceId/issues` 아래이고 **`SpaceGuard` 를 건다.**

```
GET    /api/spaces/:spaceId/issues              ?status=&assigneeId=&sprintId=&q=
POST   /api/spaces/:spaceId/issues              { title, description?, status?, priority?,
                                                  assigneeId?, sprintId?, parentId?, storyPoints? }
GET    /api/spaces/:spaceId/issues/:issueId
PATCH  /api/spaces/:spaceId/issues/:issueId     { title? description? priority? assigneeId?
                                                  sprintId? storyPoints? status? }
PUT    /api/spaces/:spaceId/issues/:issueId/position  { status, afterId?, beforeId? }
```

**목록은 평평하게 준다.** 상태별로 묶어 주지 않는 이유는 앱이 그것을 drift 에
행 단위로 넣기 때문이다 — 서버가 묶어 주면 캐시에 넣을 때 다시 풀어야 한다.
정렬은 `(status, position asc)`.

**커서를 두지 않는다.** 대신 **상태별 200건 상한**을 두고, 잘린 컬럼을
응답 `truncated: IssueStatus[]` 로 알린다. 커서를 두려면 정렬 키가 `(status,
position)` 복합이라 컬럼마다 따로 이어야 하는데, Phase 0 규모에서 그 복잡도를
살 이유가 없다. 넘치면 필터(담당자 · 스프린트)로 좁힌다 — **조용히 자르지 않고
잘렸다고 말하는 것**이 핵심이다.

**권한**: 열람은 스페이스 멤버 전원, 생성 · 수정 · 이동은 **`@MinRole('member')`**.
카테고리 · 채널이 `admin` 을 요구하는 것과 다른 이유는 성격이다 — 채널 구조는
스페이스의 뼈대라 아무나 바꾸면 안 되지만, **이슈는 일하는 사람이 만드는 것**이다.
guest 는 보드를 읽기만 한다.

**보이지 않으면 404.** 다른 스페이스의 이슈 id 를 넣어도 403 이 아니라 404 다(§3 규칙 4).

### 상태를 바꾸는 길은 둘이고, 뜻이 다르다

`PATCH` 의 `status` 와 `PUT .../position` 의 `status` 가 겹쳐 보이지만 쓰임이 다르다.

| | 뜻 | 자리 |
|---|---|---|
| `PATCH { status }` | **컬럼만 옮긴다** — 9-1 의 카드 메뉴가 쓴다 | 대상 컬럼 **맨 위** |
| `PUT position { status, afterId?, beforeId? }` | **자리까지 지정한다** — 드래그가 쓴다 | 이웃 사이 중간값 |

둘을 하나로 합치지 않는 이유는 메뉴에게 이웃을 물을 수 없기 때문이다. 메뉴는
"review 로 옮겨"까지만 말하고 어디에 꽂을지는 모른다 — 그때 서버가 맨 위를
고르는 것이 규칙이어야, 앱이 이웃을 지어내지 않는다.

### `closedAt` 은 상태 전이가 정한다

**번다운의 유일한 입력이다**(설계 §3 — 상태 전이 이력 테이블을 두지 않는다).
그래서 상태를 바꾸는 두 경로가 **모두** 같은 규칙을 타야 한다.

- `done` 이 **아니었다가** `done` 이 되면 → `closedAt = now()`
- `done` **이었다가** 벗어나면 → `closedAt = null`
- `done` 안에서 자리만 바뀌면 → **건드리지 않는다** (다시 찍으면 닫힌 시각이 밀린다)

클라이언트가 `closedAt` 을 보내는 것은 받지 않는다. 사용자가 고칠 수 있으면
번다운이 사실이 아니게 된다.

**`PUT .../position` 의 계산**은 `afterId` · `beforeId` 가 가리키는 카드의 position
사이 중간값이다. 한쪽만 주면 그 바깥(± 1000), 둘 다 없으면 그 컬럼 맨 위.
**두 이웃이 모두 같은 `status` 에 있어야 하고**, 아니면 400 이다 — 다른 컬럼의
카드를 기준으로 자리를 정하면 순서가 뜻을 잃는다.

## 4. 실시간

설계 §3.5 #4 가 `issue:updated` 를 "이슈 서비스가 붙는 단계"로 미뤄 뒀다. 지금이다.

**스페이스 룸으로 보낸다** — `room.space(spaceId)` 는 이미 있고 클라이언트가
접속 시 조인한다. 이슈는 채널에 속하지 않으므로 채널 룸을 쓸 수 없다.

| 이벤트 | 페이로드 |
|---|---|
| `issue:created` | 이슈 전체 |
| `issue:updated` | 이슈 전체 (이동도 이것) |
| `issue:deleted` | `{ spaceId, issueId }` (9-2) |

**설계 문서에는 `issue:updated` 하나뿐이지만 셋으로 나눈다.** 대화가
`message:new`/`edited`/`deleted` 로 나뉜 것과 같은 이유다 — 앱 캐시가 "넣기 ·
갈아 끼우기 · 지우기"를 이벤트 이름으로 구분하면 분기가 사라진다. 하나로 두면
앱이 매번 "이 id 가 캐시에 있나"를 먼저 물어야 한다.

**리액션의 `mine` 같은 사람마다 다른 값이 이슈에는 없다.** 그래서 이슈 전체를
그대로 실어도 된다 — 받는 쪽이 접을 것이 없다.

## 5. 앱 (9-1)

**화면은 drift 만 구독한다.** 대화에 적용한 규칙을 보드에도 그대로 쓴다.
한 화면이 두 공급원을 보면 회복되지 않는 틈이 생긴다(6-1 에서 카테고리로 겪었다).

```
data/api/issues_api.dart              목록 · 생성 · 수정 · 이동
data/local/app_database.dart          cached_issues 추가 → schemaVersion 올린다
data/repositories/issues_repository.dart   REST · 소켓 → 캐시, 화면은 여기만 본다
features/issue/board_screen.dart      4열 칸반
features/issue/issue_card.dart        카드
features/issue/board_controller.dart  상태별 묶기 · 낙관적 이동
```

- **쓰기는 온라인 전용이다.** 생성 · 수정 · 이동은 **낙관적으로 그리고 실패하면
  되돌린다.** 전송 큐를 만들지 않는 이유는 칸반 이동의 오프라인 병합이
  메시지보다 훨씬 어렵기 때문이다 — 같은 카드를 두 곳에서 옮기면 순서를
  합칠 방법이 없다. 메시지는 append 라 그 문제가 없었다.
- **읽기는 캐시된다.** 오프라인으로 켜도 보드가 보인다.
- `refreshIssues()` 는 실패를 던지지 않고 `false` 를 돌려준다. **캐시를 빈 값으로
  덮어쓰지 않는 것**이 핵심이다.
- **캐시 테이블을 더했으므로 `schemaVersion` 을 올린다.** 빠뜨리면
  `no such table` 로 앱이 멈춘다(6-1 에서 겪었다).

**라우트와 진입점**

`/s/:spaceId/issues` — 파일 목록과 같이 **셸 위에 덮어서 연다**(`context.push`).
진입점은 둘이다.

- 모바일: 하단 탭 **보드** (지금은 인덱스만 바뀌고 아무 데도 가지 않는 자리표시자다)
- 데스크톱 · 태블릿: 채널 페인 헤더의 보드 버튼

하단 탭이 전체 화면을 push 하는 것은 어색하지만, 셸 본문을 탭으로 갈아 끼우면
**"라우트가 진실의 원천"이라는 셸의 전제가 깨진다.** 탭으로 본문을 바꾸는 구조는
보드 · 알림 · 내정보가 다 생기는 시점에 셸을 통째로 다시 보는 편이 맞다.

**반응형 분기는 `app_shell.dart` 밖으로 나가지 않는다.** 보드는 열 4개를 가로
스크롤로 그리고, 폭에 따라 열 너비만 달라진다 — 분기가 아니라 제약이다.

## 6. 검증

| 층 | 무엇 |
|---|---|
| `npm run check:issues` | **실서버 · 실DB · 실소켓.** 다른 check 스크립트처럼 자체 계정 · 스페이스를 만들어 쓴다 |
| 서버 단위 테스트 | 순수 로직만 — 접두사 파생(한글 폴백 포함) · position 중간값 계산 · 이웃 컬럼 불일치 거부 |
| 앱 테스트 | 인메모리 drift — 캐시 왕복 · 상태별 묶기 · 낙관적 이동 되돌리기 |
| 실기기 | **Windows 데스크톱.** 보드 표시 · 생성 · 상태 이동 · 밖에서 만든 이슈가 실시간으로 뜨는 것 |

`check:issues` 가 반드시 덮어야 하는 것:

1. **테넌트 격리** — 다른 스페이스의 이슈 id 로 조회 · 수정 시 404
2. **채번** — 동시에 여러 건을 만들어도 키가 겹치지 않는다
3. **position** — 두 카드 사이로 옮기면 중간값을 받고, 목록 순서가 그대로 바뀐다
4. **이웃 검증** — 다른 컬럼의 카드를 기준으로 옮기면 400
5. **권한** — guest 는 생성 · 이동이 거부되고 열람은 된다
6. **소켓** — 밖에서 만든 이슈가 `issue:created` 로 도착하고, 비멤버에게는 가지 않는다
7. **상한** — 200건을 넘기면 `truncated` 에 그 상태가 담긴다
8. **`closedAt`** — done 으로 옮기면 채워지고, 되돌리면 비고, done 안에서 자리만 옮기면 그대로다

**스키마와 쿼리가 걸린 변경이므로 실제 DB 로 확인한다**(§6 의 교훈).

## 6-1. 9-2 설계 — 이슈 상세 · 댓글 · 삭제 (9-2a)

9-2 가 9-1 과 비슷한 크기라 **둘로 다시 잘랐다.**

| | 내용 | 끝나면 보이는 것 |
|---|---|---|
| **9-2a** | 이슈 상세 · 댓글 · 삭제 | 카드를 열면 내용이 있고 댓글을 단다 |
| **9-2b** | 라벨 · 대화 → 이슈 | 이슈에 색이 붙고, 대화에서 이슈를 만든다 |

### 스키마 — 마이그레이션 1건

`issue_comments` 와 `issue_label_links` 에 **`spaceId` 가 없다.** 2단계 재작성 때
빠진 것으로, 7-1 에서 `reactions` · `mentions` 에 채운 것과 같은 종류다.
§3 규칙 1 은 예외를 두지 않으므로 **두 컬럼을 한 마이그레이션으로 채운다**
(9-2b 의 라벨까지 미리 넣어 마이그레이션을 두 번 하지 않는다).

### 이슈 상세

**라우트는 `key` 로 잡는다** — `/s/:spaceId/issues/:issueKey`. 설계 문서가
정한 형태이고, 사람이 대화에 붙여 넣는 것도 `NEXUS-12` 이지 uuid 가 아니다.

**앱은 캐시로 key → id 를 푼다.** 보드 캐시에 그 스페이스의 이슈가 이미 다
있다. 다만 딥링크로 곧장 들어오면 캐시가 비어 있을 수 있어, 목록 필터에
`key` 를 더해 한 건만 받아 오는 길을 남긴다. **API 자체는 id 로 유지한다** —
키는 사람이 읽는 이름이고 id 가 참조다.

**본문은 캐시에서 그리고 댓글만 서버에서 받는다.** 이슈 본문은 이미 보드
캐시에 있으므로 상세를 열자마자 그려진다(오프라인에서도).

### 댓글 — 캐시하지 않는다

파일 목록과 같은 판단이다. 이슈 상세는 자주 여는 화면이 아니고, **오프라인에서
댓글을 읽어야 할 이유가 약하다.** 캐시하지 않으므로 **실시간 이벤트도 두지
않는다** — 들어올 때마다 새로 받으면 충분하다.

`thread:reply` 를 둔 스레드와 갈리는 지점이다. 스레드는 채널을 보고 있는
사람의 "답글 N개" 표시가 함께 움직여야 해서 이벤트가 필요했지만, 댓글 수는
보드 카드에 그리지 않는다.

- 목록 + 작성만 만든다. **수정 · 삭제는 뒤로 미룬다** — 메시지가 소프트
  삭제인 것과 맞출지 정해야 하는데, 그 판단이 이 조각의 크기를 넘는다
- **커서를 두지 않는다.** 이슈 하나에 댓글이 수백 건이면 그건 이슈가 아니라
  채널이다. 핀 목록과 같은 판단

### 이슈 삭제 — 하드 삭제다

메시지가 소프트 삭제인 것과 **일부러 다르게 간다.**

| | 메시지 | 이슈 |
|---|---|---|
| 성격 | 대화의 기록 | 할 일 |
| 지운 뒤 | "지워졌다"가 맥락이다 | 취소된 것은 흔적이 남을 이유가 없다 |

잘못 만든 이슈가 보드에 영원히 남으면 **보드가 못 쓰게 된다.** 소프트 삭제로
가려면 `deletedAt` 컬럼과 모든 쿼리의 필터가 따라붙는데, 그 값이 여기에는 없다.

- 권한은 **작성자(`reporterId`) 또는 admin 이상**이다. 만든 사람이 자기 실수를
  치울 수 있어야 하고, 남의 이슈를 아무나 지우면 안 된다
- 자식(에픽의 스토리)이 있으면 `parentId` 는 `SetNull` 이라 자식이 남는다.
  **부모를 지워도 할 일은 사라지지 않는 것**이 맞다
- `issue:deleted` 를 스페이스 룸으로 보낸다 (앱 수신부는 9-1 에서 미리 넣었다)

## 6-2. 9-3 설계 — 스프린트 · 번다운

**마이그레이션이 없다.** `sprints` 테이블도 `Issue.sprintId` · `storyPoints` ·
`closedAt` 도 2단계에 이미 만들어 뒀다. 9-1 에서 `closedAt` 을 상태 전이가
정하도록 못 박은 것이 바로 이 조각을 위한 것이었다.

### 스프린트

**`sprintId` 가 비어 있는 이슈의 집합이 곧 백로그다**(설계 §3). 백로그
테이블을 따로 두지 않는다.

- **스페이스당 `active` 는 하나.** 지금 하는 일이 둘이면 스프린트의 뜻이
  없어진다. `state` 를 `active` 로 바꿀 때 다른 `active` 가 있으면 **409**
- **닫아도 미완료 이슈의 `sprintId` 를 건드리지 않는다.** 그 스프린트에서
  무엇이 끝나지 않았는지가 **기록**이다. 자동으로 백로그에 돌려보내면 그
  기록이 사라지고, 번다운을 나중에 다시 그릴 수도 없다. 옮기고 싶으면
  사용자가 옮긴다
- 상태는 `planned → active → closed` 한 방향이다. 닫은 것을 다시 여는 길은
  두지 않는다 — 되돌릴 일이 생기면 새 스프린트를 만드는 편이 정직하다
- 목록 필터에 **`sprint=none`** 을 더한다. `sprintId` 로는 "비어 있는 것"을
  고를 수 없다(빈 문자열은 DTO 가 거른다)

### 번다운 — `closedAt` 하나로 역산한다

상태 전이 이력 테이블을 두지 않기로 했으므로(설계 §3), **"각 이슈가 언제
닫혔는가"만으로 날짜별 남은 양을 되돌려 계산한다.**

날짜 `d` 의 남은 양 = `closedAt` 이 없거나 `d` 의 끝보다 뒤인 이슈들의 합.

**두 계열을 함께 준다 — 포인트와 개수.**

| 계열 | 언제 보나 |
|---|---|
| `points` | 스토리 포인트를 매기는 경우 |
| `count` | **포인트를 안 매기는 경우** — 혼자 쓰면 추정이 품만 든다 |

포인트만 주면 `storyPoints` 를 비워 둔 사람에게는 그래프가 평평한 선이
된다. 그건 "일이 안 줄었다"가 아니라 "잴 것이 없다"인데, 화면에서 둘이
구분되지 않는다. 개수 계열이 그 자리를 메운다.

**이상선은 서버가 만들지 않는다.** 시작 시점의 총량에서 균등하게 내려오는
직선이라 클라이언트가 두 점으로 그릴 수 있다. 서버가 날짜마다 계산해 보내면
같은 값을 두 번 저장하는 셈이다.

- **기간이 없으면 400.** `startsAt` · `endsAt` 이 비면 가로축을 그릴 수 없다.
  `planned` 상태로 날짜 없이 만들어 둘 수 있으므로 실제로 일어난다
- 날짜는 **UTC 자정 기준**으로 자른다. 기기 시간대로 자르면 같은 스프린트가
  사람마다 다른 그래프가 된다

### 앱

- **스프린트는 캐시한다.** 보드 필터가 쓰는 값이라 오프라인에서도 보여야
  한다. 라벨과 달리 이슈에 붙는 것이 아니라 독립된 목록이므로 **테이블을
  따로 둔다**
- **번다운은 캐시하지 않는다.** 댓글과 같은 판단 — 열 때마다 받는다
- **차트는 `CustomPainter` 로 직접 그린다.** 선 두 개와 축이라 차트 라이브러리를
  들일 이유가 없다. 의존성은 늘리기는 쉽고 걷어내기는 어렵다

## 7. 이 조각에서 하지 않는 것

- 드래그 앤 드롭 (계약만 세워 두고 화면은 나중)
- 이슈 삭제 · 댓글 · 라벨 · 대화 → 이슈 (9-2)
- 스프린트 · 번다운 (9-3)
- 에픽 → 스토리 트리 표시 (`parentId` 는 저장만 하고 보드는 평평하게 그린다)
- 커스텀 보드 컬럼 · 상태 전이 이력 · 워크플로 자동화 — 설계 §3 이 의도적으로 뺐다
