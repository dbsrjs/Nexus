# Nexus — 앱 설계서 (Flutter)

> 단일 Flutter 코드베이스로 **모바일(iOS/Android) · 데스크톱(Windows) · 웹**을 만든다.
> 기존 `www/`(React) · `desktop/`(Electron) · `mobile/`(Capacitor)은 폐기한다. → [전환 계획](./전환-계획.md)

## 0. 대상 플랫폼 — 2026-08-14 축소

원안은 6종(android · ios · windows · macos · linux · web)이었으나 **macOS 와 Linux 를
뺐다.** 스캐폴드는 만드는 순간부터 유지 비용이 든다 — 플러그인이 늘 때마다 각
플랫폼의 등록 파일이 생기고, 빌드가 깨져도 확인할 기기가 없으면 깨진 줄도 모른다.

| 플랫폼 | 상태 |
|---|---|
| Android · iOS · Windows · Web | **유지** |
| macOS | **제외.** 개발 여부를 나중에 다시 논한다 |
| Linux | **제외** |

되살리는 방법은 `app/` 에서 `flutter create --platforms=macos .` 한 줄이다. 코드는
`lib/` 에만 있으므로 플랫폼 폴더를 지워도 잃는 것이 없다.

### 0-1. 검증은 Windows 하나로 좁힌다 — 2026-08-14

플랫폼이 넷이라고 **네 벌을 만드는 것은 아니다.** UI 코드는 한 벌이고, 비싼 것은
**매 변경을 네 곳에서 확인하려는 것**이다. 실제로 잰 값이 차이를 보여 준다.

| 경로 | 한 번 확인하는 비용 |
|---|---|
| **Windows 데스크톱** | 빌드 23초 → 실행 즉시 |
| Android 에뮬레이터 | 증분 빌드 11초 + **부팅 1~2분** + 설치 + 탭 자동화 (게다가 종종 스스로 꺼진다) |

그래서 **기본 검증 대상을 Windows 로 정한다.**

| 플랫폼 | 언제 확인하나 |
|---|---|
| **Windows** | **모든 변경.** 개발 루프의 기본값 |
| Android | 슬라이스 경계 + 플랫폼에 민감한 변경일 때 — 보안 저장소 · 키보드 · 네트워크 주소(`10.0.2.2`) · 레이아웃 경계 |
| Web | 슬라이스 경계. 포트폴리오 데모가 웹이라 뺄 수 없다 ([인프라 설계 §5](./인프라-설계.md)) |
| **iOS** | **동결.** macOS 없이는 빌드 자체가 불가능하다 — 이 PC 에서는 애초에 작업 대상이 아니었다 |

> **좁히는 것은 검증이지 코드가 아니다.** 반응형 레이아웃은 기능이 아니라 **구조**라,
> "PC 전용으로 짜고 나중에 반응형" 으로 가면 모든 화면을 다시 손대야 한다. 지금은 폭 분기가
> `features/shell/app_shell.dart` 한 곳에 갇혀 있어 화면이 늘어도 비용이 늘지 않는다.
> 플랫폼 폴더도 지우지 않는다 — 유지 비용은 거의 없는데 되살릴 때는 스캐폴드 재생성과
> 플러그인 등록을 다시 밟아야 한다.
>
> 같은 기준을 서버에서도 썼다: [전환 계획 §6](./전환-계획.md) 의 "미루는 것은 기능이지
> 구조가 아니다".

## 1. 왜 Flutter 단일 코드베이스인가

이전 구조는 "공유 웹 UI 하나를 세 플랫폼으로 래핑"하는 전략이었다. 의도는 옳았으나 실제로는 웹뷰의 한계(네이티브 스크롤·제스처·푸시)를 계속 우회해야 했다.

Flutter는 같은 목표를 **네이티브 렌더링으로** 달성한다. 특히 채팅 앱의 핵심인 긴 리스트 스크롤 성능과 키보드 처리에서 웹뷰보다 유리하다.

**포기하는 것**: 기존 2,038줄 React UI. 다만 화면 구성과 UX 흐름은 그대로 참고 자료로 쓸 수 있다.

## 2. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 상태 관리 | **Riverpod** | 컴파일 타임 안전, 테스트 용이, `provider`의 후속 |
| 라우팅 | **go_router** | 선언형, 웹 URL·딥링크 대응 |
| HTTP | **dio** | 인터셉터로 토큰 갱신 처리 |
| 실시간 | **socket_io_client** | 서버가 Socket.IO이므로 프로토콜 일치 |
| 모델 | **freezed** + **json_serializable** | 불변 모델, 유니온 타입, 보일러플레이트 제거 |
| 로컬 저장 | **drift** (SQLite) | 메시지 캐시 · 오프라인 읽기 |
| 토큰 저장 | **flutter_secure_storage** | Keychain/Keystore. 웹은 제약이 있어 §7 참조 |
| 마크다운 | **flutter_markdown** + **flutter_highlight** | 메시지 렌더링, 코드블록 강조 |
| 푸시 | **firebase_messaging** | FCM(Android) / APNs(iOS) |
| 데스크톱 | **tray_manager**, **window_manager**, **local_notifier** | 트레이 · 창 제어 · 네이티브 알림 |

## 3. 폴더 구조

```
app/
├─ lib/
│  ├─ main.dart                 # 부트스트랩, ProviderScope
│  ├─ core/
│  │  ├─ env.dart               # --dart-define 값 (API_BASE 등)
│  │  ├─ router.dart            # go_router 설정, 인증 가드
│  │  ├─ theme.dart             # 라이트/다크 테마, 디자인 토큰
│  │  ├─ result.dart            # Result<T, AppError> 공통 반환 타입
│  │  └─ errors.dart
│  ├─ data/
│  │  ├─ api/                   # dio 클라이언트 + 엔드포인트별 래퍼
│  │  ├─ socket/                # Socket.IO 연결 · 룸 · 이벤트 디스패치
│  │  ├─ local/                 # drift DB (메시지·채널 캐시)
│  │  └─ repositories/          # domain 인터페이스 구현 (원격 + 로컬 병합)
│  ├─ domain/
│  │  ├─ models/                # freezed 모델 (Space, Channel, Message …)
│  │  └─ repositories/          # 추상 인터페이스
│  ├─ features/
│  │  ├─ auth/                  # 로그인 · 회원가입 · OAuth
│  │  ├─ space/                 # 스페이스 목록 · 생성 · 초대 · 멤버
│  │  ├─ channel/               # 카테고리 트리 · 채널 목록 · 채널 설정
│  │  ├─ chat/                  # 메시지 리스트 · 입력 · 리액션 · 멘션
│  │  ├─ thread/                # 스레드 패널
│  │  ├─ issue/                 # 칸반 보드 · 이슈 상세
│  │  ├─ repo/                  # 저장소 연결 · 이벤트 피드
│  │  ├─ ai/                    # AI 대화 패널
│  │  └─ settings/              # 프로필 · 알림 · 테마
│  └─ shared/
│     ├─ widgets/               # Avatar, EmojiPicker, MarkdownBody …
│     └─ utils/                 # 날짜 포맷, 멘션 파서
└─ test/
```

각 `features/<name>/` 내부는 `presentation/`(화면·위젯)과 `application/`(Riverpod 프로바이더·컨트롤러)으로 나눈다. 데이터 접근은 반드시 `domain/repositories`의 인터페이스를 거친다.

## 4. 화면 레이아웃 — 반응형

Discord/Slack의 3단 레이아웃을 기준으로 하되, 화면 폭에 따라 접는다.

### 데스크톱 · 웹 (≥1024px)

```
┌────┬──────────────┬─────────────────────────┬──────────┐
│스페 │ 카테고리      │  메시지 리스트           │ 스레드 /  │
│이스 │  └ 채널       │                         │ 이슈 /   │
│레일 │  └ 채널       │  ─────────────────────  │ AI 패널  │
│    │ DM 목록       │  메시지 입력창           │ (토글)   │
└────┴──────────────┴─────────────────────────┴──────────┘
  72px    240px            가변                  320px
```

### 태블릿 (600~1023px)
스페이스 레일 + 채널 목록을 하나의 접이식 드로어로 합친다. 우측 패널은 오버레이로 뜬다.

### 모바일 (<600px)
- 하단 탭: **대화 · 보드 · 알림 · 내정보**
- 채널 목록은 좌측 드로어(스와이프)
- 스레드 · 이슈 상세는 전체 화면 push

`LayoutBuilder` + 브레이크포인트 상수로 분기하고, **화면 위젯은 셋이 공유**한다. 분기는 껍데기(shell) 레벨에서만 일어난다.

## 5. 라우팅

```
/login                                        로그인
/signup                                       회원가입
/spaces                                       스페이스 선택
/s/:spaceId                                   → 마지막 채널로 리다이렉트
/s/:spaceId/c/:channelId                      채널 (기본 화면)
/s/:spaceId/c/:channelId/t/:messageId         스레드
/s/:spaceId/dm/:userId                        DM
/s/:spaceId/issues                            칸반 보드
/s/:spaceId/issues/:issueKey                  이슈 상세
/s/:spaceId/repos                             저장소
/s/:spaceId/settings                          스페이스 설정
/settings                                     내 설정
```

웹에서 그대로 주소창 URL이 되고, 모바일에서는 딥링크·푸시 알림 탭 목적지가 된다. 인증 가드는 `go_router`의 `redirect`에서 토큰 유무로 판정한다.

## 6. 실시간 · 오프라인 전략

### 데이터 흐름

```
Socket.IO 이벤트 ──┐
                  ├─→ Repository ─→ drift(로컬 DB) ─→ Riverpod Stream ─→ UI
REST 응답 ─────────┘
```

**단일 진실 공급원은 로컬 DB다.** UI는 항상 drift를 구독하고, REST와 소켓은 로컬 DB를 갱신하는 두 개의 입력원일 뿐이다. 이렇게 하면 오프라인 표시와 실시간 갱신이 같은 코드 경로를 탄다.

### 규칙

| 상황 | 처리 |
|---|---|
| 채널 진입 | 로컬 캐시 즉시 렌더 → REST로 최신 페이지 fetch → 병합 |
| 메시지 전송 | **낙관적 삽입**(로컬에 pending 상태로 즉시 표시) → 서버 응답으로 확정 → 실패 시 재전송 UI |
| 소켓 재연결 | 마지막 수신 메시지 이후를 REST로 따라잡기(catch-up). 소켓만 믿지 않는다 |
| 앱 백그라운드 | 소켓 해제, 푸시 알림으로 전환 |
| 오프라인 | 캐시된 채널 읽기 가능, 전송은 큐에 적재 후 복귀 시 flush |

### 소켓 룸 재조인
서버가 채널 참여·권한 변경 시 `space:{id}` 룸으로 `rooms:invalidate`를 보내면 클라이언트가 룸 재조인을 요청한다. (이전 구조에서 재연결 전까지 새 채널을 못 받던 문제의 해결책 — [백엔드 설계 §5](./백엔드-설계.md) 참조)

## 7. 인증 · 토큰

- 로그인/회원가입/GitHub OAuth → access(짧게) + refresh(길게)
- **저장**: 모바일·데스크톱은 `flutter_secure_storage`(Keychain/Keystore).
  **웹은 브라우저 특성상 안전한 저장소가 없으므로**, refresh 토큰은 `HttpOnly` 쿠키로 서버가 내려주고 access 토큰만 메모리에 둔다. (이전 구조에서 두 토큰을 모두 `localStorage`에 두던 XSS 노출을 개선)
- dio 인터셉터가 401을 받으면 refresh를 1회 시도하고, 실패 시 로그인 화면으로 보낸다.

## 8. 플랫폼별 기능

데스크톱은 **Windows 만** 대상이다 (§0).

| 기능 | 모바일 | 데스크톱(Windows) | 웹 |
|---|---|---|---|
| 푸시 알림 | FCM / APNs | `local_notifier` | Web Push (Phase 1) |
| 트레이 아이콘 | — | `tray_manager` | — |
| 창 상태 기억 | — | `window_manager` | — |
| 파일 첨부 | 갤러리 · 카메라 · 파일 | 드래그앤드롭 | 드래그앤드롭 |
| 딥링크 | 스킴 + 앱링크 | — | URL |
| 백그라운드 동기화 | 푸시 트리거 | 상시 소켓 | 탭 활성 시 |

플랫폼 분기는 `core/platform/` 아래에 인터페이스 + 조건부 import(`dart.library.html`)로 격리한다. feature 코드에는 `Platform.isX` 분기를 넣지 않는다.

## 9. 설정 주입

API 주소는 **빌드 타임에 주입**한다. (이전 구조에서 `localhost:3000`이 하드코딩되어 실기기에서 연결 불가였던 문제의 해결)

```bash
flutter run --dart-define=API_BASE=https://api.nexus.dev
flutter build apk --dart-define=API_BASE=https://api.nexus.dev
```

`core/env.dart`가 `String.fromEnvironment`로 읽고, 기본값은 개발용 `http://10.0.2.2:3000`(Android 에뮬레이터에서 호스트를 가리키는 주소)으로 둔다.

## 10. 테스트

| 층 | 도구 | 대상 |
|---|---|---|
| 단위 | `test` | 멘션 파서, 날짜 포맷, Repository 병합 로직 |
| 위젯 | `flutter_test` | 메시지 버블, 입력창, 칸반 카드 |
| 통합 | `integration_test` | 로그인 → 채널 진입 → 메시지 전송 |

최소한 **Repository 병합 로직과 소켓 catch-up**은 반드시 단위 테스트를 둔다. 여기가 가장 버그가 나기 쉽고 수동 재현이 어렵다.

## 11. 구현 순서

1. 프로젝트 생성 + 스택 배선(Riverpod · go_router · dio · freezed) + 테마
2. 인증 (로그인 · 회원가입 · 토큰 인터셉터)
3. 스페이스 선택 · 생성 · 초대 수락
4. 반응형 셸(3단 레이아웃 ↔ 모바일 탭)
5. 채널 목록 + 메시지 리스트 + 전송 (REST만, 낙관적 갱신)
6. drift 캐시 도입 → 단일 진실 공급원으로 전환
7. Socket.IO 연결 · 실시간 갱신 · catch-up
8. 스레드 · 리액션 · 멘션 · 핀
9. 파일 업로드 · 이미지 미리보기
10. 이슈 보드
11. 저장소 이벤트 피드 · AI 패널
12. 푸시 알림 · 트레이 · 딥링크
