# Nexus — 앱 설계서 (Flutter)

> 단일 Flutter 코드베이스로 **모바일(iOS/Android) · 데스크톱(Windows) · 웹**을 만든다.
> 기존 `www/`(React) · `desktop/`(Electron) · `mobile/`(Capacitor)은 폐기한다. → [전환 계획](./전환-계획.md)

## 0. 대상 플랫폼 — 2026-08-14 축소

원안은 6종(android · ios · windows · macos · linux · web)이었으나 **macOS 와 Linux 를
뺐다.** 스캐폴드는 만드는 순간부터 유지 비용이 든다 — 플러그인이 늘 때마다 각
플랫폼의 등록 파일이 생기고, 빌드가 깨져도 확인할 기기가 없으면 깨진 줄도 모른다.

| 플랫폼 | 상태 |
|---|---|
| Android · iOS · Windows · Web | **유지** |
| macOS | **제외.** 개발 여부를 나중에 다시 논한다 |
| Linux | **제외** |

되살리는 방법은 `app/` 에서 `flutter create --platforms=macos .` 한 줄이다. 코드는
`lib/` 에만 있으므로 플랫폼 폴더를 지워도 잃는 것이 없다.

### 0-1. 검증은 Windows 하나로 좁힌다 — 2026-08-14

플랫폼이 넷이라고 **네 벌을 만드는 것은 아니다.** UI 코드는 한 벌이고, 비싼 것은
**매 변경을 네 곳에서 확인하려는 것**이다. 실제로 잰 값이 차이를 보여 준다.

| 경로 | 한 번 확인하는 비용 |
|---|---|
| **Windows 데스크톱** | 빌드 23초 → 실행 즉시 |
| Android 에뮬레이터 | 증분 빌드 11초 + **부팅 1~2분** + 설치 + 탭 자동화 (게다가 종종 스스로 꺼진다) |

그래서 **기본 검증 대상을 Windows 로 정한다.**

| 플랫폼 | 언제 확인하나 |
|---|---|
| **Windows** | **모든 변경.** 개발 루프의 기본값 |
| Android | 슬라이스 경계 + 플랫폼에 민감한 변경일 때 — 보안 저장소 · 키보드 · 네트워크 주소(`10.0.2.2`) · 레이아웃 경계 |
| Web | 슬라이스 경계. 포트폴리오 데모가 웹이라 뺄 수 없다 ([인프라 설계 §5](./인프라-설계.md)) |
| **iOS** | **동결.** macOS 없이는 빌드 자체가 불가능하다 — 이 PC 에서는 애초에 작업 대상이 아니었다 |

> **좁히는 것은 검증이지 코드가 아니다.** 반응형 레이아웃은 기능이 아니라 **구조**라,
> "PC 전용으로 짜고 나중에 반응형" 으로 가면 모든 화면을 다시 손대야 한다. 지금은 폭 분기가
> `features/shell/app_shell.dart` 한 곳에 갇혀 있어 화면이 늘어도 비용이 늘지 않는다.
> 플랫폼 폴더도 지우지 않는다 — 유지 비용은 거의 없는데 되살릴 때는 스캐폴드 재생성과
> 플러그인 등록을 다시 밟아야 한다.
>
> 같은 기준을 서버에서도 썼다: [전환 계획 §6](./전환-계획.md) 의 "미루는 것은 기능이지
> 구조가 아니다".

## 1. 왜 Flutter 단일 코드베이스인가

이전 구조는 "공유 웹 UI 하나를 세 플랫폼으로 래핑"하는 전략이었다. 의도는 옳았으나 실제로는 웹뷰의 한계(네이티브 스크롤·제스처·푸시)를 계속 우회해야 했다.

Flutter는 같은 목표를 **네이티브 렌더링으로** 달성한다. 특히 채팅 앱의 핵심인 긴 리스트 스크롤 성능과 키보드 처리에서 웹뷰보다 유리하다.

**포기하는 것**: 기존 2,038줄 React UI. 다만 화면 구성과 UX 흐름은 그대로 참고 자료로 쓸 수 있다.

## 2. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 상태 관리 | **Riverpod** | 컴파일 타임 안전, 테스트 용이, `provider`의 후속 |
| 라우팅 | **go_router** | 선언형, 웹 URL·딥링크 대응 |

| 모델 | **freezed** + **json_serializable** | 불변 모델, 유니온 타입, 보일러플레이트 제거 |
| 로컬 저장 | **drift** (SQLite) | 메시지 캐시 · 오프라인 읽기 · 전송 큐 |
| 토큰 저장 | **flutter_secure_storage** | Keychain/Keystore. 웹은 제약이 있어 §7 참조 |
| 파일 선택 | **file_picker** | 첨부 (8-2) |
| 외부 브라우저 | **url_launcher** | GitHub OAuth 는 시스템 브라우저에서 한다 — GitHub 이 임베디드 웹뷰 로그인을 막는다 |
| UI 부품 | ~~Material · Cupertino~~ → **자체 위젯** (`lib/ui/`, 앱 뼈대는 `WidgetsApp`) | 플랫폼 기본 UI 와 관용 패턴(바텀시트 · NavigationBar · 햄버거 · 물결)을 쓰지 않는다 — 15단계. `test/no_platform_ui_test.dart` 가 import 를 막는다 |
| 마크다운 | ~~flutter_markdown + flutter_highlight~~ → **직접 구현** (`shared/markdown/`) | 멘션을 같은 파서 안에 둬야 했고, 하이라이팅은 네 가지(주석 · 문자열 · 숫자 · 키워드)만 칠한다. 패키지를 들이지 않는 판단(CLAUDE.md §3-8) |
| 푸시 | **firebase_messaging** | FCM(Android) / APNs(iOS) — ⬜ «마지막»에서 뺐다(보스 결정, 2026-10-09 — 데스크톱 · 웹만) |
| 통화 · 화면 공유 | **livekit_client** (+ 화면 · 창 목록에 `flutter_webrtc` 직접) | WebRTC 를 직접 짜면 플랫폼 넷의 캡처 · 코덱 · 재연결을 떠안는다. `VoiceEngine` 뒤에 숨겨 테스트는 가짜로 돈다 — ✅ 20단계 |
| 데스크톱 · 웹 알림 · 트레이 | ~~tray_manager · window_manager · local_notifier~~ → **직접 구현** | Windows 는 러너의 `desktop_shell.cpp`(Shell_NotifyIcon 하나로 트레이 · 메뉴 · 알림), 웹은 `dart:js_interop` 으로 브라우저 `Notification`. 패키지를 들이지 않는 판단(CLAUDE.md §3-8) — ✅ «마지막» 4 |

> 2026-10-09 기준으로 **실제로 들어간 것은 푸시 한 줄을 뺀 전부**다. 데스크톱 · 웹 알림과 트레이는 패키지 없이 만들었다.

## 3. 폴더 구조

```
app/
├─ lib/
│  ├─ main.dart                 # 부트스트랩, ProviderScope
│  ├─ core/
│  │  ├─ env.dart               # --dart-define 값 (API_BASE 등)
│  │  ├─ router.dart            # go_router 설정, 인증 가드
│  │  ├─ theme.dart             # 라이트/다크 테마, 디자인 토큰
│  │  ├─ result.dart            # Result<T, AppError> 공통 반환 타입
│  │  └─ errors.dart
│  ├─ data/
│  │  ├─ api/                   # dio 클라이언트 + 엔드포인트별 래퍼
│  │  ├─ socket/                # Socket.IO 연결 · 룸 · 이벤트 디스패치
│  │  ├─ local/                 # drift DB (메시지·채널 캐시)
│  │  └─ repositories/          # domain 인터페이스 구현 (원격 + 로컬 병합)
│  ├─ domain/
│  │  ├─ models/                # freezed 모델 (Space, Channel, Message …)
│  │  └─ repositories/          # 추상 인터페이스
│  ├─ features/
│  │  ├─ auth/                  # 로그인 · 회원가입 · OAuth
│  │  ├─ space/                 # 스페이스 목록 · 생성 · 초대 · 멤버
│  │  ├─ channel/               # 카테고리 트리 · 채널 목록 · 채널 설정
│  │  ├─ chat/                  # 메시지 리스트 · 입력 · 리액션 · 멘션
│  │  ├─ thread/                # 스레드 패널
│  │  ├─ issue/                 # 칸반 보드 · 이슈 상세
│  │  ├─ repo/                  # 저장소 연결 · 이벤트 피드
│  │  ├─ ai/                    # AI 대화 패널
│  │  └─ settings/              # 프로필 · 알림 · 테마
│  └─ shared/
│     ├─ widgets/               # Avatar, EmojiPicker, MarkdownBody …
│     └─ utils/                 # 날짜 포맷, 멘션 파서
└─ test/
```

각 `features/<name>/` 내부는 `presentation/`(화면·위젯)과 `application/`(Riverpod 프로바이더·컨트롤러)으로 나눈다. 데이터 접근은 반드시 `domain/repositories`의 인터페이스를 거친다.

> **위는 목표 구조이고, 실제로는 쓰는 것만 만든다.** 빈 디렉터리를 미리 파 두지 않는다.
> 실제 구조는 [코드 둘러보기 §5](./코드-둘러보기.md) 에 있다. 지금까지 의도적으로
> 다르게 간 곳:
>
> | 계획 | 실제 | 이유 |
> |---|---|---|
> | `features/thread/` 별도 | `features/chat/` 안 | 메시지 타일·입력창을 채널과 공유한다. 같은 대화가 화면마다 달라 보이면 안 된다 |
> | `domain/repositories/` 추상 인터페이스 | 없음. `data/repositories/` 구현만 | 구현이 하나뿐인 인터페이스는 지금 값이 없다. 두 번째 구현이 생길 때 뽑는다 |
> | `core/result.dart` (`Result<T, E>`) | `AuthFailure` · `ApiFailure` 열거형 | 실패 **종류**만 필요하고 성공 값은 그냥 반환하면 된다 |
> | feature 안 `presentation/` · `application/` 분리 | 파일 단위로만 분리 | 화면이 한둘인 feature 에 디렉터리를 두 겹 파면 찾기만 어려워진다 |
> | `shared/utils/` 멘션 파서 | `shared/markdown/` 안 | 마크다운과 멘션이 한 본문을 각자 쪼개면 위치가 어긋난다. 파서는 하나여야 한다 |
> | `features/files/` 없음 | `features/files/` | 스페이스 파일 목록(8-3)이 따로 생겼다 |
> | 없음 | `features/voice/` | 20단계 통화. 채널 주소 하나(`c/:channelId`)가 종류에 따라 통화 화면 / 대화로 갈린다 |
> | `core/theme.dart` (Material 테마) | `ui/theme.dart` 의 `NxTheme` + `ui/` 자체 위젯 | 15단계에 Material 을 걷었다. 토큰 이름은 `tokens.css` 와 1:1 그대로다 |

## 4. 화면 레이아웃 — 반응형

Discord/Slack의 3단 레이아웃을 기준으로 하되, 화면 폭에 따라 접는다.

### 데스크톱 · 웹 (≥1024px)

```
┌────┬──────────────┬─────────────────────────┬──────────┐
│스페 │ 카테고리      │  메시지 리스트           │ 스레드 /  │
│이스 │  └ 채널       │                         │ 이슈 /   │
│레일 │  └ 채널       │  ─────────────────────  │ AI 패널  │
│    │ DM 목록       │  메시지 입력창           │ (토글)   │
└────┴──────────────┴─────────────────────────┴──────────┘
  72px    240px            가변                  320px
```

### 태블릿 (600~1023px)
스페이스 레일 + 채널 목록을 한 판으로 합쳐 왼쪽에서 밀려 나오게 한다. 우측 패널은 오버레이로 뜬다.

### 모바일 (<600px)
- 하단 탭: **대화 · 이슈 · 저장소 · 파일** (고른 탭은 경로에서 읽는다 — 스프린트는 이슈 탭)
- 채널 목록은 **본문 머리의 제목을 누르면** 레일과 함께 왼쪽에서 밀려 나온다. 햄버거 · 드로어를 쓰지
  않는다(15단계)
- 스레드 · 이슈 상세는 전체 화면 push. 계정 메뉴(설정 · 로그아웃)는 레일 맨 아래 아바타

> 원안의 「알림 · 내정보」 탭은 만들지 않았다 — 알림은 18단계, 내 정보는 설정 창(14단계)이 맡는다.

`LayoutBuilder` + 브레이크포인트 상수로 분기하고, **화면 위젯은 셋이 공유**한다. 분기는 껍데기(shell) 레벨에서만 일어난다.

## 5. 라우팅

**가르는 기준: 한 번 가서 머무는 곳은 셸 안, 보고 돌아오는 곳은 덮어서.**
2026-08-22 에 `ShellRoute` 로 정리했다.

```
── 셸 밖 ────────────────────────────────────────────────────────
/                                             토큰 확인 중(거쳐 가는 화면) ✅
/login                                        로그인 (?from= 원래 주소) ✅ «마지막» 3
/signup                                       가입 (?from= 원래 주소)   ✅ «마지막» 5
/spaces                                       스페이스 선택 · 만들기 · 참여 ✅ 16-1
/invite/:code                                 초대 링크 — 한 번 더 눌러 참여 ✅ «마지막» 3

── 셸 안 (ShellRoute — 레일 + 두 번째 판이 유지된다) ─────────────
/s/:spaceId                                   셸 홈(채널 미선택)        ✅
/s/:spaceId/c/:channelId                      채널 (기본 화면)          ✅
/s/:spaceId/issues                            칸반 보드                 ✅ 9-1
/s/:spaceId/issues/:issueKey                  이슈 상세                 ✅ 9-2a
/s/:spaceId/sprints                           스프린트 · 번다운         ✅ 9-3
/s/:spaceId/files                             파일                      ✅ 8-3
/s/:spaceId/repos                             저장소 목록               ✅ 10-2b
/s/:spaceId/notifications                     알림함 (캐시하지 않는다)  ✅ 18
/s/:spaceId/c/:channelId (DM)                 DM — 채널 화면 그대로     ✅ 17-1
                                              (DM 은 kind=dm 채널이라 주소도 같다)

── 셸 위에 덮어서 (push — 보고 돌아온다) ─────────────────────────
/s/:spaceId/c/:channelId/t/:messageId         스레드                    ✅ 7-2
/s/:spaceId/repos/:repoId/browse              저장소 열람               ✅ 10-3a
/s/:spaceId/repo-events/:eventId              그 push 의 커밋들         ✅ 10-3b
/s/:spaceId/repos/:repoId/commits             브랜치 이력               ✅ 10-3b
/s/:spaceId/repos/:repoId/commits/:sha        커밋 상세                 ✅ 10-3b
/s/:spaceId/repos/:repoId/pulls               PR 목록                   ✅ 11
/s/:spaceId/repos/:repoId/pulls/:number       PR 상세 · 바뀐 파일       ✅ 11
/s/:spaceId/settings/:section                 스페이스 설정(일반 · 멤버 · 초대)   ✅ 16-1
/s/:spaceId/c/:channelId/settings/:section    채널 설정(개요 · 멤버 · 권한)      ✅ 16-2

/settings/:section                            내 설정(내 계정 · 비밀번호 · 알림 · 화면)  ✅ 14
```

`/s/:spaceId` 는 계획상 "마지막 채널로 리다이렉트"였으나, 지금은 **채널을 고르지 않은
셸**을 그대로 보여 준다. 마지막 채널을 기억하려면 어디에 저장할지(로컬 · 서버)부터
정해야 하는데 아직 그럴 이유가 없다.

**셸 안이 `ShellRoute` 인 것이 핵심이다.** 셸이 마운트된 채로 남아 갈래를 옮겨도
레일과 채널 목록이 다시 만들어지지 않고, **무엇을 그릴지는 여전히 라우터가 정한다** —
셸이 본문을 탭으로 갈아 끼우면 "라우트가 진실의 원천"이라는 전제가 깨진다.

AI 패널은 라우트가 아니라 채널 화면 위에 뜨는 패널이다(13-1 · 13-2). 지난 대화(19)도 라우트가 아니라 이 패널의 한 모드다 — 입력 화면의 「지난 대화」 → 목록 → 누르면 그 사슬의 칩과 문답을 되살려 이어 묻는다.

**스레드 · 저장소 열람 · 커밋 · PR · 설정 창(내 설정 · 스페이스 · 채널)은 덮어서 연다**(push). 설정 창 셋은 같은 틀(`SettingsFrame` · `SettingsNav`)이고, 볼 수 있는 섹션만 싣는다. 특정 메시지 · 특정 저장소에서 파고드는 것이라
돌아오는 길이 분명한 편이 낫다. 이슈 보드와 스프린트를 셸 안으로 들인 것과 갈리는
지점은 **머무느냐 돌아오느냐**이지 중요도가 아니다.

웹에서 그대로 주소창 URL이 되고, 모바일에서는 딥링크·푸시 알림 탭 목적지가 된다. 인증 가드는 `go_router`의 `redirect`에서 토큰 유무로 판정한다.

## 6. 실시간 · 오프라인 전략

### 데이터 흐름

```
Socket.IO 이벤트 ──┐
                  ├─→ Repository ─→ drift(로컬 DB) ─→ Riverpod Stream ─→ UI
REST 응답 ─────────┘
```

**단일 진실 공급원은 로컬 DB다.** UI는 항상 drift를 구독하고, REST와 소켓은 로컬 DB를 갱신하는 두 개의 입력원일 뿐이다. 이렇게 하면 오프라인 표시와 실시간 갱신이 같은 코드 경로를 탄다.

### 규칙

| 상황 | 처리 | 구현 상태 |
|---|---|---|
| 채널 진입 | 로컬 캐시 즉시 렌더 → REST로 최신 페이지 fetch → **교체** | ✅ 6-1 |
| 메시지 전송 | **큐에 넣고 흘려보낸다.** 큐에 들어간 순간 화면에 보이고, 온라인이면 곧바로 오프라인이면 재연결 때 나간다 | ✅ 6-2 |
| 소켓 재연결 | **첫 페이지를 통째로 다시 받는다.** 놓친 구간의 길이를 알 수 없어 커서를 잇지 않는다 | ✅ 5-4 |
| 오프라인 | 캐시된 대화 읽기 가능, 전송은 큐에 적재 후 복귀 시 flush | ✅ 6 |
| 앱 백그라운드 | 데스크톱 · 웹은 **소켓을 그대로 둔다** — 창을 닫으면 트레이로 숨고, 새 알림은 OS 알림으로 띄운다. 모바일 푸시는 없다 | 🔸 «마지막» 4 (모바일 푸시는 뺐다) |

> **병합이 아니라 교체인 이유**: 서버에서 지워진 메시지가 캐시에 남으면 화면에서
> 사라지게 할 근거가 없다. 다만 **채널 타임라인 교체는 최상위(`parent_id IS NULL`)만**
> 지운다 — 서버 응답에 스레드 답글이 없으므로 함께 지우면 열어 둔 스레드가 빈다.
>
> **전송 큐는 캐시와 다른 테이블에 둔다.** 캐시는 서버에서 다시 받으면 되지만 큐에
> 있는 것은 사용자가 쓴 유일본이라, 스키마가 바뀌어 캐시를 통째로 재생성할 때
> 함께 지워지면 안 된다.

### 시각을 저장하는 방법 — 실제로 두 번 틀렸다

`DateTime` 을 **UTC 마이크로초 정수**로 저장한다(`_UtcMicros` 컨버터).

- drift 기본값(Unix **초**)은 밀리초를 잘라, 같은 초에 도착한 메시지가 정렬에서
  동률이 되고 **순서가 뒤집힌다.**
- `storeDateTimeAsText` 는 `toIso8601String()` 을 그대로 쓰는데, Dart 는 마이크로초가
  0이면 소수점 3자리, 아니면 6자리로 자릿수를 바꾸고 로컬에는 ` +09:00`, UTC 에는
  `Z` 를 붙인다. **문자열 정렬이 곧 시간 순서**라는 전제가 깨진다.

**큐의 전송 순서는 시각이 아니라 삽입 순번(`seq`)이 정한다.** Windows 의
`DateTime.now()` 는 밀리초 해상도라 연속 전송이 완전히 같은 시각을 갖는다.

### 소켓 룸 재조인
서버가 채널 참여·권한 변경 시 `space:{id}` 룸으로 `rooms:invalidate`를 보내면 클라이언트가 룸 재조인을 요청한다. (이전 구조에서 재연결 전까지 새 채널을 못 받던 문제의 해결책 — [백엔드 설계 §5](./백엔드-설계.md) 참조)

**볼 수 없게 되는 쪽은 앱에 맡기지 않는다**(16단계) — 서버가 그 소켓을 룸에서 직접 빼고, 앱은 화면만 정리한다. 스페이스에서 빠지면(`space:removed`) 그 스페이스의 캐시와 전송 큐를 지우고 `/spaces` 로, 보던 채널이 목록에서 빠지면 스페이스 홈으로 옮기고 그 채널의 메시지 캐시를 지운다(전송 큐는 남긴다).

## 6-1. 대화 상호작용 — 리액션 · 스레드 · 답장

셋 다 메시지에 붙지만 **성격이 다르다.** 길게 누르기 시트 한 곳에 모아 두되,
스레드와 답장은 이름만으로 차이가 드러나지 않아 한 줄씩 설명을 붙였다.

| | 리액션 | 스레드 | 답장(인용) |
|---|---|---|---|
| 타임라인 | 메시지에 붙음 | **빠진다** | **남는다** |
| 쓰임 | 말 없이 반응 | 곁가지를 접어 둠 | 흐름 중 한 발언을 가리킴 |
| 서버 | `reactions` 테이블 | `parent_id` | `quoted_message_id` |
| 화면 | 칩 | 별도 라우트 | 인용 블록 |

### 리액션 — `mine` 은 소켓에 실을 수 없다

서버는 `emoji · count · mine` 요약을 준다. 그런데 **`mine`("내가 눌렀는지")은 받는
사람마다 답이 다르다.** 브로드캐스트에 실으면 남의 답이 내 화면에 온다.

그래서 소켓은 `(emoji, userId)` 쌍만 보내고 **앱이 자기 id 로 접는다.** 같은 접기
규칙이 서버·앱 양쪽에 하나씩 있으므로 각각 단위 테스트로 고정했다.

리액션은 **낙관적 토글**이다. 실패하면 서버 값으로 되돌린다 — 전송 큐에 쌓지 않는
이유는 리액션이 *지금 이 순간의 반응*이라 나중에 몰아 보낼 값이 아니어서다.

**순서를 유지한다.** 개수 순으로 재정렬하면 남이 리액션을 달 때마다 버튼이 움직여
누르기 어려워진다.

### 스레드 — `thread:{id}` 룸을 쓰지 않는다

설계상 스레드 전용 룸이 있었지만(§백엔드-설계 §5) 쓰지 않았다. **채널을 보고 있는
사람도 답글 수 갱신이 필요해서**, 별도 룸을 두면 본문은 스레드 룸 · 개수는 채널
룸으로 경로가 둘로 갈린다. `thread:reply` 를 채널 룸으로 보내고 갱신된 `replyCount`
를 함께 싣는다. 트래픽이 문제가 될 때 나누면 된다.

캐시에서는 **채널 새로고침이 답글을 지우지 않도록** 최상위만 교체한다.

### 답장 — `parentId` 를 재사용할 수 없다

`parentId` 가 있으면 서버가 타임라인에서 빼는데, 답장은 흐름에 남아야 한다.
그래서 `quotedMessageId` 를 따로 뒀고, **둘을 함께 쓸 수도 있다**(스레드 안에서 인용).

- **인용은 한 겹만** 펼친다. 원본을 통째로 중첩하면 그 원본의 인용이 딸려 와 화면이
  계단이 된다 — 서버가 요약만 준다
- **같은 채널만** 인용할 수 있다. 다른 채널을 가리키면 못 보는 대화가 인용문으로 샌다
- **원본이 삭제돼도 인용은 남기되 본문은 싣지 않는다.** 맥락은 필요하지만 소프트
  삭제의 의미는 지켜야 한다
- **큐에도 인용 요약을 함께 넣는다.** 보내기 전에는 서버에서 원본을 받아올 수 없어,
  없으면 큐에 있는 동안 인용문이 빈 채로 보인다

## 7. 인증 · 토큰

- 로그인/회원가입/GitHub OAuth → access(짧게) + refresh(길게)
- **저장**: 모바일·데스크톱은 `flutter_secure_storage`(Keychain/Keystore).
  **웹은 브라우저 특성상 안전한 저장소가 없으므로**, refresh 토큰은 `HttpOnly` 쿠키로 서버가 내려주고 access 토큰만 메모리에 둔다. (이전 구조에서 두 토큰을 모두 `localStorage`에 두던 XSS 노출을 개선)
- dio 인터셉터가 401을 받으면 refresh를 1회 시도하고, 실패 시 로그인 화면으로 보낸다.

## 9. 설정 주입

API 주소는 **빌드 타임에 주입**한다. (이전 구조에서 `localhost:3000`이 하드코딩되어 실기기에서 연결 불가였던 문제의 해결)

```bash
flutter run --dart-define=API_BASE=https://api.nexus.dev
flutter build apk --dart-define=API_BASE=https://api.nexus.dev
```

`core/env.dart`가 `String.fromEnvironment`로 읽고, 기본값은 개발용 `http://127.0.0.1:3000` 이다(기본 검증 대상이 Windows 라서). Android 에뮬레이터는 `--dart-define=API_BASE=http://10.0.2.2:3000` 을 반드시 넘긴다 — 에뮬레이터에게 `127.0.0.1` 은 자기 자신이다.

2026-10-11 메시지 수정 · 삭제 시점 `app/test/` 에 **665개**가 있다(토큰 강제 · 대비 · 모션 줄이기 검사 포함). 영역별 수는 [CLAUDE.md §5 «알려진 빚»](../CLAUDE.md).

**단위 테스트는 인메모리 drift(`NativeDatabase.memory()`)로 실제 DB 동작까지 덮는다.**
스텁이 아니라 진짜 SQLite 라 정렬·트랜잭션·마이그레이션이 그대로 검증된다.

무엇을 덮을지는 **수동 재현이 얼마나 번거로운가**로 정했다. 아래는 전부 서버를 껐다
켜 가며 손으로 재현해야 하는 것들이다:

- 큐의 전송 순서 (같은 시각에 여러 건, 앞이 실패했을 때)
- 네트워크 실패와 영구 실패의 구분
- 캐시를 재생성해도 큐가 살아남는가
- 답글이 채널 타임라인에 새지 않는가
- 리액션 `mine` 이 보는 사람마다 다르게 계산되는가

**화면 계층은 통합 테스트가 한 줄기로 돈다** — CI 는 창 없이(flutter_tester, 데스크톱 폭) push 마다 돌고,
화면 모습을 바꾼 변경은 사람이 Windows 창으로 `app:flow` 를 돌린다. 실기 한글 IME 는 여전히 사람 눈으로만 확인한다.
그리고 서버 계약은 단위 테스트가 아니라 `npm run check:*` 가 실서버로 확인한다
(두 층을 섞지 않는 이유는 [전환-계획 §6](./전환-계획.md)).

## 11. 구현 순서

1. ✅ 프로젝트 생성 + 스택 배선(Riverpod · go_router · dio · freezed) + 테마
2. ✅ 인증 (로그인 · 토큰 인터셉터) — 가입 화면은 «마지막» 5
3. ✅ 스페이스 선택 — 만들기 · 초대 코드 참여 화면은 16-1, 초대 링크는 «마지막» 3

5. ✅ 채널 목록 + 메시지 리스트 + 전송 (REST만, 낙관적 갱신)
6. ✅ Socket.IO 연결 · 실시간 갱신 · catch-up
7. ✅ drift 캐시 도입 → 단일 진실 공급원으로 전환 + 전송 큐 → **Phase 0**
8. ✅ 리액션 → ✅ 스레드 → ✅ 답장(인용) → ✅ 멘션 → ✅ 핀
9. ✅ 파일 업로드 · 이미지 미리보기 · 파일 목록 (8단계)
10. ✅ 이슈 보드 · 상세 · 라벨 · 스프린트 (9단계)
11. ✅ 저장소 연결 · 이벤트 피드 · 열람 · 커밋 · PR (10 · 11단계) → ✅ AI 패널 (13-1 · 13-2)

> **6과 7의 순서가 계획과 바뀌었다.** 원안은 캐시를 먼저 넣고 소켓을 붙이는
> 순서였는데, 실시간을 뒤로 미루면 앱 상태 계층을 REST 전제로 짰다가 다시 쓰게
