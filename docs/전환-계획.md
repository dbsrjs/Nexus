## 2. 새 최상위 구조

```
nexus/
├─ app/            Flutter — 모바일 · 데스크톱 · 웹        ← 신규 (아직 없음)
├─ server/         NestJS 백엔드                          ← 개편
├─ design-system/  토큰 · 컴포넌트 · 화면 프리뷰 (HTML)
├─ docs/           기획 · 설계
│  └─ archive/     구 사내 UI 디자인 소스 (참고용)
└─ README.md
```

루트 `package.json`은 서버 개발 편의 스크립트만 남긴다. (Flutter 쪽은 `flutter` CLI를 직접 쓴다.)

### 3.4 기존 모듈 이관

> **미이관 모듈은 현재 빌드에서 빠져 있다.** 스키마를 재작성한 순간 이 모듈들은
> 사라진 모델·필드를 참조하게 되어 컴파일되지 않는다. 3단계 이후에 하나씩
> 고칠 것이므로 **소스는 `src/` 에 그대로 두고** `tsconfig.json` ·
> `tsconfig.build.json` 의 `exclude` 로 컴파일 대상에서만 뺐다.
> 대상: `permissions` `notifications` `files` `issues` `gitlab` `ai`.
> `realtime` 은 4단계에서 이관을 마쳤다 — `redis-io.adapter.ts` 하나만 다중
> 인스턴스가 될 때까지 개별 제외돼 있다(스펙 §6).
>
> 되살리는 절차 — ① 두 tsconfig 의 `exclude` 에서 경로 삭제 → ② `spaceId` 기준으로
> 코드 수정 → ③ `app.module.ts` 의 `imports` 에 다시 등록.

- [x] 모든 컨트롤러 라우트를 `/spaces/:spaceId/…` 아래로 — channels · messages · categories

| 4 | `presence:changed` · `issue:updated` 미구현 | — | Redis 프레즌스 + 이슈 서비스 emit | ⬜ 범위 제외(4단계 설계 스펙 §1) — 화면이 없어 검증할 방법이 없다. `issue:updated` 는 이슈 서비스가 붙는 7단계 이후 |

**2단계에서 함께 고친 것 (위 표에 없던 것)**

| 문제 | 조치 |
|---|---|
| `GET /api/users` 가 전역 사용자 목록을 반환 — 멀티테넌트에서 다른 스페이스 사용자까지 노출 | 엔드포인트 제거. 사람 목록은 `GET /api/spaces/:spaceId/members` 로만 |
| `ValidationPipe` 가 DTO 밖 필드를 **조용히 제거**해, 잘못된 요청이 성공으로 보임 | `forbidNonWhitelisted: true` — 400으로 거부 |
| 전역 `Role` 이 JWT 페이로드에 박혀 있어 역할 변경이 토큰 만료 전까지 반영되지 않음 | 토큰에서 역할 제거. 매 요청 `SpaceGuard` 가 DB에서 읽는다 |
| `.env.example` 의 `change-me` 값이 그대로 복사돼 배포될 수 있음 | 필수 시크릿은 **빈 값**으로 두어 부팅이 실패하게 함 |

**4단계에서 새로 발견된 것 (이번 범위 밖, 다음 작업으로 남김)**

| 문제 | 상태 |
|---|---|
| 비공개 채널을 만들어도 생성자가 `channel_members` 에 들어가지 않아, 생성자 본인조차 그 채널을 보거나(404) 메시지를 보낼 수 없다 | ✅ 채널 생성과 생성자 멤버 행 생성을 한 트랜잭션으로 묶었다. 덕분에 4단계에서 실행할 수 없던 격리 케이스(**비공개 채널 메시지가 비참여자에게 새지 않는다**)가 처음으로 검증됐다. 단 채널 멤버 추가·제거 API 는 아직 없어 비공개 채널은 "나만 보는 채널"이다 |
| `updateMemberRole` 의 `rooms:invalidate`(`member.role`)는 코드 리뷰로만 확인 — `check:realtime` 자동 검증에 없음 | ⬜ 두 번째 admin 계정과 역할 왕복이 필요해 검증 스크립트에서 뺐다 |

### 6단계 진행

- [x] **6-1 drift 캐시 — 읽기 경로.** 화면이 로컬 DB 만 구독한다.
      REST 와 소켓은 캐시를 갱신할 뿐이고, 표시는 한 경로로 모인다.
      캐시 대상은 스페이스 · 채널 · 카테고리 · 메시지.

      **에뮬레이터로 확인한 것** — 서버를 끄고 앱을 완전히 종료한 뒤 재시작:
      로그인 화면으로 튕기지 않고(캐시된 계정) 스페이스 → 채널 → 대화까지
      전부 캐시로 그려진다. 서버를 다시 켜면 소켓이 자동 재연결되고
      메시지가 중복 없이 유지된다.

      검증 중 **버그 두 개**를 잡았다.
      ① 오프라인으로 켜면 `/me` 실패를 세션 만료로 취급해 로그인 화면으로
      튕겼다 — 네트워크 실패와 토큰 만료를 구분하고, 마지막으로 확인된 계정을
      보안 저장소에 함께 둔다.
      ② 카테고리만 캐시 밖에 남겨 뒀더니, 오프라인에서 한 번 빈 목록을 받으면
      서버가 돌아와도 채널이 계속 '기타'에 묶여 있었다. **같은 화면을 그리는
      목록이 서로 다른 공급원을 보면 회복되지 않는 틈이 생긴다.**
      카테고리도 캐시로 옮기고 재연결 시 함께 갱신한다. 회귀 테스트 추가.
- [x] **6-2 전송 큐 — 6단계 완료 · Phase 0.** 보내기가 큐에 넣는 일이 됐다.
      네트워크 상태를 묻지 않고, 온라인이면 곧바로 오프라인이면 재연결 때 나간다.

      **큐를 캐시와 다른 테이블(`outbox_messages`)에 뒀다.** 캐시는 서버에서 다시
      받으면 되지만 큐에 있는 것은 사용자가 쓴 유일본이라, 캐시 재생성이 큐를
      건드리지 않아야 한다. 목록은 두 테이블을 `UNION` 하는 쿼리 하나로 읽는다.

      재시도 규칙: **네트워크 실패는 시도 횟수로 치지 않는다**(오프라인은 오류가
      아니다). 401 · 404 는 즉시 실패로 넘기고, 서버 오류는 3회까지 다시 건다.
      한 채널에서 실패하면 그 채널의 뒤 메시지는 이번 회차를 건너뛴다 — 순서가
      뒤집히면 안 되기 때문이다.

      **에뮬레이터로 확인**: 서버를 끈 채 작성 → pending 표시 → 앱 완전 종료 후
      재시작에도 큐 생존 → 서버 기동 시 앱을 건드리지 않아도 자동 전송 · 순서 유지.
      전송 실패 UI 는 채널을 지워 404 를 유발해 확인했고, 채널을 되살린 뒤
      재시도로 전송됐다. 테스트 26개(큐 14개 추가), `flutter analyze` 0건.

      검증 중 결함 **셋**을 잡았다. 모두 오래 켜 두거나 여러 건을 한꺼번에
      보낼 때만 드러나는 종류라, 짧은 수동 확인으로는 나오지 않는다.

      ① 쌓아 둔 메시지를 내보내면 **순서가 뒤집혔다.** drift 가 시각을 초 단위로
      저장해 동률이 된 것이다. 텍스트 저장으로 바꿔 봤더니 `toIso8601String()` 의
      자릿수(마이크로초 0이면 3자리)와 시간대 표기(`Z` vs ` +09:00`)가 일정하지
      않아 더 나빴다 — **UTC 마이크로초 정수**로 확정했다.

      ② 그래도 순서가 뒤집혔다(테스트 15회 중 5회). Windows 의 `DateTime.now()` 는
      밀리초 해상도라 연속 전송이 **완전히 같은 시각**을 갖는다. 시각이 아니라
      **삽입 순번(`seq`)** 으로 정렬하도록 고쳤다.

      ③ 앱을 오래 켜 두면 **소켓이 영영 붙지 않았다.** 핸드셰이크는 연결 시점
      토큰으로 한 번만 검증되는데 액세스 토큰은 15분이다. `SocketUnauthorized` 를
      받고도 아무 처리가 없었고(`reconnectWithFreshToken()` 은 정의만 되어 있었다),
      소켓이 큐 flush 의 계기라 **큐까지 함께 멈췄다.** 토큰을 갱신해 재연결하고,
      채널 진입 시에도 큐를 내보내도록 계기를 하나 더 뒀다.
- [x] **drift 웹 자산** — `sqlite3.wasm` · `drift_worker.js` 를 `app/web/` 에 두었다.
      빌드 산출물 포함과 서빙(200)까지 확인했으나, **웹에서 캐시가 실제로 열리는지는
      미확인**이다(캔버스라 자동화로 로그인을 통과하지 못했다).

- [x] **7-4 멘션.** 본문 파싱 · 멘션 저장 · 안 읽은 멘션 뱃지 · 입력 자동완성.

      저장 형식을 정한 것이 이번 조각의 핵심이다. 본문에 `<@userId>` 를 박는다 -
      `@이름` 을 저장하면 이름을 바꿀 때 지난 메시지가 낡고, 동명이인을 구분할 수
      없으며, 이름 속 공백에서 파싱이 무너진다. 저장 형식은 나중에 바꾸기 가장
      비싼 종류라 처음부터 견고한 쪽을 골랐다.

      그 대가로 **앱의 자동완성이 필수 경로가 된다.** 사용자가 `<@uuid>` 를 직접
      칠 수는 없다.

      **입력창에도 이름이 보인다(7-4 보완).** 처음에는 고른 결과를 그대로
      `<@uuid>` 로 끼워 넣어, 보내기 전까지 입력창에 uuid 가 박혀 있었다 -
      누구를 부른 것인지 읽을 수 없다. 저장 형식은 그대로 두고 **입력창만
      이름을 보여 준 뒤 보낼 때 되돌린다**(`MentionDraft` 가 위치를 들고 있다).
      이름을 본문에 두고 나중에 다시 찾는 방법은 쓰지 않았다 - 이름 속 공백과
      동명이인 문제가 그대로 돌아온다.

      같은 이유로 **인용 요약과 큐에 있는 메시지**도 이름으로 그린다. 둘 다
      멘션 목록이 없어(서버가 본문만 주거나 아직 보내지 않았다) 스페이스 멤버
      목록으로 이름을 채운다.

      안 읽은 멘션 수 쿼리를 처음에 `INNER JOIN channel_members` 로 썼다가 고쳤다.
      공개 채널은 읽음 마커를 남기기 전까지 그 행이 없어 멘션이 통째로 빠진다.

      확인: `npm run check:mentions` 18개, 서버 62개, 앱 91개. 에뮬레이터로
      `@` 입력 · 후보 표시 · **입력창에 `@이름` 표시** · 전송 · `@이름` 렌더 ·
      멘션 뱃지를 확인했고, 서버에는 `<@uuid>` 로 저장된 것을 확인했다.
      인용 블록·답장 미리보기에서도 이름으로 보이고, 이름 안쪽을 지우면
      강조가 풀리며 글자는 남는 것까지 확인했다.

      **알림(푸시 · 알림 센터)은 범위 밖이다** - `notifications` 모듈이 미이관이고

      기다려야 해 스크립트에 넣지 못했고, 부팅 때도 돌게 한 뒤 손으로 확인했다
      (행 삭제 · 파일 삭제 · `storage_used_bytes` 감소).

      검증 중 결함 하나를 잡았다. `.env` 에 `STORAGE_LOCAL_DIR=` 를 자리만 잡아
      두면 `??` 가 빈 문자열을 통과시켜 저장 위치가 작업 디렉터리가 됐다 -
      첨부가 서버 소스 옆에 흩어졌다. 빈 문자열을 미설정으로 친다.
- [x] **8-2 첨부(앱).** 파일 선택, 업로드 진행률, 메시지에 첨부 표시.

      **고르는 즉시 올린다.** 전송 때 몰아 올리지 않는 것은 서버가 그렇게 설계돼
      있어서다 - 업로드가 `message_id` 없이 먼저 끝나고 전송이 이어 붙인다. 큰
      파일이 올라가는 동안에도 본문을 계속 쓸 수 있고, 전송 순간에는 기다릴 것이
      없다. 대신 **올라가는 중에는 전송을 막는다** - 아직 id 가 없는 첨부는 실을
      수 없고, 빼고 보내면 붙인 파일이 조용히 사라진다.

      **큐에는 파일이 아니라 id 를 담는다.** 업로드는 온라인에서만 되지만 한 번
      올라가면 그 뒤 오프라인이 되어도 메시지는 큐에서 기다렸다 나간다. 다만
      24시간 안에 나가야 한다 - 그 전에 연결되지 못한 첨부는 서버가 지운다.

      채널을 옮기면 담아 둔 첨부를 버린다. 업로드 주소에 채널이 들어 있어, 들고
      옮기면 엉뚱한 채널에 올라간 파일을 붙이게 된다.

      확인: `flutter analyze` 0건, `flutter test` 102개. 에뮬레이터로 선택 ·
      업로드 완료 표시 · 전송 · 첨부 행 표시를 확인했고 첨부만 있는 메시지도
      확인했다. 서버 DB 와 대조해 메시지 하나에 첨부 하나가 정확히 연결되고
      고아가 남지 않는 것까지 봤다.

      결함 둘을 **읽어서** 잡았다. 하나는 Dart 에서 `..` 가 대입보다 느슨해
      `a ??= B()..listen()` 이 `(a ??= B())..listen()` 으로 묶여 getter 를 읽을
      때마다 리스너가 붙은 것이고, 다른 하나는 담아 둔 첨부를 비우는 일을
      `build()` 안에서 해 build 중 `setState` 가 된 것이다.

## 6. 실행 순서

> **2026-08-13 개정.** 원안은 계층을 하나씩 완성해 올라가는 순서였고, 그 결과 5단계까지 화면이 하나도 없었다. 화면이 없으면 **Flutter 한 코드베이스가 6개 플랫폼을 감당하는지, 디자인 시스템이 Flutter에서 그대로 나오는지, 토큰 회전이 실기기에서 동작하는지, API 응답 모양이 실제 화면에 맞는지** — 이 중 어느 것도 검증되지 않는다. 서버를 아무리 쌓아도 답이 안 나오는 항목들이다.
>
> 그래서 **3·4단계를 뼈대만 남기고 앱을 앞으로 당긴다.** 다만 잘라내는 기준을 둔다:
>
> - **잘라도 되는 것 — 스레드 · 리액션 · 멘션 · 핀.** 테이블이 이미 다 있고 기존 엔드포인트를 거의 건드리지 않는 **덧붙이는 작업**이라, 뒤로 미뤄도 재작업이 없다.
> - **자르면 안 되는 것 — 실시간.** 메시지 목록을 "REST로 한 번 가져오는 것"으로 전제하고 앱 상태 계층을 짜면, 나중에 소켓을 붙일 때 그 계층을 다시 쓴다. 채팅 앱에서 가장 비싼 재작업이라 **앱보다 먼저** 최소한이라도 넣는다.
>
> **미룰 것은 기능이지 구조가 아니다.** 그리고 첫 세로 한 줄이 끝난 뒤부터는 작업 단위를 계층에서 **기능**으로 바꾼다 — 한 기능이 서버에서 화면까지 끝나야 완료로 친다. 그러면 이후로 "화면 없는 구간"이 다시 생기지 않는다.

|---|---|---|
| ~~**1**~~ ✅ | 기존 자산 정리 (§1 삭제 · 아카이브), 루트 구조 재편 | 빈 슬레이트 |
