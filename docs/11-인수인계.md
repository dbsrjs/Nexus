| 결함 | 원인 | 커밋 |
|---|---|---|
| PR 본문의 `## Summary` 가 제목으로 안 그려짐 | GitHub 본문이 **CRLF** 다. 파서가 `'\n'` 으로만 쪼개 줄 끝에 `\r` 이 남았고, Dart 에서 `.` 는 `\r` 을 지나치지 못하고 `$` 는 입력 끝에서만 맞아 **`$` 로 끝나는 제목 · 번호목록 정규식만** 실패했다. 인용은 `startsWith` 라 멀쩡했고 그 비대칭이 증상 | `ca7f1b9` |

## 4. 되돌리면 안 되는 결정들

### 4.1 `readPullNumber` 는 `payload.raw` 를 벗긴다

**계약 검증이 잡은 진짜 버그다.** `WebhooksService` 는 GitHub 원본을
`{ deliveryId, event, raw }` 로 **한 겹 감싸** 저장한다. `readPushCommits` 는
벗기고 읽는데 `readPullNumber` 는 벗기지 않아 **PR 이벤트가 언제나 `other` 로
접혔다.** 단위 테스트도 이미 벗겨진 객체를 넘겨서 이 경로를 못 잡았다 —
**실서버로 태워야만 드러났다.**

`pr-event.spec.ts` 의 테스트는 **실제로 저장되는 감싼 모양**을 넘긴다. 벗겨진
모양으로 되돌리면 틀린 계약을 다시 굳히게 된다.

### 4.2 `pull_requests` 테이블을 쓰지 않는다

백엔드 설계에 "웹훅으로 upsert 해 그것을 화면의 소스로 쓴다"고 적혀 있었으나
**뒤집었다.** 사본을 두면 ① 연결 전에 열린 PR 이 안 보이고(백필이 숙제가 된다)
② 웹훅을 놓치면 행이 영영 어긋난다 — 이 프로젝트의 터널은 띄울 때마다 주소가
바뀐다. 10-2b 가 저장소 목록에서 같은 이유로 프록시를 골랐다.

이유는 [설계 스펙 §0](superpowers/specs/2026-08-30-PR-열람-design.md) 이 원본이고,
백엔드 설계의 해당 자리 여섯 곳에 취소선과 함께 그리로 가리키는 줄을 남겼다.

### 4.3 diff 를 그리지 않는다

`/diff` 대신 `/files` 를 두고, 파일을 누르면 10-3a 의 파일 보기가 head 브랜치로
열린다. 10-3b 의 판단을 그대로 이은 것이다 — 줄 단위 diff 렌더러는 통합 diff
파싱 · 헝크 · 긴 줄 · 접기를 전부 새로 만드는 일이고, "무엇이 바뀌었더라"의
대부분은 바뀐 파일 목록이 이미 답한다.

### 4.4 모르는 값은 `null` 이고 `0` 이 아니다

GitHub 의 PR **목록** API 는 `additions` · `deletions` · `changed_files` 를 주지
않는다(단건에만 있다). 채우려면 PR 마다 왕복이 하나씩 더 붙는다. 그래서 목록에는
변경량을 그리지 않고, 모르면 화면이 **아예 말하지 않는다**. 0 으로 두면
"안 바뀐 PR"로 읽힌다. 10-3b 의 `changedCount` 와 같은 규칙이다.

### 4.5 리뷰의 `null` 은 `pending` 이 아니다

리뷰어마다 **마지막 것만** 세고 `COMMENTED` · `DISMISSED` 는 버린다. 남은 것이
없으면 `null` 이고 화면은 **리뷰 칸 자체를 만들지 않는다**. `PullReviewState` 에
`pending` 값을 만들면 안 된다 — GitHub 의 `PENDING` 은 제출하지 않은 초안이라
남에게 보이지도 않는 값이다.

### 4.6 파일 행은 `ListTile` 이어야 한다

위젯 테스트가 `onTap == null` 로 "지워진 파일은 누를 수 없다"를 확인한다. 다른
위젯으로 바꾸면 그 테스트가 조용히 무의미해진다.

| `pulls.controller.ts` | `ParseIntPipe` 가 음수를 통과시켜 `/pulls/-5` 가 GitHub 까지 갔다 404 로 돌아온다. `?page=2.5` 도 정수 검사 없이 실린다 |
| `github-oauth.client.ts` | 파일이 **정확히 300개**면 `truncated: true` 가 뜬다(4장째를 부르지 않으면 "정확히 300"과 "300 초과"를 구분할 수 없다). 모를 때 truncated 쪽으로 기우는 것이 의도다 |
| `chat_screen.dart:101` | `catch (_)` 가 모든 예외를 삼킨다(스레드 열기 쪽. 저장소 이벤트 쪽은 고쳤다). 탭 실패를 조용히 넘기는 것은 의도지만 개발 중 프로그래머 오류도 가린다 |
| `pulls_screen.dart` | 위젯 테스트가 **더 불러오기 · 빈 목록 문구**까지는 생겼다(`pulls_list_test.dart`). **필터 전환 · 미연결 폴백**은 아직이다. «더 불러오기» 버튼이 로딩 중 비활성이 아니라 아예 사라지는 것도 그대로다 |
| `pulls_screen.dart` · `pull_detail_screen.dart` | **`autoDispose` 가 빠져 목록 · 상세가 앱을 끌 때까지 굳는다.** 이 프로젝트의 «캐시하지 않는» 화면 다섯(파일 목록 · 이슈 상세 · 댓글 · 라벨 · 번다운)은 전부 `autoDispose` 인데 이 둘만 빠졌다. 성공한 결과에는 새로고침 경로도 없어, PR 이 머지돼도 「열림」 으로 남는다 |
| `github-oauth.client.ts` (리뷰) | `getPullReview` 가 `per_page=100` **한 장만** 받는다. GitHub 은 리뷰를 오래된 것부터 주므로, 리뷰가 100건을 넘으면 최신 리뷰가 통째로 빠져 이미 해결된 「변경 요청됨」 이 계속 뜬다. 같은 파일의 `listPullFiles` 는 3장까지 도는 것과 어긋난다 |
| `pull_detail_screen.dart` | 변경량을 `additions` 하나로만 검사하고 `deletions` · `changedFiles` 를 그린다. 셋이 각각 nullable 이라 나머지가 비면 «−null · 파일 null개» 가 찍힌다 — «모르면 말하지 않는다» 규칙이 정작 더 나쁜 표시를 낸다 |
| `pull-view.ts` | `pr.number` 가 `Number.isFinite` 를 거치지 않아 NaN 이 통과할 수 있다 |
| `github-error.ts` · `http-exception.filter.ts` | **`toGithubHttpError` 가 만드는 오류의 `error` 라벨이 전부 틀린다.** 401 응답이 `{"statusCode":401, …, "error":"InternalServerError"}` 로 나간다 — `new HttpException('문자열', 상태)` 는 `getResponse()` 가 문자열을 돌려주는데 필터의 그 갈래가 `error` 를 채우지 않는다(429 는 객체를 넘겨 `"HttpException"` 이 된다). 앱은 상태 코드만 보므로 화면에는 영향이 없다. 2026-09-01 화면 확인 중 응답 본문을 보다 찾았다 |

**딸려 바뀐 동작 하나** — `GET /me/github/repos` 가 GitHub 404 를 받으면 예전에는
502 였는데 이제 **404** 다. 오류 변환 함수 두 벌을 하나로 합치며 그렇게 됐고,
502("GitHub 에서 못 받았다")보다 404 가 정확하다고 판단해 받아들였다. 사용처는
저장소 목록 한 곳이고 `/user/repos` 는 자원 id 를 받지 않아 실제로는 거의 나오지
않는다.

## 6. 이 PC 에만 있고 옮겨지지 않는 것

- **`server/.env`** — §2.3 참고. 대부분은 `npm run env:setup` 이 만들어 낸다
- **DB 전체** — 계정 · 스페이스 · 채널 · 메시지 · **저장소 등록과 웹훅 시크릿**.
  시드로 새로 만들어진다. §3.1 의 6·7번을 태우려면 회사 PC 에서 저장소를 다시 붙여야 한다
- **`.superpowers/sdd/2026-08-30-11-PR-열람/`** — 태스크 브리프 11개 · 구현자
  보고서 · 리뷰 diff · **진행 원장(`progress.md`)**. `.gitignore` 대상이라 넘어가지
  않는다. 이 문서 §4 · §5 가 그중 넘길 값이 있는 것을 옮겨 적은 것이다
- `app/.dart_tool/` 빌드 캐시. `app/pubspec.lock` 이 뒤집히면 **커밋하지 말고
  `git restore`**

**`build_runner` 가 멈추면** — 이번에도 겪었다. 그 프로세스만 죽이고
`app/.dart_tool/build` 를 지운 뒤 다시 돌리면 35초에 끝난다. `dart.exe` 를 전부
죽이지 말 것(VS Code 의 language server 가 섞여 있다).
