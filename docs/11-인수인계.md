## 2. 회사 PC 에서 이어받는 절차

### 2.1 브랜치

```bash
git fetch origin
git checkout feat/pr-browse
```

**`main` 에는 아직 합치지 않았다.** 화면 확인이 끝나기 전에는 합치지 않는 편이 낫다.

### 2.2 DB · 서버

CLAUDE.md §1 과 같다. 새 PC 라면 `npm run env:setup` → `db:setup` → `db:up` →
`prisma:generate` → `prisma:deploy` → `db:seed` 순이다.

### 2.3 `.env` — `npm run env:setup` 뒤에 남는 것

시크릿 셋(JWT 둘 · `OAUTH_TOKEN_KEY`)은 스크립트가 그 PC 에서 새로 만든다.
**손으로 채워야 하는 것은 아래뿐이다.**

| 키 | 값 |
|---|---|
| `GITHUB_CLIENT_ID` · `GITHUB_CLIENT_SECRET` | GitHub OAuth App. 콜백이 양쪽 PC 다 localhost 라 **PC 마다 따로 등록해도 된다** |
| `PUBLIC_BASE_URL` | 계약 검증만 돌릴 거면 `http://127.0.0.1:3000` 이면 된다. 진짜 웹훅을 받으려면 cloudflared 터널 주소 |
| `GITHUB_OAUTH_BASE` · `GITHUB_API_BASE` | **계약 검증을 돌릴 때만** `http://127.0.0.1:4599`. 진짜 GitHub 에 붙일 때는 **비운다**(바꾸면 서버 재시작) |

### 2.4 검증 — 이어받자마자 돌려 상태를 확인한다

```bash
npm run check:pulls     # 35개
npm run check:browse    # 56개
npm --prefix server test
cd app && flutter analyze && flutter test
```

기대값: 35 · 56 · 181 · 0건 · 235. 하나라도 어긋나면 **그것부터** 본다.

## 3. 바로 다음에 할 일

### 3.1 화면을 눈으로 본다 (가장 중요)

```bash
cd app && flutter run -d windows --dart-define=API_BASE=http://127.0.0.1:3000
```

**개발 빌드는 시작 메뉴에 없어 자동화 도구가 창을 잡지 못한다 — 사람이 봐야 한다.**
화면 확인용 계정은 `design@example.com` / `design-check-1234` 다.

확인할 일곱 갈래:

1. 저장소 → 앱바의 **PR 아이콘**(커밋 아이콘 왼쪽) → 열린 PR 목록
2. 필터를 «닫힘»으로 → 머지된 것에 **«머지됨» 칩**(«닫힘»이 아니어야 한다)
3. 상세 — 본문이 마크다운으로 그려짐 · 변경량(`+12 −3`) · **리뷰 칸이 없음**
   (혼자 쓰는 저장소라 비는 것이 정상이다. 칸이 보이면 그게 결함이다)
4. 파일을 눌러 **그 PR 브랜치 시점의 전문**이 열림(기본 브랜치가 아니어야 한다)
5. **지워진 파일은 눌리지 않음**(회색)
6. 채널의 «… PR #n 를 열었습니다» 를 눌러 **PR 상세로** 감
7. push 메시지는 **여전히 커밋 목록으로** 가고, 이슈 메시지는 **아무 일도 안 함**

**주의: 이 PC 의 DB 에는 PR 이벤트 메시지가 없다.** 6·7번을 태우려면 회사 PC 에서
저장소를 붙이고 실제로 PR 을 열거나, 웹훅을 손으로 쏘아야 한다.
`server/scripts/check-pulls.mjs` 가 PR·이슈 웹훅을 만들어 보내는 코드를 갖고 있으니
그것을 참고하면 된다.

### 3.2 최종 리뷰 (SDD 절차)

태스크별 리뷰는 다 돌았지만 **브랜치 전체를 보는 최종 리뷰는 아직이다.** 화면
확인이 끝난 뒤에 돌리는 편이 낫다 — 거기서 나온 수정까지 함께 보게 된다.

```
git merge-base main HEAD   # 기점
```

리뷰어에게 아래 §4 와 «파킹한 것»(§5)을 함께 넘겨 병합 전 처리 여부를 분류하게 한다.

### 3.3 문서 마무리

화면 확인이 끝나면 CLAUDE.md §4 의 «11 PR 열람» 절에서 «확인하지 못한 것»의
화면 항목을 실제 결과로 바꾼다. **지금은 "보지 않았다"라고 정직하게 적혀 있다.**

## 4. 되돌리면 안 되는 결정들

### 4.1 `readPullNumber` 는 `payload.raw` 를 벗긴다

**계약 검증이 잡은 진짜 버그다.** `WebhooksService` 는 GitHub 원본을
`{ deliveryId, event, raw }` 로 **한 겹 감싸** 저장한다. `readPushCommits` 는
벗기고 읽는데 `readPullNumber` 는 벗기지 않아 **PR 이벤트가 언제나 `other` 로
접혔다.** 단위 테스트도 이미 벗겨진 객체를 넘겨서 이 경로를 못 잡았다 —
**실서버로 태워야만 드러났다.**

`pr-event.spec.ts` 의 테스트는 **실제로 저장되는 감싼 모양**을 넘긴다. 벗겨진
모양으로 되돌리면 틀린 계약을 다시 굳히게 된다.

### 4.2 `pull_requests` 테이블을 쓰지 않는다

백엔드 설계에 "웹훅으로 upsert 해 그것을 화면의 소스로 쓴다"고 적혀 있었으나
**뒤집었다.** 사본을 두면 ① 연결 전에 열린 PR 이 안 보이고(백필이 숙제가 된다)
② 웹훅을 놓치면 행이 영영 어긋난다 — 이 프로젝트의 터널은 띄울 때마다 주소가
바뀐다. 10-2b 가 저장소 목록에서 같은 이유로 프록시를 골랐다.

이유는 [설계 스펙 §0](superpowers/specs/2026-08-30-PR-열람-design.md) 이 원본이고,
백엔드 설계의 해당 자리 여섯 곳에 취소선과 함께 그리로 가리키는 줄을 남겼다.

### 4.3 diff 를 그리지 않는다

`/diff` 대신 `/files` 를 두고, 파일을 누르면 10-3a 의 파일 보기가 head 브랜치로
열린다. 10-3b 의 판단을 그대로 이은 것이다 — 줄 단위 diff 렌더러는 통합 diff
파싱 · 헝크 · 긴 줄 · 접기를 전부 새로 만드는 일이고, "무엇이 바뀌었더라"의
대부분은 바뀐 파일 목록이 이미 답한다.

### 4.4 모르는 값은 `null` 이고 `0` 이 아니다

GitHub 의 PR **목록** API 는 `additions` · `deletions` · `changed_files` 를 주지
않는다(단건에만 있다). 채우려면 PR 마다 왕복이 하나씩 더 붙는다. 그래서 목록에는
변경량을 그리지 않고, 모르면 화면이 **아예 말하지 않는다**. 0 으로 두면
"안 바뀐 PR"로 읽힌다. 10-3b 의 `changedCount` 와 같은 규칙이다.

### 4.5 리뷰의 `null` 은 `pending` 이 아니다

리뷰어마다 **마지막 것만** 세고 `COMMENTED` · `DISMISSED` 는 버린다. 남은 것이
없으면 `null` 이고 화면은 **리뷰 칸 자체를 만들지 않는다**. `PullReviewState` 에
`pending` 값을 만들면 안 된다 — GitHub 의 `PENDING` 은 제출하지 않은 초안이라
남에게 보이지도 않는 값이다.

### 4.6 파일 행은 `ListTile` 이어야 한다

위젯 테스트가 `onTap == null` 로 "지워진 파일은 누를 수 없다"를 확인한다. 다른
위젯으로 바꾸면 그 테스트가 조용히 무의미해진다.

## 5. 파킹한 것 — 최종 리뷰가 병합 전 처리 여부를 정한다

| 자리 | 내용 |
|---|---|
| `api_failure.dart:36-56` | **미연결(400)과 서버 오류(500)가 구분되지 않는다.** `classifyDioException` 에 `case 400` 이 없어 둘 다 `ApiFailure.server` 로 접히고, 그래서 진짜 500 에도 «GitHub 을 연결하세요» 가 뜬다. 고치려면 **앱의 모든 API 의 실패 분류를 바꾸는 일**이라 이 단계 범위를 넘겼다 |
| `pulls.service.ts` · `repo-browse.service.ts` | `nextPage`/`nextCursor` 를 **필터링된 뒤** 길이로 판단한다. 30건 중 하나라도 모양이 깨지면 29가 되어 다음 장이 조용히 사라진다. 커밋 목록도 같은 방식이라 신규 결함은 아니다 — 고친다면 두 곳을 함께 |
| `pulls.controller.ts` | `ParseIntPipe` 가 음수를 통과시켜 `/pulls/-5` 가 GitHub 까지 갔다 404 로 돌아온다. `?page=2.5` 도 정수 검사 없이 실린다 |
| `github-oauth.client.ts` | 파일이 **정확히 300개**면 `truncated: true` 가 뜬다(4장째를 부르지 않으면 "정확히 300"과 "300 초과"를 구분할 수 없다). 모를 때 truncated 쪽으로 기우는 것이 의도다 |
| `chat_screen.dart:101` | `catch (_)` 가 모든 예외를 삼킨다. 탭 실패를 조용히 넘기는 것은 의도지만 개발 중 프로그래머 오류도 가린다 |
| `pulls_screen.dart` | `PullsScreen` 자체를 겨눈 위젯 테스트가 없다(필터 전환 · 더 불러오기 · 미연결 폴백). «더 불러오기» 버튼이 로딩 중 비활성이 아니라 아예 사라진다 |
| `pull-view.ts` | `pr.number` 가 `Number.isFinite` 를 거치지 않아 NaN 이 통과할 수 있다 |

**딸려 바뀐 동작 하나** — `GET /me/github/repos` 가 GitHub 404 를 받으면 예전에는
502 였는데 이제 **404** 다. 오류 변환 함수 두 벌을 하나로 합치며 그렇게 됐고,
502("GitHub 에서 못 받았다")보다 404 가 정확하다고 판단해 받아들였다. 사용처는
저장소 목록 한 곳이고 `/user/repos` 는 자원 id 를 받지 않아 실제로는 거의 나오지
않는다.

## 6. 이 PC 에만 있고 옮겨지지 않는 것

- **`server/.env`** — §2.3 참고. 대부분은 `npm run env:setup` 이 만들어 낸다
- **DB 전체** — 계정 · 스페이스 · 채널 · 메시지 · **저장소 등록과 웹훅 시크릿**.
  시드로 새로 만들어진다. §3.1 의 6·7번을 태우려면 회사 PC 에서 저장소를 다시 붙여야 한다
- **`.superpowers/sdd/2026-08-30-11-PR-열람/`** — 태스크 브리프 11개 · 구현자
  보고서 · 리뷰 diff · **진행 원장(`progress.md`)**. `.gitignore` 대상이라 넘어가지
  않는다. 이 문서 §4 · §5 가 그중 넘길 값이 있는 것을 옮겨 적은 것이다
- `app/.dart_tool/` 빌드 캐시. `app/pubspec.lock` 이 뒤집히면 **커밋하지 말고
  `git restore`**

**`build_runner` 가 멈추면** — 이번에도 겪었다. 그 프로세스만 죽이고
`app/.dart_tool/build` 를 지운 뒤 다시 돌리면 35초에 끝난다. `dart.exe` 를 전부
죽이지 말 것(VS Code 의 language server 가 섞여 있다).
