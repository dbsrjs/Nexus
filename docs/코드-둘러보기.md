무엇을 어떤 순서로 보면 되는지. **스택 자체를 배우는 순서**는
[기술-스택-가이드.md](./기술-스택-가이드.md) 에 따로 있다.

> 파일을 위에서부터 훑지 말 것. 이 문서는 **돌아가는 것을 먼저 보고, 그다음 한 줄기를

## 1. 먼저 돌아가는 걸 본다

### 서버가 자기 라우트를 전부 찍어 준다

```bash
npm run db:up
npm run server:dev
```

부팅 로그에 이런 줄이 쭉 나온다:

```
Mapped {/api/auth/login, POST}
Mapped {/api/me, GET}
Mapped {/api/spaces, GET}
Mapped {/api/spaces/:spaceId/channels, GET}
Mapped {/api/spaces/:spaceId/channels/:channelId/messages, POST}
Mapped {/api/spaces/:spaceId/messages/:messageId, PATCH}
```

**이 목록이 곧 API 계약이다.** Swagger 같은 별도 문서가 없는 이유이기도 하다 — 서버가
실제로 등록한 것만 나오므로 문서와 코드가 어긋날 수 없다.

### 데이터는 Prisma Studio 로 클릭해서 본다

```bash
npm run db:studio
```

브라우저에서 테이블을 열고 행을 눌러 관계를 타고 다닐 수 있다. `spaces` → `channels`
→ `messages` 순으로 눌러 보면 데이터가 어떻게 엮여 있는지 SQL 없이 보인다.

### 실시간이 정말 도는지 보고 싶으면

```bash
npm run check:realtime -- <시드비밀번호>
```

실제 서버 · 실제 DB · 실제 소켓으로 41개 케이스를 돌린다. **출력 자체가 소켓 계약의
목록**이다 — 어떤 이벤트가 언제 누구에게 가는지 한글로 한 줄씩 찍힌다.

### 앱은 Windows 로 띄운다

```bash
cd app
flutter run -d windows --dart-define=API_BASE=http://127.0.0.1:3000
```

**기본 검증 대상은 Windows 하나로 좁혀 두었다** ([앱-설계 §0-1](./앱-설계.md)).
빌드 23초에 즉시 실행이라 개발 루프가 가장 짧다.

나머지는 슬라이스 경계에서만 확인한다.

```bash
# 웹 — 포트 5173 고정 (서버 CORS_ORIGINS 가 이 주소만 허용)
flutter run -d chrome --web-port=5173 --dart-define=API_BASE=http://127.0.0.1:3000

# Android 에뮬레이터 — 호스트 주소가 다르다. 에뮬레이터에게 127.0.0.1 은 자기 자신이다
flutter run -d emulator-5554 --dart-define=API_BASE=http://10.0.2.2:3000
```

iOS 는 동결이다 — macOS 없이는 빌드되지 않는다.
그 밖의 플랫폼 사정은 [CLAUDE.md §1 · §2](../CLAUDE.md) 에 있다.

## 2. 서버 구조

```
server/src/
  main.ts            부팅 — CORS · 전역 파이프 · BigInt 직렬화 · 소켓 어댑터 (67줄)
  app.module.ts      켜져 있는 모듈의 목차 (50줄)
  config/            JWT 시크릿 해석의 유일한 지점
  auth/              가입 · 로그인 · 리프레시 회전 · 재사용 탐지
  users/             /api/me 만. 전역 사용자 목록은 없다(테넌트 격리)
  spaces/            스페이스 · 멤버 · 초대 + SpaceGuard   ← 격리의 심장
  categories/        채널 그룹
  channels/          채널 · 가시성 규칙 · 읽음 마커 (388줄, 가장 두껍다)
  messages/          목록 · 전송 · 수정 이력 · 소프트 삭제
  realtime/          소켓 게이트웨이 · 룸 계산 · 이벤트 발신
  prisma/ common/    DB 클라이언트 · 예외 필터 · 데코레이터 · 페이지네이션
```

`src/` 아래에는 이 밖에 `permissions` `notifications` `files` `issues` `gitlab` `ai` 도
보이는데, **옛 스키마를 참조해 컴파일되지 않는다.** 두 `tsconfig` 의 `exclude` 로
빌드에서 빠져 있고 `app.module.ts` 에도 없다. 참고용 잔해이니 헷갈리지 말 것.

### 각 모듈의 파일이 하는 일

NestJS 는 파일 이름이 곧 역할이다.

| 파일 | 역할 |
|---|---|
| `*.module.ts` | 이 모듈이 무엇을 쓰고 무엇을 내보내는지 (배선) |
| `*.controller.ts` | URL → 메서드 연결. **로직은 거의 없다** |
| `*.service.ts` | 실제 로직. 여기를 읽어야 한다 |
| `dto/*.dto.ts` | 요청 본문의 모양 + 검증 규칙 |
| `guards/*.guard.ts` | 라우트에 들어가기 전 통과 검사 |

## 3. 한 줄기를 끝까지 따라가기 — 가장 빠른 이해법

**"메시지를 보낸다" 요청 하나**를 쫓아가면 이 코드베이스의 규칙이 한 번에 보인다.

| # | 어디 | 무슨 일이 |
|---|---|---|
| 1 | [`channels.controller.ts`](../server/src/channels/channels.controller.ts) 의 `@Post(':channelId/messages')` | URL 을 받는다. 컨트롤러는 넘기기만 한다 |
| 2 | [`space.guard.ts`](../server/src/spaces/guards/space.guard.ts) (55줄) | 이 사람이 그 스페이스 멤버인가? **아니면 403 이 아니라 404** |
| 3 | [`messages.service.ts`](../server/src/messages/messages.service.ts) 의 `create()` | 로직 시작 |
| 4 | [`channels.service.ts`](../server/src/channels/channels.service.ts) 의 `assertCanSend()` → `canView()` | 공개/비공개 가시성 규칙 |
| 5 | Prisma | DB 저장 |
| 6 | [`realtime-emitter.ts`](../server/src/realtime/realtime-emitter.ts) | `message:new` 를 `channel:{id}` 룸에 쏜다 |

**하나만 읽는다면 2번**을 권한다. 55줄짜리인데 이 프로젝트의 최우선 규칙(테넌트 격리)이
어떻게 강제되는지가 거기 다 있다.

### 다른 줄기들

| 궁금한 것 | 따라갈 곳 |
|---|---|
| 로그인하면 무슨 일이 | `auth.controller.ts` → `auth.service.ts` → `refresh-token.service.ts` |
| 왜 토큰을 두 개 쓰나 | `refresh-token.service.ts` — 회전과 **재사용 탐지** |
| 소켓이 어떻게 인증되나 | `realtime.gateway.ts` 의 `afterInit` 안 미들웨어 |
| 어느 룸에 들어가나 | `rooms.service.ts` 의 `computeRooms()` |
| 안 읽은 수는 어떻게 세나 | `channels.service.ts` 의 `unreadCounts()` — 유일한 raw SQL |

## 5. 앱 구조 (`app/lib/`)

[앱-설계.md §3](./앱-설계.md) 의 구조를 따르되 **쓰는 것만 만든다.**

```
core/env.dart            API 주소를 읽는 유일한 지점
core/theme.dart          design-system/tokens.css 이식
core/router.dart         go_router + 인증 가드
core/breakpoints.dart    Layout(mobile 600 tablet 1024 desktop) + 고정 폭
data/api/api_client.dart dio + 401 → 리프레시 1회 재시도
data/api/auth_api.dart   login · me · logout
data/api/spaces_api.dart GET /spaces
data/auth_storage.dart   flutter_secure_storage 래퍼
domain/models/           freezed 모델 (User · AuthTokens · Space)
features/auth/           로그인 화면 + 컨트롤러
features/space/          스페이스 선택 화면 + provider
features/shell/          반응형 셸 — app_shell · space_rail · channel_pane
shared/widgets/          NexusAvatar 등 공용 위젯
```

앱도 한 줄기가 있다: **로그인 버튼 → `auth_controller.signIn()` → `auth_api.login()` →
`api_client` (dio) → 토큰 저장 → 상태 변경 → `router` 의 `redirect` 가 `/spaces` 로 →
스페이스를 고르면 `/s/:spaceId` 의 `AppShell`.**
`core/router.dart` 의 `redirect` 함수를 먼저 읽으면 화면 전환이 왜 그렇게 되는지 보인다.

**반응형은 `features/shell/app_shell.dart` 하나만 보면 된다.** 폭 분기가 거기에만 있고,
안쪽 위젯(`SpaceRail` · `ChannelPane` · 본문)은 자기가 어떤 폭에 있는지 모른다.
이 규칙이 깨지면 반응형 분기가 화면마다 흩어져 손댈 수 없게 된다.
