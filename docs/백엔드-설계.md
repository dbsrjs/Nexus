# Nexus — 백엔드 설계서

> 개정 이력: 2026-08-11 — 사내 단일 테넌트 → **멀티테넌트(Space)** 로 전면 개정.
> 제품 방향은 [제품 기획서](./제품-기획.md), 클라이언트는 [앱 설계서](./앱-설계.md) 참조.

## 1. 기술 결정

| 항목 | 결정 | 이전 대비 |
|---|---|---|
| 프레임워크 | **NestJS 10** (TypeScript) | 유지 |
| RDB | **PostgreSQL** + Prisma | 유지 |
| 캐시 · 실시간 | **Redis** (프레즌스 · Socket.IO 어댑터 · 큐) | 유지 |
| 실시간 | **Socket.IO** | 유지 |
| 파일 저장 | **S3 호환 추상화** (개발: MinIO 컨테이너 / 운영: S3 · R2) | 온프렘 MinIO 고정 → **교체 가능** |
| 호스팅 | **클라우드 전제**, 온프렘 배포도 가능 | 온프렘 고정 → 변경 |
| 인증 | 이메일+비밀번호(argon2) + **회원가입** + **GitHub OAuth** | 가입 흐름 신설 |
| 테넌시 | **Space 단위 멀티테넌트** | 단일 테넌트 → **전면 변경** |
| 이슈 | 자체 구현 (`IssueProvider` 추상화 유지) | 유지 |
| 저장소 연동 | **GitHub · GitLab** 웹훅 + 폴링 | GitLab 읽기 전용 → 확장 |
| AI | **실제 기능** (외부 LLM API) | 501 스텁 → **승격** |

> **왜 NestJS를 유지하는가**: TypeScript · PostgreSQL · Redis · Socket.IO 조합은 이 도메인에서 가장 보편적인 선택이고, 이미 동작하는 구현이 있다. 프레임워크를 바꿔서 얻는 것보다 잃는 것이 크다.

## 2. 멀티테넌시 — 가장 중요한 변경

이전 스키마는 채널 목록이 전역이고 사용자 역할이 전역 enum이었다. 조직이 하나라는 전제였다. **Space를 도입해 모든 데이터에 테넌트 경계를 긋는다.**

```
Space (테넌트 루트)
 ├─ SpaceMember   (User × Space, 역할은 여기에)
 ├─ Invite
 ├─ Category
 │   └─ Channel
 │       ├─ ChannelMember       (읽음 마커)
 │       ├─ ChannelPermission   (역할별 view/send)
 │       └─ Message
 │           ├─ Message (parentId — 스레드 답글)
 │           ├─ MessageEdit
 │           ├─ Reaction
 │           ├─ Mention
 │           └─ Attachment
 ├─ Issue → IssueComment
 ├─ Repo  → RepoEvent
 └─ AiRun
```

### 격리 규칙 (반드시 지킨다)

1. **테넌트 소속 테이블은 예외 없이 `spaceId` 컬럼을 갖는다.** 부모를 타고 유추 가능해도 비정규화해서 직접 들고 있는다 — 모든 쿼리의 `WHERE`에 강제로 넣기 위함이다.
2. 모든 서비스 메서드는 `spaceId`를 **첫 인자로** 받는다. 옵션이 아니다.
3. `SpaceGuard`가 URL의 `:spaceId`에 대한 요청자의 멤버십을 검증하고 `req.spaceMember`에 실어 준다. 컨트롤러는 이후 신뢰한다.
4. Phase 2 착수 전, **"A 스페이스 사용자가 B 스페이스 리소스에 접근하면 404"** 를 모든 엔드포인트에 대해 확인하는 통합 테스트를 둔다.

## 3. 데이터 모델

`id`는 uuid, `created_at`/`updated_at`은 공통이므로 표기 생략.

### 계정 · 테넌트

**users** — 전역 계정
`email unique, password_hash(nullable — OAuth 전용 계정), name, avatar_url, global_status(online/away/offline)`

**oauth_accounts** — 소셜 로그인 연결
`user_id FK, provider(github/gitlab), provider_user_id, access_token(암호화), UNIQUE(provider, provider_user_id)`

> 저장소 연동에 쓸 토큰을 여기서 함께 확보한다. GitHub 로그인 → 저장소 연결이 추가 인증 없이 이어진다.

**spaces**
`slug unique, name, icon_url, owner_id FK`

**space_members**
`space_id FK, user_id FK, role enum(owner|admin|member|guest), nickname, joined_at` · PK `(space_id, user_id)`

**invites**
`space_id FK, code unique, created_by FK, role(가입 시 부여), expires_at, max_uses, use_count`

### 채널 · 메시지

**categories**
`space_id FK, name, position`

**channels**
`space_id FK, category_id FK null, key, name, topic, kind enum(text|dm), is_private, position` · UNIQUE `(space_id, key)`

**channel_members**
`channel_id FK, user_id FK, last_read_at, last_read_message_id, muted` · PK `(channel_id, user_id)`

**channel_permissions**
`channel_id FK, role, can_view, can_send` · PK `(channel_id, role)`

**messages**
`space_id FK, channel_id FK, author_id FK, body, parent_id FK null(스레드), reply_count, last_reply_at, pinned, edited_at, deleted_at`
인덱스: `(channel_id, created_at)`, `(parent_id)`

> `parent_id`가 `null`이면 채널 최상위 메시지, 값이 있으면 그 메시지의 스레드 답글이다. 채널 리스트는 `parent_id IS NULL`만 조회한다.

**message_edits** — 수정 전 본문 이력
`message_id FK, prev_body, edited_at`

**reactions**
`message_id FK, user_id FK, emoji` · PK `(message_id, user_id, emoji)`

**mentions**
`message_id FK, user_id FK null, type enum(user|channel|everyone)`
인덱스 `(user_id, message_id)` — 읽지 않은 멘션 뱃지 계산용

**attachments** (구 `files`)
`space_id FK, channel_id FK, message_id FK null, uploader_id FK, name, ext, size_bytes, storage_key, width, height`

> 이전의 `retained` 플래그("영구 보관")는 사내 요구였다. 서비스화 시에는 스페이스별 스토리지 쿼터가 필요하므로 `spaces.storage_used_bytes` 집계로 대체한다.

### 이슈

**issues**
`space_id FK, key(SPACE-138), title, description, status enum(backlog|doing|review|done), priority enum(low|mid|high), label, assignee_id FK null, source enum(native|github|gitlab), external_id, origin_message_id FK null`
UNIQUE `(space_id, key)`

> `origin_message_id` — "대화 → 이슈" 기능의 역방향 링크. 이슈에서 원래 대화로 돌아갈 수 있다.

**issue_comments**
`issue_id FK, author_id FK, body`

### 저장소 연동

**repos**
`space_id FK, provider enum(github|gitlab), external_project_id, name, full_path, default_branch, linked_channel_id FK null, webhook_secret, synced_at`

**repo_events** — 채널 피드로 흘려보낸 이벤트
`repo_id FK, type(push|pr|mr|issue|release), payload jsonb, message_id FK null, occurred_at`

### 알림 · AI

**notifications**
`space_id FK, user_id FK, type, payload jsonb, read` · 인덱스 `(user_id, read)`

**ai_runs** — 사용량 추적 (서비스화 시 과금·제한의 기반)
`space_id FK, user_id FK, kind(summarize|ask|draft_issue), prompt_tokens, completion_tokens, model, created_at`

### 제거되는 테이블

`attendance`, `worklogs`, `notices`, `gitlab_repos`(→ `repos`로 대체)

```
GET    /api/auth/github/callback
```


## 5. 실시간 (Socket.IO)

### 룸

| 룸 | 용도 |
|---|---|
| `user:{userId}` | 개인 알림, 다중 기기 동기화 |
| `space:{spaceId}` | 프레즌스, 채널 목록 변경, 룸 무효화 |
| `channel:{channelId}` | 메시지 · 리액션 · 타이핑 |
| `thread:{messageId}` | 스레드 답글 (스레드 패널을 연 사용자만) |

### 서버 → 클라이언트

```
message:new           message:edited        message:deleted
reaction:added        reaction:removed
thread:reply
typing
presence:changed
notification:new
issue:updated
repo:event
rooms:invalidate      ← 채널 참여·권한 변경 시. 클라이언트가 룸 재조인 요청
```

### 클라이언트 → 서버
```
rooms:sync            연결 직후 및 rooms:invalidate 수신 시
typing                { channelId }
read                  { channelId, lastReadMessageId }
```

### 이전 구조에서 고칠 것

| 문제 | 해결 |
|---|---|
| 연결 시점에만 룸 join → 새 채널·권한 변경 반영 안 됨 | `rooms:invalidate` / `rooms:sync` 왕복 도입 |
| `read` 이벤트가 `last_read_at`을 DB에 저장하지 않고 릴레이만 함 | `ChannelMember`에 실제 저장 후 `read:synced` 브로드캐스트 |
| `presence:changed`, `issue:updated`가 설계에만 있고 미구현 | Redis 프레즌스 + 이슈 서비스에서 emit |
| 게이트웨이의 JWT 시크릿 폴백이 다른 모듈과 불일치 | 시크릿 해석을 단일 `JwtConfig`로 통합 (§6) |

## 6. 인증 · 권한

### 토큰
- access(15분) + refresh(7일). refresh는 회전(rotation)시키고 재사용을 탐지한다.
- 웹 클라이언트에는 refresh를 `HttpOnly` 쿠키로 내려 XSS 노출을 줄인다. 네이티브는 보안 저장소를 쓰므로 응답 바디로 준다.
- **시크릿 하드코딩 폴백(`'dev-insecure-secret'`)을 전부 제거하고**, 부팅 시 `JWT_SECRET` 미설정이면 프로세스를 중단시킨다. 조용히 약한 키로 뜨는 것보다 낫다.

### 가드 체인
```
JwtAuthGuard          전역. @Public()으로만 예외
  └ SpaceGuard        :spaceId 멤버십 검증 → req.spaceMember 주입
      └ SpaceRoleGuard         @MinRole('admin') 등
      └ ChannelPermissionGuard @ChannelAction('send') 등
```

역할 서열: `guest < member < admin < owner`. `owner`는 스페이스당 1명, 이전 불가 상태에서 탈퇴할 수 없다.

### CORS
이전의 무조건 `enableCors()`를 **환경변수 화이트리스트**로 바꾼다. Flutter 웹 배포 도메인만 허용한다. 네이티브 앱은 CORS 대상이 아니다.

## 7. 저장소 연동

1. GitHub OAuth로 얻은 토큰으로 사용자의 저장소 목록을 조회한다.
2. 저장소를 채널에 연결하면 서버가 해당 provider에 **웹훅을 등록**하고 `webhook_secret`을 저장한다.
3. `POST /api/webhooks/:provider/:repoId`가 이벤트를 받아 **서명을 검증**하고(HMAC), `repo_events`에 적재한 뒤 연결된 채널에 시스템 메시지로 게시한다.
4. 웹훅을 등록할 수 없는 환경(사내망 등)을 위해 폴링 폴백을 유지한다.

`GitProvider` 인터페이스로 GitHub/GitLab 차이를 흡수한다. 기존 `IssueProvider` 추상화와 같은 패턴이다.

## 8. AI

이전에는 사내 코드 유출 우려로 501 스텁이었다. 개인 프로젝트에서는 그 제약이 없으므로 실제 기능으로 만든다.

| 기능 | 입력 컨텍스트 |
|---|---|
| 대화 요약 | 채널 최근 메시지 N개 |
| 코드 질의 | 질문 + 연결된 저장소의 관련 파일 |
| 이슈 초안 | 선택한 메시지들 → 제목·설명·라벨 제안 |

- 호출은 **큐(Redis)를 거쳐 비동기 처리**하고 결과를 소켓으로 밀어 준다. LLM 응답 지연이 HTTP 타임아웃을 물지 않게 한다.
- 모든 호출을 `ai_runs`에 토큰 수와 함께 기록한다. 서비스화 시 스페이스별 한도의 근거가 된다.
- **API 키는 서버에만 둔다.** 클라이언트가 LLM을 직접 호출하는 경로는 만들지 않는다.

## 10. 구현 순서

1. **스키마 재작성** + 마이그레이션 리셋 + 시드 (데이터가 없으므로 지금이 가장 싸다)
2. **auth 개편** — 가입 · 시크릿 폴백 제거 · 리프레시 회전
3. **spaces + SpaceGuard** — 이후 모든 모듈이 이것에 의존한다
4. 기존 channels · messages를 **spaceId 기준으로 이관**
5. 스레드 · 리액션 · 멘션 · 핀
6. realtime 개편 (룸 동기화 · 읽음 저장 · 프레즌스)
7. attachments (스토리지 추상화)
8. issues (+ 대화 → 이슈)
9. repos (OAuth · 웹훅 · 이벤트 피드)
10. ai (큐 · 요약 · 질의)
11. **테넌트 격리 통합 테스트** — Phase 2 진입 조건
