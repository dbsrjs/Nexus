# Nexus — 제품 기획서

> 개정 이력: 2026-08-11 — 사내 통합 개발 환경 → **개인 프로젝트(서비스화 지향)** 로 방향 전환.
> 2026-09-23 — §5.1 에 구현 상태(13-2 시점)를 붙였다.
> 이전 기획(사내 메신저 통합 솔루션)은 폐기되었다. 변경 내역은 [§8](#8-이전-기획에서-바뀐-점)에 정리한다.

## 1. 한 줄 정의

**Nexus는 개발자를 위한 커뮤니케이션 허브다.**
Discord의 가벼움, Slack의 업무 구조, 그리고 개발 워크플로(이슈 · 저장소 · AI)를 한 화면에 합친다.

## 2. 왜 만드는가

일반 메신저는 개발 맥락을 모른다. 저장소에서 무슨 일이 있었는지, 지금 논의 중인 게 어떤 이슈인지 알려면 사람이 링크를 붙여 넣어야 한다. 반대로 개발 도구(GitHub, Jira)는 대화를 담지 못한다.

Nexus는 그 사이를 메운다.

- 커밋 · MR · 이슈 이벤트가 **채널 안으로 흘러 들어온다**
- 대화 중에 **그 자리에서 이슈를 만든다**
- AI가 **대화와 코드를 같은 맥락으로 읽는다**

경쟁 상대는 Slack이 아니라 "Slack + Jira + GitHub 알림 봇을 각각 켜 놓은 상태"다.

## 3. 단계별 타겟

서비스화를 목표로 하되, 처음부터 남을 위해 만들지 않는다. **내가 매일 쓰는 도구가 먼저다.**

| 단계 | 사용자 | 검증할 것 |
|---|---|---|
| **Phase 0 — 나** | 나 혼자 | 내 사이드 프로젝트들을 채널로 나누고, 할 일 보드와 저장소를 붙여 실제로 매일 쓰이는가 |
| | | ↑ **기능은 갖춰졌다**(2026-09-23). 대화(오프라인 포함) · 파일 · 이슈 보드 · 스프린트 · GitHub 연동 · AI 까지 동작한다. 남은 것은 알림 · 푸시와 실제 배포 |
| **Phase 1 — 소규모** | 2~10인 팀 (스터디 · 사이드 프로젝트) | 초대 → 온보딩이 매끄러운가. 여러 명이 붙어도 실시간이 버티는가 |
| **Phase 2 — 공개** | 누구나 스페이스 생성 | 테넌트 격리, 스토리지 쿼터, 과금 |

> **설계 원칙**: Phase 0에서는 기능을 최소로 만들되, **데이터 모델과 테넌트 경계는 Phase 2 기준으로 미리 잡는다.** 나중에 갈아엎는 비용이 가장 큰 게 이 둘이기 때문이다. 반대로 UI·과금·관리자 도구는 필요해질 때 만든다.

## 4. 핵심 개념

Discord와 Slack의 용어가 섞이면 혼란스러우므로 아래로 통일한다.

| 개념 | 대응 | 설명 |
|---|---|---|
| **Space** | Discord 서버 / Slack 워크스페이스 | **테넌트 루트.** 모든 데이터는 스페이스에 속한다 |
| **Category** | Discord 카테고리 / Slack 섹션 | 채널을 묶는 폴더 |
| **Channel** | 양쪽 동일 | 대화 단위. 공개 · 비공개 |
| **Thread** | Slack 스레드 | 메시지에 달리는 답글 묶음 (Discord식 별도 스레드 채널이 아님). **채널 타임라인에서 빠진다** |
| **Reply(답장)** | 카카오톡 답장 | 특정 메시지를 인용해 **대화 흐름 안에서** 답한다. 스레드와 다른 축이라 컬럼도 따로다(`quoted_message_id`) |
| **DM** | 양쪽 동일 | **스페이스 내부**에 한정 (§7 결정 참조) |
| **Member** | 양쪽 동일 | 사용자 × 스페이스. 역할은 스페이스마다 따로 |

**출시 준비 앞으로** 옮겼다 — 설정 창은 외부 사용자를 받기 전에 있어야 하는 기본 기능이다.

| 항목 | 내용 |
|---|---|
| **사용자 설정** | 디스코드식 설정 창 — 표시 이름 · 프로필 사진 · 비밀번호 변경 · 알림 설정 · 화면(테마) |

**설계할 때 볼 것** (2026-09-23 에 코드를 보고 적어 둔 것 — 결정이 아니라 출발점):

- **표시 이름** — `PATCH /api/me { name }` 은 이미 있다. 남은 것은 화면과, 바뀐 이름이 다른 멤버의
  캐시(메시지 작성자명)에 퍼지는 경로. 받는 사람마다 같은 값이라 스페이스 룸 브로드캐스트로 충분하다
- **프로필 사진** — 가장 큰 덩어리. 첨부는 스페이스에 묶여 `SpaceGuard` 로 지키는데 아바타는
  **사용자 단위**라 저장 · 열람 경로를 새로 정해야 한다(누가 볼 수 있나 — 스페이스를 함께 쓰는
  사람만). 업로드 시 `sharp` 로 정사각 축소(썸네일과 같은 도구). `UpdateMeDto` 의 `avatarUrl`
  (임의 URL 을 받는 자리)은 이때 걷는다. 앱의 `NexusAvatar` 는 지금 이니셜만 그린다
- **비밀번호 변경** — 현재 비밀번호 확인 + 새 비밀번호(가입과 같은 10자 규칙). 바꾸면 다른
  기기의 리프레시 토큰 family 를 끊는다. **틀린 현재 비밀번호를 401 로 답하지 않는다** — 앱의
  401 인터셉터가 리프레시로 오인한다
- **알림 설정** — 실제 알림(푸시 · 데스크톱 · 인앱)은 14단계 뒤의 «마지막» 단계에서 생긴다.
  **동작하지 않는 스위치는 두지 않는다**(CLAUDE.md §3-7). 그래서 14단계의 「알림」 항목에는 지금
  동작하는 **채널 음소거**만 넣고(`channel_members.muted` 컬럼은 있고 바꾸는 API 가 없다),
  푸시 · 데스크톱 알림 스위치는 «마지막» 단계가 알림을 만들 때 **같은 자리에** 더한다
- **화면** — 지금 계정 메뉴에 있는 테마 선택을 설정 창으로 옮길지
- **메시지 답장**은 7-3 에서 이미 만들었다(인용 답장). 14단계 대상이 아니다

### 5.1-b 15단계 — UI/UX 개편 (14 다음, 출시 준비 전) — ✅ 2026-09-29

> 없다. 아래 「설계할 때 볼 것」은 출발점 기록으로 남긴다. 실제로 정한 것은
> [15단계 설계](superpowers/specs/2026-09-27-15-자체-UI-design.md), 경과는 진행 기록 «15-1»~«15-3».

2026-09-23 에 더했다. **Flutter 기본(Material) 컴포넌트를 전부 자체 UI 로 바꾸고, 앱 디자인을
더 세련되게 다듬는다.**

2026-08-22 의 UI 리디자인은 **토큰 층과 셸 구조**를 고친 것이었다 — 컴포넌트 테마로 Material 의
기본값을 덮었을 뿐 위젯은 Material 그대로다. 이번은 그 위젯들을 바꾸는 단계다.

**설계할 때 볼 것** (2026-09-23 에 코드를 세어 적어 둔 것 — 결정이 아니라 출발점):

- **대상 규모** — `app/lib` 에서 쓰는 Material 위젯: 로딩 스피너 25 · `IconButton` 22 ·
  `ListTile` 17 · `TextButton` 16 · `SnackBar` 14 · `AppBar` 14 · `OutlinedButton` 11 ·
  `TextField` 9(+`TextFormField` 2) · 바텀시트 7 · `FilledButton` 6 · 팝업 메뉴 5 ·
  `Chip` 3 · `Tooltip` 3 · 다이얼로그 2 · `Checkbox` 2. 자체 위젯은 지금
  `shared/widgets/` 에 `NexusAvatar` · `NexusLogo` 둘뿐이다
- **어디까지 바꾸나** — 눈에 보이는 컴포넌트(버튼 · 입력 · 목록 행 · 시트 · 메뉴 · 토스트 ·
  스피너 · 칩)가 대상이다. `MaterialApp` · `Scaffold` · 라우팅 같은 뼈대까지 걷을지는 설계 때
  정한다 — 뼈대는 접근성 · 키보드 · 텍스트 선택을 공짜로 준다
- **지킬 규칙** — 토큰 이름은 바꾸지 않는다(`tokens.css` ↔ `theme.dart` 1:1). 색 · 간격을 바꾸면
  [디자인 시스템](./디자인-시스템.md)을 먼저 고친다. 반응형 분기는 `app_shell.dart` 한 곳.
  컴포넌트 라이브러리를 들이지 않고 직접 만든다(CLAUDE.md §3-8). 카드에 그림자를 쓰지 않는 규칙은
  디자인 방향을 바꾼다면 함께 다시 본다
- **시작 자료** — `.design/` 에 2026-08-22 의 열 화면 목업(캔버스 원본)이 있고,
  `design-system/components/` 에 컴포넌트 프리뷰 여덟이 있다
- **검증이 가장 큰 위험이다** — 화면을 도는 통합 테스트가 없다. 지난 리디자인이 심은 라우터 결함은
  열흘 뒤에야 드러났다. 컴포넌트를 바꾸는 단위마다 Windows 로 눈으로 확인하고, 위젯 테스트가
  텍스트 · 위젯 타입을 찾는 곳(Material 위젯 타입으로 찾는 테스트)은 함께 고친다
- **14단계와의 순서** — 14단계 설정 창은 지금 컴포넌트로 만들고 15단계에서 함께 바뀐다. 두 번
  손대는 비용이 크면 14단계를 시작할 때 설정 창에 쓸 자체 컴포넌트만 먼저 뽑는 것도 방법이다
- **이슈 보드 드래그 정렬(2026-09-27 에 이 단계로 넣었다)** — 서버의 `PUT .../position` 은
  9-1 부터 있고 화면만 메뉴로 옮긴다. 컴포넌트를 바꾸는 단계라 끌어 놓기도 여기서 만든다

### 5.1-c 16~20단계 — 단계 밖에 있던 기능 (2026-09-27 편입)

13-3 까지 끝난 시점에 §5.1 표의 ⬜ · 🔸 와 CLAUDE.md §4 «아직 없는 것» 이 **어느 단계에도
속하지 않았다.** 그것을 묶어 16~20단계로 만들었다.

- **16 멤버 · 권한**
  - 서버에는 `GET/PATCH/DELETE .../members/:userId` · `POST .../invites` · `POST /invites/:code/accept`
    가 이미 있다. 앱에는 멤버 목록을 읽는 `members_api.dart` 뿐이다 — 초대 링크 만들기 · 받기
    화면과 역할 변경 · 내보내기 화면이 남았다. **초대 받기는 딥링크 없이도 되게** 코드 붙여넣기로
    시작한다(딥링크는 «마지막»)
  - 비공개 채널 멤버 추가 · 제거 API 가 없다(CLAUDE.md §5 빚). 추가하면 대상의 `rooms:invalidate`
    가 필요하다 — 역할 변경이 이미 같은 경로를 쓴다
  - `channel_permissions` 행은 스키마에 있고 **기본값을 덮는 예외**로만 쓴다(CLAUDE.md §3).
    옛 `src/permissions/` 는 단일 테넌트 시절 코드라 `spaceId` 기준으로 다시 쓴다. 읽기 전용
    채널에서도 리액션은 남긴다(§3 판단 9)
- **17 DM · 프레즌스 · 타이핑**
  - DM 은 `ChannelKind.dm` 채널 한 개 + `channel_members` 두 행으로 둔다(스키마에 자리가 있다).
    **스페이스 안 한정**(§7). 같은 두 사람의 DM 이 둘 생기지 않게 유일성을 어디서 지킬지 정한다
  - 프레즌스는 `users.global_status` 가 있지만 **스페이스를 넘는 값**이다. 브로드캐스트는 함께
    쓰는 스페이스 룸으로만 — 모르는 사람에게 온라인 여부가 새지 않게
  - 타이핑은 저장하지 않는 휘발 이벤트다. 실시간 스펙에 `typing` 자리만 있다
- **18 인앱 알림**
  - `notifications` 테이블(`type` 문자열 + `payload` JSON)이 있고 옛 모듈은 미이관이다.
    **멘션 뱃지(7-4)는 알림 테이블 없이 집계로 돈다** — 알림함이 그 집계를 대체할지, 옆에 둘지 정한다
  - 채널 음소거(14단계)가 알림 생성을 막아야 한다
- **19 AI 기록**
  - `ai_runs` 에 사슬(`parentRunId`)은 있고 **목록 API 가 없다**(`GET .../ai/runs/:runId` 하나).
    본인 것만(13-1 판단) · 사슬의 뿌리 단위로 묶어 보인다
- **20 GitLab 연동**
  - `OauthProvider.gitlab` · `RepoProvider` enum 은 있다. 옛 `src/gitlab/` 은 살릴 것이 없다(전환 계획 §3.4).
    `repos/` 가 GitHub 을 직접 부르는 자리를 provider 뒤로 숨기는 것이 첫 일이다

### 5.2 SHOULD — Phase 1~2

검색(채널 내 · 전체), 알림 세분화 설정, 커스텀 역할/권한, 스페이스 테마, 메시지 임시저장, 링크 미리보기(unfurl), 파일 스토리지 쿼터

### 5.3 보류 — Phase 2+

| 기능 | 보류 이유 |
|---|---|
| **음성 · 화상 채널** | Discord의 시그니처지만 WebRTC SFU(mediasoup/LiveKit) 운영은 별도 프로젝트급 비용. **"디스코드 느낌"에서 가장 크게 빠지는 부분이므로 우선순위를 다시 논의할 여지가 있다.** |
| 봇 · 앱 플랫폼 | 서드파티 생태계는 사용자가 생긴 뒤 |
| 화면 공유 | 음성/화상에 종속 |
| 전문 검색 엔진 | Postgres FTS로 시작. Elasticsearch는 규모가 필요해진 뒤 |
| 소셜 로그인 외 SSO/SAML | 기업 고객이 생긴 뒤 |

### 5.4 이번 전환으로 **제거**되는 기능

| 기능 | 제거 사유 | 대체 |
|---|---|---|
| **근태 (출퇴근 체크)** | 사내 조직 전제. 개인 프로젝트에서 의미 없음 | 없음 |
| **업무일지** | 위와 동일 | 개인 노트가 필요하면 채널로 |
| **공지 게시판** | 별도 모델일 이유가 없음 | 공지 채널 + 메시지 핀 고정 |
| **전역 역할 매트릭스** | 단일 조직 전제라 멀티테넌시와 정면 충돌 | 스페이스별 역할 |

## 6. 차별점 — "개발 연동"을 어떻게 구현할 것인가

이 부분이 없으면 Nexus는 그냥 Slack 클론이다. 세 가지를 반드시 구현한다.

1. **저장소 이벤트 → 채널**
   저장소를 채널에 연결하면 커밋 · PR/MR · 이슈 이벤트가 그 채널에 카드 형태로 흐른다. 웹훅 수신(폴링 폴백은 두지 않았다).

2. **대화 → 이슈 (한 번의 동작으로)**
   메시지 우클릭 → "이슈로 만들기". 원문 메시지가 이슈 설명에 인용되고, 역방향 링크가 남아 이슈에서 원래 대화로 돌아갈 수 있다.

3. **맥락을 아는 AI**
   AI에 채널 대화 + 연결된 저장소 정보를 함께 넘긴다. 용례:
   - "이 채널에서 오늘 결정된 것 요약해줘"
   - "이 스택트레이스, 우리 저장소 어디랑 관련 있어?"
   - "위 논의로 이슈 초안 만들어줘"

   > 이전 기획에서 AI는 사내 코드 외부 유출 우려로 501 스텁이었다. **개인 프로젝트에서는 이 제약이 사라지므로 AI를 실제 기능으로 승격한다.**

## 7. 확정한 설계 결정 (되돌릴 수 있음)

| 결정 | 선택 | 근거 | 재검토 조건 |
|---|---|---|---|
| DM 범위 | **스페이스 내부 한정** (Slack식) | 전역 DM(Discord식)은 스페이스 탈퇴·차단·프라이버시 경계 처리가 복잡해진다 | 사용자가 여러 스페이스에 걸친 인맥을 원할 때 |
| 스레드 방식 | **메시지 하위 답글** (Slack식) | Discord식 스레드-as-채널보다 모델과 UI가 단순 | 스레드가 길어져 독립 공간이 필요해질 때 |
| 역할 | **고정 enum 4종** | 커스텀 역할은 권한 UI 비용이 큼. Phase 0에 불필요 | Phase 2 |
| 음성 채널 | **보류** | §5.3 | 사용자 요구가 확인될 때 |

## 8. 이전 기획에서 바뀐 점

| 항목 | 이전 (사내 통합 개발 환경) | 이후 (Nexus) |
|---|---|---|
| 성격 | 사내 단일 조직 전용 | 개인용으로 시작 → 서비스화 |
| 테넌시 | 단일 테넌트 (전역 채널 목록) | **멀티테넌트 (Space가 루트)** |
| 모바일 | Capacitor (웹뷰 래핑) | **Flutter 네이티브** |
| 웹 · PC | 공유 `www/` + Electron | **Flutter 웹 · 데스크톱으로 통합** |
| 호스팅 | 사내 온프렘 고정 | 클라우드 전제, 온프렘 가능 |
| 인증 | 이메일/비번 (가입 없음, 시드로만 생성) | **회원가입** (GitHub OAuth 는 저장소 연동용 계정 연결) |
| 저장소 연동 | 사내 GitLab 읽기 전용 | GitHub 웹훅 기반(GitLab 은 나중) |
| AI | 501 스텁 (유출 정책 보류) | **실제 기능** |
| 근태 · 업무일지 · 공지 | 포함 | 제거 |
| 대화 기능 | 메시지 + 수정 이력 | **+ 스레드 · 리액션 · 멘션 · 핀** |

## 9. 성공 기준

- **Phase 0**: 내가 다른 메신저를 켜지 않고 2주 연속 Nexus만으로 내 프로젝트를 관리한다.
- **Phase 1**: 초대받은 사람이 설명 없이 가입 → 첫 메시지까지 도달한다.
- **Phase 2**: 스페이스 간 데이터가 절대 새지 않는다(테넌트 격리 테스트 통과).
